# Issue tracker：飞书反馈台账与 GitHub

本仓库新的缺陷、功能切片、Spec 和执行 Ticket 使用 GitHub Issues 跟踪，默认通过仓库内已认证的 `gh` CLI 读写。

## 与正式资料的关系

- `docs/requirements/`、已批准原型、技术设计、开发计划和 `docs/project/work-orders/` 继续承担正式范围与验收依据；Issue 不替代它们。
- 既有 S00–S12 工单保留原位，不批量迁移、不删除，也不在 GitHub 重复创建同内容 Issue。
- 只有尚未完成、需要独立实施或跟踪的具体缺陷和功能切片才创建 Issue。
- Issue 应链接对应正式工单或需求，并只记录本次问题、证据、范围、依赖、验收标准和明确排除项。
- Issue 与正式资料冲突时停止实施，先按 `AGENTS.md` 的资料层级修正正式资料或取得确认。

## 飞书反馈与迭代台账

业务同事不了解 GitHub 时，使用飞书多维表格 `跟单管理系统｜反馈与迭代台账` 收集反馈和展示处理进度。仓库只记录多维表名称、数据表名称和协作规则，不保存 Base Token、table ID、record ID、访问凭证或带资源标识的内部链接；需要操作时按标题解析当前有权限的真实 Base。

多维表包含两张数据表：

| 数据表 | 用途 | 主要字段 |
|---|---|---|
| `业务反馈` | 面向业务同事收集问题、建议和操作疑问 | 反馈标题、反馈类型、使用端、问题描述、截图/视频、提交人、提交时间、状态、关联研发任务 |
| `开发任务` | 由项目负责人维护分析、开发和交付进度 | 任务标题、任务类型、来源反馈、优先级、负责人、开发状态、GitHub Issue、PR链接、完成时间 |

`业务反馈.状态` 只使用：

- `待处理`：尚未完成分析和处理安排；新反馈默认使用该状态。
- `处理中`：正在分析、已建立开发任务，或关联任务仍在实施和验证。
- `已完成`：处理结果已经验证或由反馈方明确接受；仅创建开发任务或 GitHub Issue 不能视为完成。

`开发任务.开发状态` 只使用：`待分析`、`待建Issue`、`已建Issue`、`开发中`、`PR检查`、`待部署`、`待验证`、`已完成`。状态按实际进度更新；合并 PR 不自动等于已部署，部署也不自动等于业务验证完成。

### 反馈到交付的关系

1. `业务反馈` 原则上一条记录一个可独立描述的现象或建议，并附上能够定位问题的端、说明和证据。
2. 分析后在 `开发任务` 建立对应记录并关联来源反馈。多条相同根因的反馈可以合并到一个开发任务；一个范围过大的反馈也可以拆成多个开发任务。
3. 尚在收集或分析中的开发任务不自动创建 GitHub Issue。确认需要独立实施或长期跟踪，且范围、依赖和验收标准已明确后，才按本文件规则创建 Issue，并把链接回填到 `GitHub Issue` 字段。
4. 开始开发后，人工维护开发状态、PR链接和完成时间；一期先不建设 Base 与 GitHub 的自动同步，避免重复创建或错误改状态。
5. 关联开发任务完成并通过对应环境验证或明确接受边界后，再把业务反馈改为 `已完成`。仍有未完成拆分任务时，反馈保持 `处理中`。

Base 是业务反馈入口和进度台账，GitHub Issue 是正式开发执行入口，二者都不能覆盖正式资料。反馈涉及业务范围、权限、状态、字段或验收口径变化时，必须先按 `AGENTS.md` 更新并确认对应需求；涉及页面交互或实现方式时，还要同步对应原型或技术设计。对 Base、GitHub 或正式资料的写入继续分别遵守各自确认门。

## Issue 最小完整度

Issue 可以比正式工单简短，但必须让新的执行者无需依赖聊天记录即可回答：

1. 当前有什么问题或要实现什么；
2. 已有何种可复现证据或业务依据；
3. 本次修改包含和不包含什么；
4. 依赖哪些正式资料、前置任务或确认门；
5. 通过哪些可验证结果才算完成。

## 操作约定

- 创建：`gh issue create`，优先使用仓库的 Bug 或 Feature 模板。
- 读取：`gh issue view <number> --comments`。
- 列表：`gh issue list --state open`，按需要增加标签或状态条件。
- 评论、关闭或修改标签属于 GitHub 外部写操作，执行前遵守当前任务授权范围。
- Pull Request 不是需求入口；PR 必须关联 Issue，并使用仓库 PR 模板记录验证、风险和发布边界。

## 默认交付流程

1. 先确认正式资料、页面确认门和 Issue 范围；Issue 记录问题、证据、包含与排除项及验收标准。
2. 从完整 CI 已通过的最新 `main` 创建独立分支或 Worktree，默认命名为 `codex/issue-<编号>-<简短说明>`；主工作区有未提交修改时必须使用独立 Worktree。
3. 一个分支和 PR 原则上只交付一个可独立验收的 Issue；提交和测试证据只覆盖该范围。
4. PR 正文关联对应 Issue；确实完成全部验收标准时使用 `Closes #<编号>`，尚未完成时只使用普通关联，不提前关闭。
5. PR 完整 CI 和必要审查通过后才能合并 `main`；合并后的最终提交必须再次通过 `main` 完整 CI，才可作为后续发布候选。
6. 纯文档小改、紧急修复或用户明确指定直接使用 `main` 时可以省略 PR，但仍须保护无关修改、完成相称验证，并遵守远程 CI 和所有发布确认门。

合并 PR 只表示代码进入稳定集成基线，不等于创建版本、部署环境、执行迁移、发布小程序或发送真实消息。

## 当 Skill 要求发布或读取 Ticket

- “发布到 issue tracker”表示创建 GitHub Issue。
- “读取 Ticket”表示读取对应 GitHub Issue 正文、评论和标签。
- `to-spec` 只用于需要跨多个任务或上下文的变更；单一小缺陷可直接创建一个 Bug Issue。
- `to-tickets` 只把已确认 Spec 拆成纵向、可独立验收的 Issue，不把技术层横向拆成互相无法交付的票据。
