# 二期能力构想：仓库来货验收、工厂分析与库存预警

> **版本：** V0.1
>
> **日期：** 2026-09-01
>
> **状态：** IDEA（后续能力构想）
>
> **范围声明：** 本文档只用于记录候选方向和待确认问题，不属于一期或当前 S12 实施范围，不代表正式需求、原型、技术方案或开发授权。任一能力进入开发前，必须另行完成口径确认、需求更新、原型确认、技术设计和工单确认。

## 1. 构想目标

在一期订单、派工、正常发货、质检返修和通知闭环之上，继续探索三类能力：

1. 让仓库人员以尽可能少的操作完成来货数量验收、多货和少货登记；
2. 对各工厂的交付、来货差异、次品、返修和报废数据做可追溯的月度分析；
3. 只读查询聚水潭库存、销售、采购和实际入库数据，生成 SKU 级每日库存风险和催货建议。

三类能力共用以下原则：

- MySQL 8.0 继续作为跟单管理系统正式业务事实库，不因为接入 OCR 或大模型而更换数据库；
- OSS 保存需要留档的原始图片、语音和报告文件，MySQL 保存结构化结果、快照、确认与审计记录；
- AI 优先负责识别、解释和起草建议，不直接修改正式业务数据；
- 数量、比率、风险等级和截止日期由确定性规则计算，大模型不自行编造指标；
- 每份识别结果或分析结论都应能下钻到原始图片、发货单、采购单、入库单或计算快照。

## 2. 当前基线与新范围

一期正式需求明确不设置正常发货的待收货、已收货、实际收到数量或到货日期；质检单返修也不关联原订单或原发货单。因此，“来货验收”不是在现有页面上增加一个 AI 按钮，而是新的业务流程和数据事实。

一期已支持一个实体纸箱混装多个订单、商品和颜色/规格，并按发货单、箱号和箱内明细保存数据。后续箱贴和扫码验收应复用这一结构，不按“一箱一商品”假设重做数据模型。

当前返修数据已包含工厂、商品规格、仓库退回数量、返修数量和报废数量，但由于不关联原发货批次，暂不能严谨计算按发货批次或收货批次的真实次品率。

## 3. 仓库来货验收与差异登记

### 3.1 现有输入场景

当前仓库图片通常是纸箱全景，中间贴有纸质标签，标签包含打印的工厂、货号和品名，以及手写的颜色、尺码、装箱数量、发货日期和箱号。多货或少货数量可能另外手写在纸箱上，或后续标注在图片中。

这类图片同时存在手写、涂改、胶带反光、斜拍和背景干扰，不适合让 OCR 识别后无确认地直接写入正式数据。

### 3.2 候选输入方式

保留三种互补入口：

1. **拍照＋OCR＋语音或点选差异**：兼容现有箱贴和仓库习惯，适作首期候选方案；
2. **小程序码＋语音或点选差异**：系统生成标准箱贴后，仓库扫码精准定位一只纸箱，适作长期主流方案；
3. **手动选择＋结构化表单**：当照片、语音或扫码失败时的必备兜底。

系统不把对话框当作唯一入口。自由文本和语音用于降低差异录入成本，结构化确认卡片才是正式提交入口。

### 3.3 OCR 验收流程

1. 仓库人员拍摄箱贴和纸箱；
2. 原图先保存到受控 OSS，识别任务异步执行；
3. OCR 识别工厂、货号、品名、颜色/规格、装箱数量、发货日期、箱号和差异标注；
4. 服务端使用工厂、发货单、SKU 和箱号做严格匹配，不接受模型生成的未知本地商品；
5. 页面展示原图、识别值、候选匹配、置信度和阻断错误；
6. 仓库人员修正后确认，服务端在事务内写入正式来货记录和操作日志。

低置信度、多个候选匹配、数量非法、找不到来源发货单、来源发货单已作废或疑似重复图片时，必须阻止自动确认。

### 3.4 标准箱贴与扫码验收

一张箱贴对应一个实体纸箱，不对应单个订单或单个商品。主要生成入口放在工厂小程序的正式发货单详情；管理员网页发货单详情可提供查看和重新下载。订单详情只通过关联发货单进入箱贴，不直接按订单生成箱贴。

箱贴建议包含：

- 小程序码；
- 发货单号、工厂、发货日期和箱号/总箱数；
- 箱内各订单、货号、品名、颜色/规格和数量；
- 本箱总数量；
- 当纸面无法完整展示混装明细时，明确提示扫码查看全部。

小程序码不直接存放商品、手机号或完整业务数据，只携带随机、不可猜测且可失效的箱贴标识。服务端验证登录身份、仓库权限、箱贴版本和发货单状态后，再返回箱内数据。

发货单作废或装箱内容改变后，旧箱贴必须失效。相同数据只是重新打印时，应沿用同一箱贴版本，不制造多个同时有效的身份。

### 3.5 仓库员工角色与小程序页面

如果仓库人员不属于现有管理员，后续候选方案为新增独立的“仓库员工”角色，不为了扫码验收而授予管理员权限。

最小页面集合：

1. **扫码验收**：扫一扫入口、待继续草稿和最近扫码；
2. **箱子验收**：箱贴状态、发货单与箱号、箱内全部明细、一致/多货/少货录入、语音辅助、现场图片和确认提交；
3. **我的验收记录**：查看本人近期草稿、已提交记录和更正状态；
4. **我的**：身份、手机号脱敏信息和退出登录。

最小权限：

- 使用微信身份登录并绑定仓库员工身份；
- 扫描箱贴并且只查看该箱子验收所必需的工厂、发货单、箱号和箱内明细；
- 创建和修改本人未提交的验收草稿；
- 确认数量一致，或登记多货、少货、备注和现场凭证；
- 查看本人近期提交和更正结果。

明确不授予：

- 查看全部订单、价格、合同或人员资料；
- 修改工厂已提交的原发货单；
- 管理用户、工厂、产品、订单、返修或通知配置；
- 删除已提交验收记录或无痕修改正式数据。

已提交记录填错时，候选规则为新建可追溯的更正记录，不直接覆盖原记录。

### 3.6 候选数据结构

正式表名和字段仍需在技术设计阶段确认，当前只记录职责：

| 候选数据 | 职责 |
|---|---|
| 识别任务 | 原图/语音、识别状态、模型版本、置信度、错误和耗时 |
| 识别明细 | 原始文本、候选工厂、SKU、规格、箱号和差异结果 |
| 箱贴标识 | 箱子、版本、生成人、生成时间、是否失效和签名标识 |
| 来货验收 | 来源发货单、箱子、工厂、验收人、验收时间、来源和状态 |
| 验收明细 | 订单、SKU、规格、应收、实收、多货、少货和修正链路 |

### 3.7 待确认问题

- 仓库人员是否全部使用微信，是否需要另外支持网页或飞书入口；
- 是否新增独立仓库员工角色，由谁审核、启停和更正记录；
- “应收”和“实收”的口径是否以箱内发货数量为准，是否允许分次验收同一箱；
- 多货、少货是否会回写订单进度，还是只作为仓库差异事实和月账单依据；
- 箱贴尺寸、打印设备、纸张格式、混装明细换页和重打规则；
- 仓库原图、语音和现场凭证的保留期限与访问权限；
- 确认后填错、重复扫码、整单作废和旧箱贴流转到仓库时的处理规则。

## 4. 工厂履约与质量分析

### 4.1 分析节奏

工厂履约和质量分析以月度复盘为主，每日或每周可补充严重延迟和高风险异常。

候选指标：

| 指标 | 候选口径 |
|---|---|
| 数量及时率 | 截止合同出货时间已有效发货数量 ÷ 应发数量 |
| 整单及时率 | 合同出货时间前全部发完的订单数 ÷ 当期到期订单数 |
| 来货差异率 | 多货和少货绝对数量 ÷ 验收实收数量 |
| 次品率 | 质检次品数量 ÷ 同口径质检实收数量 |
| 报废率 | 报废数量 ÷ 次品数量 |
| 返修完成周期 | 返修完成时间 − 仓库退回时间 |
| 重复问题率 | 同工厂、商品/规格和次品原因的重复出现情况 |

上述口径均为候选。特别是次品率、来货差异率和返修完成周期，需先补齐验收批次关联、质检分母和明确完成时间后才能正式计算。

### 4.2 后端处理原则

1. 定时任务按日和月生成不可变的指标快照；
2. 指标模块按已确认公式计算比率、同比/环比和工厂排名；
3. 规则模块识别连续延期、次品率上升、同类原因反复出现等可证明异常；
4. AI 只接收结构化指标、变化幅度和证据标识，生成原因解释和改进建议草稿；
5. 管理员确认后才将建议标记为正式报告，报告保留公式版本、快照时间、模型版本、提示词版本和证据链接。

### 4.3 管理员网页候选页面

管理员网页候选新增“数据分析”一级导航：

- **经营概览**：日期筛选、工厂比较、趋势和异常概览；
- **工厂分析**：单个工厂的交付、来货差异、次品、返修、报废和问题原因趋势；
- **AI 月报**：月度问题、证据、建议草稿、人工确认状态和导出。

首版不以自由聊天框为核心，先确保指标、证据、报告和下钻链路可验证。

### 4.4 Agent 升级边界

只有当系统能够按周期读取指标、根据风险选择进一步查询、跟踪建议是否执行，并经人工确认后创建协同任务或起草消息时，才视为向 Agent 转变。

首版定位为“AI 分析助手/月报工作流”，默认只读，不自动评罚工厂、修改业务数据或对外发送通知。

## 5. 聚水潭库存风险与催货建议

### 5.1 分析节奏与目标

库存风险以日分析为主，与工厂月度质量复盘分开：

| 能力 | 频率 | 目的 |
|---|---|---|
| 库存风险与催货建议 | 每日 | 识别当天应优先跟进的 SKU、采购单和工厂 |
| 工厂交付异常 | 每日或每周 | 识别可能延期的订单和持续不改善的异常 |
| 工厂质量与履约分析 | 每月 | 复盘及时率、来货差异、次品、返修和报废 |

每日库存报告不应等同于“库存低于固定数量就报警”。候选计算需组合当前库存、销售速度、待处理订单、采购进度、计划交期、实际入库和历史交付表现，生成未来 7/14/30 天风险。

### 5.2 聚水潭只读数据口径

| 数据对象 | 用途与约束 |
|---|---|
| 实际库存 | 使用库存明细的 `qty`，按 SKU 展示并去重后汇总；缺失数量不当作 0 |
| 销售订单 | 用于构建受控时间窗口内的销售速度、季节性和订单需求 |
| 采购单 | 使用采购数、已入库数、退货数、剩余未交数、计划交期和工厂/供应商信息 |
| 实际采购入库 | 实际入库数量和入库时间必须来自采购入库记录，按 `io_id` 去重，按实际入库时间使用 `date_type=2` |
| SKU 和款式资料 | 使用 SKU 连接库存、销售、采购与入库；款号用于管理层的款式汇总 |

实际库存、锁定量、订单占有数和仓库待发数应分开展示。在没有正式确认业务计算口径前，不自行相减并声称得到“可用库存”。

### 5.3 每日处理流程

1. 在固定时点只读获取目标范围内的聚水潭数据，记录查询时间、页数、数量和字段覆盖；
2. 去重、校验空值和异常值，保存不可变的每日数据快照；
3. 在已确认口径下计算 SKU 未来 7/14/30 天需求、库存覆盖天数、预计缺货日期、在途覆盖和交期风险；
4. 用规则或统计/机器学习模型生成风险等级和催货排序；
5. 大模型只基于风险结果、采购单和入库证据解释原因、组织日报和起草催货建议；
6. 第一阶段只展示和导出，不回写聚水潭、不自动创建任务、不自动向工厂发送催货消息。

正式分析必须先确定 SKU 覆盖范围、时间窗口和字段字典，再通过固定快照、历史回测和人工复核评估误报与漏报。

### 5.4 管理员网页候选页面

“数据分析”下候选增加：

- **库存预警**：SKU 风险列表、款式汇总、库存/销售/在途下钻、风险变化和筛选；
- **每日分析**：高风险 SKU、新增风险、已解除风险、预计缺货、交期冲突和今日建议跟进清单；
- **采购/催货证据**：查看相关采购单、剩余未交、计划交期、实际入库及历史变化。

日报优先展示与前一份快照相比发生变化的高风险项，避免每天反复罗列全量正常 SKU。

### 5.5 日报候选结构

每条高风险记录至少包含：

- SKU、款号、商品名称和颜色/规格；
- 原始库存、锁定/占有/待发等已定义字段；
- 7/14/30 天需求与预计缺货日期；
- 相关采购单、采购数、剩余未交数、计划交期和工厂/供应商；
- 经去重的实际入库数量和入库时间；
- 风险等级、触发规则、与前日差异和建议动作；
- 查询范围、截止时间、数据快照和公式版本。

### 5.6 向库存与催货 Agent 升级

当日报的数据口径、风险计算和历史回测稳定后，可分阶段增加：

1. 针对高风险 SKU 自动选择需要深查的采购单和实际入库记录；
2. 生成指定负责人、建议截止时间和证据链接的待办草稿；
3. 次日重新检查风险是否改善，区分未处理、已缓解和已解除；
4. 经人工单独确认后，再创建内部待办或起草催货消息。

即使升级为 Agent，也默认保持对聚水潭只读，不自动修改库存、采购单或入库单。

## 6. 候选模块与接口

为了让前端、定时任务和测试不绑定具体 OCR、大模型或聚水潭实现，候选按下列深模块划分：

| 模块 | 小接口的候选职责 |
|---|---|
| 来货识别 | 提交照片/语音，返回可修正的结构化草稿 |
| 来货确认 | 使用草稿和人工修正值进行严格校验，确认后事务写入 |
| 箱贴 | 根据正式发货单生成箱级箱贴，解析扫码标识，管理失效和重打 |
| 工厂指标 | 按已确认公式生成日/月指标快照和证据索引 |
| 库存风险 | 根据只读快照计算 SKU 风险、排序、变化和触发证据 |
| AI 报告 | 仅从已计算快照生成解释和建议草稿，保存版本与人工确认状态 |

OCR、语音识别、大模型和聚水潭连接均作为模块内部可替换的 adapter，不把厂商参数或响应结构泄漏到业务页面。

## 7. 候选实施顺序

正式编号和工单需等一期收口后单独确认，当前只记录依赖顺序：

1. 确认来货验收、多货/少货、改错和仓库权限口径；
2. 先实现不依赖 AI 的手动来货验收闭环；
3. 增加拍照 OCR、语音输入和人工确认；
4. 在发货流程稳定后增加标准箱贴与仓库扫码验收；
5. 补齐指标所需的验收批次、质检分母和返修完成时间；
6. 实现确定性工厂指标与月度快照，验证后再增加 AI 月报；
7. 针对受控 SKU 范围做聚水潭字段盘点、固定快照和基线回测；
8. 先上线规则型库存预警和每日分析，再增加 AI 解释、催货建议和 Agent 跟踪。

## 8. 正式启动前确认门

任一候选能力进入正式实施前，至少需要：

1. 在需求文档中定义业务对象、角色、字段、状态、数量和错误修正口径；
2. 确认管理员网页和小程序的页面、交互、空状态、错误状态和跳转；
3. 完成数据表、事务、幂等、审计、文件和外部 adapter 设计；
4. 使用真实但脱敏的箱贴、手写和模糊图片建立识别评测集，记录准确率、需人工修正比例和失败类型；
5. 确认聚水潭字段字典、SKU 覆盖、时间窗口、分页完整性和缺失值处理；
6. 对库存风险和工厂分析公式做历史回测，并由业务人员确认误报、漏报和建议的可执行性；
7. 单独确认所有真实模型调用、定时任务、通知、待办和对外发送，不从“开发 AI 能力”默认扩展授权。

## 9. 当前不在范围内

- 立即修改一期正式需求、原型或技术设计；
- 立即增加仓库角色、来货表、箱贴、扫码、OCR、AI 报告或定时任务；
- 更换 MySQL，迁移生产数据或增加未验证的向量数据库；
- 使用 AI 无确认地写入正式来货、数量、采购或返修数据；
- 自动回写聚水潭，自动修改库存/采购/入库单，或未经确认对外发送催货消息；
- 自动对工厂评罚、扣款或生成正式业绩结论。
