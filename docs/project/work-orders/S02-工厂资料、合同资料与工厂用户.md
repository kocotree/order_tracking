## 1. 工单目标

本工单打通“管理员建立工厂资料 → 工厂人员在小程序申请 → 管理员审核并绑定工厂 → 工厂用户恢复所属工厂身份”的闭环：

1. 普通管理员和最高管理员均可新增、查看和编辑工厂基础资料、联系人、来源别名和合同资料；
2. 工厂用户首次进入单一微信小程序工程时取得微信身份并授权本人手机号；
3. 未绑定工厂身份的用户填写真实姓名，选择固定职位和系统已有工厂后提交申请；
4. 普通管理员和最高管理员均可查看申请详情、通过或填写原因拒绝申请；
5. 通过时管理员再次确认绑定工厂，系统把申请人设为该工厂的启用工厂用户；
6. 管理员可以按工厂查看用户，并启用或停用工厂用户；
7. 后端在会话、查询和资源访问处始终校验当前工厂归属，禁止跨工厂读取。

S02 完成后可以独立演示两个不同工厂账号分别申请、审核、登录和隔离访问。订单、产品、发货、返修、合同 Excel 和通知设置仍不在本工单实现。

## 2. 已确认范围与权限边界

### 2.1 本工单包含

- 工厂、联系人、来源别名、供应商编号、工厂代码和合同资料；
- 工厂资料版本冲突和审计记录；
- 工厂用户微信登录、官方手机号授权、申请、重新申请、审核和拒绝原因；
- 工厂用户归属、固定职位、启用和停用；
- 管理员网页端“工厂资料”和“人员管理”中工厂用户相关页面；
- 单一微信小程序工程中的工厂登录、申请、审核中、已拒绝、已停用和已登录身份入口；
- OpenAPI、网页端和小程序端生成类型、权限测试和真实 MySQL 8 集成测试。

### 2.2 权限边界

- 普通管理员和最高管理员都可以维护工厂资料、审核工厂用户申请、确认绑定工厂以及启停工厂用户。
- 只有最高管理员可以查看和审核管理员申请、启停普通管理员；S02 不改变 S01 的该项规则。
- 工厂用户只能归属一个工厂，职位只允许“老板”或“工厂员工”，职位不产生权限差异。
- 待审核、已拒绝、账号停用或工厂归属失效的工厂用户不能查看业务数据。
- 工厂数据隔离必须由后端查询条件和资源授权实现；不能先读取全部数据再由前端过滤。

### 2.3 明确不包含

- 不实现产品同步、产品页面或聚水潭生产接口；
- 不实现飞书订单获取、候选、草稿、派工、发布或订单页面；
- 不实现发货、退回、返修、附件、合同 Excel 导出或合同编号生成；
- 不实现通知偏好、微信订阅消息或“我的”页面通知设置；
- 不创建第二个微信小程序工程，不发布小程序，不修改正式 AppID；
- 不选择、购买或创建短信、对象存储及其他付费资源；
- 不提供长期批量导入工厂资料的可见入口；上线前一次性初始化属于后续受控数据准备，不在本工单写入真实数据。

## 4. 数据库迁移与领域模型

所有迁移和集成测试使用真实 MySQL 8、InnoDB 和 `utf8mb4`。所有时间戳保存 UTC；手机号和小程序授权结果不得明文写入日志。

### 4.1 `factories`

至少保存：

- 内部 `factory_id`；
- 供应商编号、日常工厂名称、工厂代码；
- 单位全称、单位地址、法定代表人、可选委托代理人；
- 可选开户银行和银行账号；
- 启用状态、版本、创建和更新时间。

约束：

- 供应商编号必填，去除首尾空白并统一保存为大写，全系统唯一；
- 工厂名称必填且全系统唯一；
- 工厂代码必填，去除首尾空白并统一保存为大写，全系统唯一；
- 单位全称允许重复；
- 合同资料完整仅指工厂代码、单位全称、单位地址和法定代表人均已填写；
- 供应商编号与工厂代码是两个独立字段，不能互相覆盖；
- 普通编辑时供应商编号只读，其他允许编辑的资料按版本更新。

### 4.2 `factory_contacts`

保存一个或多个联系人：

- 工厂、联系人姓名、联系电话；
- 展示顺序和是否主要联系人；
- 创建和更新时间。

联系人允许为空；保存时按页面顺序整体校验并在同一事务内更新，不能留下半套联系人资料。

### 4.3 `factory_source_aliases`

保存飞书来源工厂名称到系统工厂的严格映射：

- 来源别名、目标工厂和展示顺序；
- 来源别名去除首尾空白后全系统唯一；
- 同一工厂可以有一个或多个来源别名；
- S02 只维护映射，不连接飞书、不导入订单。

### 4.4 `factory_applications`

至少保存：

- 申请用户、真实姓名和已验证手机号引用；
- 固定职位、申请目标工厂；
- 待审核、已通过或已拒绝状态；
- 申请时间、审核人、审核时间、拒绝原因；
- 审核时最终确认的绑定工厂；
- 版本和重新申请历史关联。

约束：

- 同一用户只能有一条当前待审核申请；
- 申请工厂必须是系统已有且启用的工厂，客户端不能自由创建或提交任意工厂名称；
- 申请手机号必须来自微信官方手机号授权结果，不信任客户端自行填写号码；
- 通过和拒绝只能处理当前待审核版本，重复或并发审核返回 409；
- 拒绝原因必填，历史申请和审核证据不可覆盖；
- 审核通过时用户角色、工厂归属、启用状态和审核记录在同一事务内生效。

### 4.5 `users` 与会话

在 S01 `users` 和会话基础上增加或启用：

- 工厂用户的 `factory_id` 归属；
- “老板”“工厂员工”固定职位；
- 归属和身份版本变化所需字段。

账号停用、角色撤销或工厂归属失效后，网页或小程序已有会话必须立即无权访问；重新启用后旧会话不得自动复活，需要重新登录。普通管理员对工厂用户的启停不得影响最高管理员或普通管理员账号。

## 5. 后端业务模块与 API

### 5.1 模块边界

新增独立的工厂与工厂身份模块，公开接缝为：

- 工厂命令和查询服务；
- 工厂用户申请、审核和用户状态服务；
- `/api/v1` HTTP API；
- 微信身份与手机号适配接口；
- MySQL 仓储和审计接口。

模块复用 S01 的内部用户、微信外部身份、会话、安全和审计基础，不复制第二套登录或用户模型。

### 5.2 代表性 API

具体字段以实现时生成的 OpenAPI 为准，路径保持技术设计的稳定分组：

- `GET /api/v1/factories`：工厂小程序只读搜索和选择启用工厂，返回申请所需的最小字段；
- `POST /api/v1/factory-applications`：提交或按规则重新提交本人申请；
- `GET /api/v1/factory-applications/me`：查询本人当前申请及历史审核状态；
- `GET /api/v1/admin/factories`、`POST /api/v1/admin/factories`：管理员列表和新增；
- `GET /api/v1/admin/factories/{factoryId}`、`PATCH /api/v1/admin/factories/{factoryId}`：详情和带版本编辑；
- `GET /api/v1/admin/factory-applications`、`GET /api/v1/admin/factory-applications/{applicationId}`：管理员列表和详情；
- `POST /api/v1/admin/factory-applications/{applicationId}/approve`：确认绑定工厂并通过；
- `POST /api/v1/admin/factory-applications/{applicationId}/reject`：填写原因并拒绝；
- `GET /api/v1/admin/users?role=factory`：按工厂查询工厂用户；
- 复用 S01 用户状态接口启停工厂用户，但后端按操作者和目标角色重新校验权限。

写接口继续使用 S00/S01 已有请求编号、幂等和审计基础。可编辑资料提交 `version`，版本不一致返回 409 和统一错误结构。

### 5.3 审计

至少记录：

- 工厂新增和编辑的操作者、目标、版本和字段级非敏感变更摘要；
- 工厂申请提交、重新提交、通过、拒绝；
- 审核时申请工厂与最终绑定工厂；
- 工厂用户启用、停用和归属变化；
- 被拒绝的越权访问和关键 409 冲突。

日志和审计不得保存微信临时 code、手机号授权 code、访问凭证、完整手机号、Cookie、Token、密钥或验证码。

## 7. 工厂小程序

继续使用现有 `miniprogram/` 单一微信小程序工程，通过角色和身份状态进入对应流程，不创建第二套项目。

- 登录页、协议勾选、微信授权登录和身份识别沿用已确认工厂小程序原型；
- 首次未绑定用户通过微信官方能力授权手机号；
- 申请页只展示真实姓名、已验证联系电话、固定职位和从系统已有工厂中搜索单选；
- 申请审核中页展示提交资料、提交时间、刷新审核结果和退出登录；
- 已拒绝页展示拒绝原因和审核时间，允许修改资料后重新提交；
- 已停用或无权限页展示对应提示和所属工厂；
- 已通过用户能够恢复同一内部账号并取得本人所属工厂身份；登录成功后的最小可见落点按第 13 节确认结果实施；
- S02 不实现订单任务、发货记录、返修、通知设置等后续业务页面；登录成功后只提供验证身份与归属所需的最小只读入口，不伪造后续业务数据。

真实微信 AppID、官方手机号能力和真机条件缺失时，沿用 S01 的显式本地演示开关和假适配器完成自动化及本地演示；普通开发、测试和生产配置不得出现默认假登录后门。

### 11.2 本地人工验收

使用本地假适配器和真实 MySQL 8 演示：

1. 管理员新增两个工厂，核对供应商编号自动大写、唯一约束和合同资料完整状态；
2. 编辑工厂时供应商编号不可修改，其他允许字段可保存，过期版本出现冲突提示；
3. 两个不同微信测试身份分别授权不同手机号，选择不同已有工厂并提交申请；
4. 普通管理员查看申请详情，分别完成通过和填写原因拒绝；
5. 重新申请后由最高管理员通过并再次确认绑定工厂；
6. 两个工厂用户重新登录，系统恢复各自内部用户和工厂归属；
7. 工厂 A 身份访问工厂 B 的测试资源被后端拒绝；
8. 管理员停用工厂用户后旧会话立即失效，重新启用后必须重新登录；
9. 审计记录能关联操作者、申请、工厂和请求编号，且不包含敏感明文。

由于订单、发货和返修属于后续工单，S02 的隔离验收使用最小受保护测试资源或身份范围查询证明后端工厂谓词生效，不提前制作业务页面。

## 13. 开工确认

正式资料与已确认低保真原型之间存在两项可见内容缺口，必须在业务编码前确认：

1. V1.40 要求管理员维护委托代理人、开户银行、银行账号和来源别名，但现有工厂详情/新增/编辑低保真弹窗只展示供应商编号、工厂代码、工厂名称、法定代表人、单位全称、联系人、联系电话和单位地址。建议在原有弹窗内补充前述四项正式字段，不新增独立页面或额外操作。
2. S02 要验证审核通过后的工厂用户重新登录，但工厂“任务”属于 S04，“发货记录”属于 S05，“我的—通知设置”属于 S11。建议 S02 登录成功后只进入最小只读身份页，展示姓名、脱敏联系电话、职位、所属工厂和退出登录；不展示订单、发货、返修、通知开关或不可用的占位业务入口。

用户确认上述两项最小方案和本工单其余范围后，把状态改为“已确认，待实施”，再在 `codex/s02-factory-users` 独立 worktree 开始第一个失败测试。确认前不得提交 S02 业务代码。
