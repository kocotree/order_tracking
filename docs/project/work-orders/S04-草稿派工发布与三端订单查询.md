## 1. 工单目标

本工单先用应急手工建单打通“管理员保存草稿 → 完整派工 → 发布正式订单 → 管理员双端查询 → 工厂只查看本厂任务 → 管理员撤回、删除、完成或撤销完成”的核心闭环：

1. 管理员网页端可以手工创建订单草稿，填写唯一订单编号、订单日期、唯一跟单人员、唯一合同出货时间、产品规格和订单数量；
2. 管理员可以把每条订单明细完整分配给一个或多个工厂，保存草稿时使用版本号防止并发覆盖；
3. 发布时在单个 MySQL 事务中完成最终校验、生命周期变更、审计日志和通知发件箱写入；
4. 草稿对所有工厂不可见，发布后只有被分配的工厂能查询本厂任务，且不能读取其他工厂名称、数量或进度；
5. 管理员网页端和管理员小程序通过同一套 API 查询全部订单、展示状态与进度，管理员小程序保持只读；
6. 尚无有效正式发货记录的已发布订单可以撤回到草稿或删除；草稿可以删除；
7. 管理员可以确认订单完成，或填写原因撤销完成，系统保留每次完成和撤销历史；
8. 三端正式订单只显示“未完成、已逾期、已完成”，草稿只在管理员网页端单独展示。

S04 完成后，一张包含多产品、多规格和两个工厂的手工草稿可以发布，并由管理员网页端、管理员小程序和两个工厂账号从同一 MySQL 数据中看到各自正确的内容。S05 后续只需把飞书候选转换为同一套草稿、明细和派工数据，不另建订单流程。

## 2. 已确认业务范围

### 2.1 订单和草稿

- 订单编号必填、全系统唯一；数据库使用内部 `order_id` 关联数据；
- S04 只创建来源为 `manual` 的应急手工订单，来源为 `feishu` 的草稿由 S05 接入；
- 一张订单只有一个订单日期、一个跟单人员和一个合同出货时间；
- 跟单人员只允许正式需求已确认的“烧麦、松子、橄榄、大葱、青椒”，用于展示和筛选，不限制其他管理员处理；
- 一张订单可以包含多个产品规格；同一订单内同一 `product_variant_id` 只能有一条订单明细，重复选择时合并数量；
- 产品只能从 S03 已落库且当前可用于新订单的规格中选择，不允许在建单页新增或补齐产品资料；
- 草稿可以反复编辑；已发布订单一期不允许直接编辑订单内容或派工；
- 草稿只对管理员网页端可见，管理员小程序和工厂小程序均不返回草稿。

### 2.2 多工厂派工

- 每条订单明细可以分配给一个或多个工厂；
- 同一订单明细和工厂只能存在一条派工，重复选择时合并下单数量；
- 数量只接受正整数，不接收小数、负数、空值或数字字符串的模糊转换；
- 发布前，每条订单明细的全部工厂下单数量合计必须严格等于该明细订单数量；
- 发布前，涉及的工厂必须处于启用状态，并且每个工厂至少有一名审核通过且启用的工厂用户；
- 工厂只读取本厂下单数量，不填写计划数量，也不能查看同一订单的其他工厂信息。

### 2.3 生命周期和展示状态

数据库持久化生命周期只使用：

- `DRAFT`：草稿，工厂不可见；
- `PUBLISHED`：已发布正式订单；
- `COMPLETED`：管理员确认完成。

展示状态按东八区业务日期计算：

- `COMPLETED` 始终显示“已完成”；
- `PUBLISHED` 且当前日期晚于合同出货时间时显示“已逾期”；
- 其他 `PUBLISHED` 显示“未完成”；
- `DRAFT` 在管理员网页端单独显示“草稿”，不属于正式订单状态；
- 不增加“待生产、生产中、发货中、已取消、已删除”等订单状态。

### 2.4 发布、撤回、删除、完成和撤销完成

- 发布必须使用客户端当前 `version`，二次确认后执行；
- 发布事务必须重新校验订单编号、产品可用性、工厂状态、工厂用户、合同出货时间和派工合计，不能只相信草稿保存时的结果；
- 发布成功后写操作日志和通知发件箱；外部通知发送失败不回滚订单发布；
- 已发布订单尚无任何有效正式发货记录时可以撤回到草稿，保留订单内容和历史，撤销相关工厂待办并写入通知发件箱；
- 已经存在有效正式发货记录时拒绝撤回；
- 草稿可以软删除；已发布订单只有在不存在有效正式发货记录时才能软删除；删除后二次确认，订单不再出现在订单列表和工厂任务中，但审计证据继续保留；
- 订单不会因为数量达到目标而自动完成；管理员在网页端核对后手工确认完成；
- 确认完成前必须确认不存在待管理员处理的发货单作废申请；S04 尚未实现发货单时该结果为空，S07、S08 必须接入同一守卫；
- 管理员撤销完成时必须填写原因，订单恢复为 `PUBLISHED`，再按当前日期显示“未完成”或“已逾期”；原完成记录不能覆盖或删除；
- S04 的数量汇总初始已发数量为 0。S07 接入正式发货数量台账后复用相同响应字段和状态操作，不重写 S04 订单生命周期。

## 6. 数据库迁移与领域模型

迁移和集成测试必须使用真实 MySQL 8、InnoDB、`utf8mb4` 和微秒时间戳，不能用 SQLite 替代。数据库时间戳保存 UTC，订单日期和合同出货时间使用东八区业务日期。

### 6.1 `orders`

至少保存：

- `order_id`：内部 UUID 主键；
- `order_no`：业务订单编号，规范化后全系统唯一；
- `source`：`manual` 或 `feishu`，S04 只写 `manual`；
- `order_date`：订单日期；
- `tracker`：唯一跟单人员；
- `contract_ship_date`：唯一合同出货时间；
- `lifecycle`：`DRAFT`、`PUBLISHED`、`COMPLETED`；
- `version`：草稿并发控制版本；
- `published_at`、`published_by`；
- `completed_at`、`completed_by`；
- `deleted_at`、`deleted_by`；
- `created_at`、`created_by`、`updated_at`、`updated_by`。

约束：

- `order_no` 唯一，空白裁剪后不能为空；
- `source` 和 `lifecycle` 使用数据库检查约束；
- 删除使用 `deleted_at` 软删除，不增加 `DELETED` 生命周期；
- 对外查询默认排除 `deleted_at IS NOT NULL`；
- 订单编号是否区分大小写由数据库唯一索引和服务规范化规则统一，不能只靠页面判断。

### 6.2 `order_lines`

至少保存：

- `order_line_id`、`order_id`、`product_variant_id`；
- `order_quantity` 正整数；
- 产品编码、产品名称、颜色/规格、商品分类和图片引用的订单快照；
- `created_at`、`updated_at`。

约束：

- 同一 `order_id + product_variant_id` 唯一；
- 历史展示读取订单快照，不因 S03 产品改名、停用、移出白名单或换图而改写；
- 草稿新增或替换规格时只允许当前 `available_for_new_orders = true` 的规格；已发布历史引用不因来源停用而删除。

### 6.3 `order_assignments`

至少保存：

- `order_assignment_id`、`order_line_id`、`factory_id`；
- `assigned_quantity` 正整数；
- 工厂名称的订单快照；
- `created_at`、`updated_at`。

约束：

- 同一 `order_line_id + factory_id` 唯一；
- 发布时逐行校验派工合计等于订单数量；
- 已发布后不直接更新派工；S07 的发货进度通过派工主键关联。

### 6.4 `order_completion_records`

每次状态事件追加一条，不覆盖历史：

- `record_id`、`order_id`；
- `action`：`COMPLETE` 或 `REOPEN`；
- `reason`：确认完成可空，撤销完成必填；
- 操作人、来源终端、操作时间；
- 操作前后生命周期和数量摘要。

### 6.5 进度响应和后续工单接缝

- S04 查询层返回订单、明细和派工的订单数量、已发数量、未发数量、多发数量、少发数量及进度百分比；
- S04 没有正式发货记录，已发数量恒为 0，但必须通过统一的进度读取接口返回，不能在三端各自写死；
- S07 通过数量台账接入同一进度读取接口后替换为真实累计值；
- 撤回、删除和完成守卫使用公开的订单执行状态查询接缝。S04 默认结果为“无有效发货、无待处理作废申请”，S07、S08 必须实现真实查询，不修改订单路由的业务判断顺序。

## 7. 领域服务和事务

### 7.1 保存草稿

单个事务中：

1. 校验管理员身份和订单字段；
2. 规范化并检查订单编号唯一性；
3. 锁定已有草稿并校验 `version`，新建时创建 `manual` 草稿；
4. 校验产品规格当前可用、数量为正整数并合并重复规格；
5. 校验工厂存在，规范化并合并重复派工；
6. 原子替换该草稿的明细和派工，版本加一；
7. 写入操作日志后提交。

草稿允许暂时未完成派工，但页面和 API 必须返回明确校验问题；只有发布要求所有字段与派工完整。保存失败整体回滚，不留下半张草稿。

### 7.2 发布

发布使用高风险写操作幂等键，并锁定订单、明细和派工：

1. 订单必须为未删除的 `DRAFT`，且 `version` 与客户端一致；
2. 订单编号、订单日期、跟单人员和合同出货时间完整有效；
3. 至少有一条订单明细，每条数量为正整数；
4. 每个规格仍可用于新订单；
5. 每条明细至少有一个工厂，派工合计严格等于订单数量；
6. 所有工厂启用且各自至少有一名审核通过、启用的工厂用户；
7. 生命周期改为 `PUBLISHED`，记录发布人和时间；
8. 为各工厂写入唯一待办/通知发件箱记录并写审计日志。

任一步失败整体回滚。重复相同幂等键返回首次成功结果，不重复发布、通知或审计。

### 7.3 撤回和删除

- 撤回锁定订单并查询执行守卫；只有 `PUBLISHED` 且不存在有效正式发货记录时可以回到 `DRAFT`；
- 撤回保留原明细、派工、发布记录和审计，撤销工厂待办并为受影响工厂写通知发件箱；
- 删除锁定订单；`DRAFT` 可以删除，`PUBLISHED` 只有无有效正式发货记录时可以删除，`COMPLETED` 不允许直接删除；
- 删除只写 `deleted_at/deleted_by` 和审计，不级联物理删除订单、明细、派工、完成历史或通知证据；
- 撤回和删除均要求二次确认后的高风险幂等请求；并发发布、撤回或删除只能有一个成功。

### 7.4 完成和撤销完成

- 确认完成锁定 `PUBLISHED` 订单，检查不存在待处理发货单作废申请后改为 `COMPLETED`；
- 完成不以已发数量等于订单数量为前提，记录当时订单/已发/多发/少发摘要；
- 撤销完成锁定 `COMPLETED` 订单，要求非空原因，改回 `PUBLISHED` 并追加 `REOPEN` 记录；
- 重复请求通过幂等键返回首次结果；不同管理员并发操作时后到请求返回明确的 409 状态冲突；
- 完成、撤销完成均只允许管理员网页端调用，管理员小程序和工厂小程序即使直接请求也必须被后端拒绝。

## 8. 后端 API 与权限

所有接口位于 `/api/v1`，使用现有会话和角色校验；响应带 `requestId`，列表统一分页、排序白名单和总数。具体请求响应模型以 FastAPI OpenAPI 为准。

### 8.1 管理员网页端写接口

| 方法 | 路径 | 用途 |
|---|---|---|
| `POST` | `/admin/orders` | 手工新建草稿 |
| `PUT` | `/admin/orders/{orderId}` | 按 `version` 保存完整草稿 |
| `POST` | `/admin/orders/{orderId}/publish` | 发布草稿 |
| `POST` | `/admin/orders/{orderId}/withdraw` | 撤回无有效发货的已发布订单 |
| `DELETE` | `/admin/orders/{orderId}` | 删除草稿或无有效发货的正式订单 |
| `POST` | `/admin/orders/{orderId}/complete` | 确认完成 |
| `POST` | `/admin/orders/{orderId}/reopen` | 填写原因撤销完成 |

发布、撤回、删除、完成和撤销完成要求 `Idempotency-Key`；保存草稿要求 `version`。典型错误：

- `400`：字段、数量或派工不完整；
- `403`：角色、终端或工厂权限不符；
- `404`：记录不存在、已删除或不在可见范围；
- `409`：订单编号重复、版本冲突、生命周期冲突、已经存在有效发货记录、存在待处理作废申请；
- `422`：请求模型类型不合法。

### 8.2 三端共用查询接口

| 方法 | 路径 | 权限和返回范围 |
|---|---|---|
| `GET` | `/orders` | 管理员返回全部未删除正式订单；工厂只返回本厂被派工的正式订单；管理员网页端通过管理参数可另外查询草稿 |
| `GET` | `/orders/{orderId}` | 管理员返回全部工厂进度；工厂只返回本厂派工，其他工厂字段在序列化前即移除 |
| `GET` | `/admin/dashboard/orders` | 管理员网页端订单看板统计和最近订单 |
| `GET` | `/admin/orders/{orderId}/audit-logs` | 管理员网页端查看订单操作日志 |

禁止先返回完整对象再由前端隐藏其他工厂数据。工厂列表和详情查询必须在 SQL 条件和响应 DTO 两层限制 `factory_id`；用另一个工厂的 `orderId` 猜测访问时返回 404。

### 8.3 查询字段和排序

- 搜索：订单编号、产品名称、颜色/规格；管理员小程序和工厂小程序按已确认原型只开放其对应搜索字段；
- 筛选：持久化生命周期/计算展示状态、工厂、跟单人员、合同出货时间范围；
- 排序白名单：默认紧急程度、合同出货时间升降序、订单日期最新、更新时间最新；
- 状态、逾期和默认排序统一在服务器查询服务中定义，三端不得各自计算出不同结果；
- 查询按东八区“今天”计算逾期边界，并对合同出货当天、次日和已完成优先级建立固定时钟测试。
