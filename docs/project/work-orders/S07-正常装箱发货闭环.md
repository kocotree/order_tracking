## 1. 工单目标

本工单打通“工厂查看本厂未完成任务 → 创建服务端发货草稿 → 选择本厂多个订单和规格 → 逐箱或按装箱组录入 → 选填凭证和备注 → 预览并幂等提交 → 发货立即计入订单进度 → 三端读取同一发货事实 → 管理员确认订单完成”的正常发货闭环：

1. 一张发货单只属于一个工厂，可以包含该工厂多个已发布、未删除订单的多个产品规格；
2. 工厂只能选择本厂派工，不得读取或提交其他工厂的订单、数量和进度；
3. 同一规格存在于多个订单时默认按合同出货时间最早的订单分配，工厂可以在提交前调整归属；
4. 每只实体箱有唯一箱号，允许混装多个订单、产品和规格；相同装法可使用装箱组批量应用到连续箱，尾箱和混装箱单独编辑；
5. 箱内明细按发货明细汇总后必须完全一致，不允许无箱归属或无订单归属的数量；
6. 工厂可以选填 0 至 3 张压缩后的发货凭证照片和备注；
7. 提交时在 MySQL 单事务内固化发货事实、追加数量台账、写操作日志和通知发件箱；正式发货不可直接编辑或删除；
8. 提交后的系统有效发货数量与初始已发数量形成统一已发数量，立即刷新三端订单进度；
9. 管理员网页端、管理员小程序和所属工厂小程序读取同一发货单，但接口按终端和角色裁剪字段；
10. 管理员网页端继续手工确认订单完成；S07 接入真实发货守卫，但作废申请守卫到 S08 才产生真实数据。

S07 完成后，两个不同工厂账号可以分别创建并提交发货单，系统在并发和重复提交下仍只形成一次有效数量变化，管理员双端和工厂端看到的发货、装箱与进度结果一致。

## 2. 业务范围与规则

### 2.1 发货草稿和正式发货单

- 发货单持久化状态只使用 `DRAFT`、`SHIPPED`；`VOID_PENDING`、`VOIDED` 及作废申请属于 S08，本工单不开放；
- 草稿只对创建它的同工厂用户可编辑，其他工厂不可见，管理员列表和正常发货记录不展示草稿；
- 正式发货单号在提交成功时生成，格式为 `FHYYYYMMDD-NNN`，日期使用 Asia/Shanghai 提交业务日期，当日流水号三位起步且全系统唯一；
- 草稿使用内部 UUID，不提前占用正式发货单号；提交失败或废弃草稿不造成正式流水号空洞；
- 正式发货日期取提交成功时的 Asia/Shanghai 业务日期，不由工厂手工修改；
- 正式发货单提交后不可直接编辑、删除或覆盖；撤回申请和审核作废由 S08 实现；
- 草稿和正式发货查询均排除已删除订单，不允许通过历史客户端数据向已撤回或已删除订单提交发货。

### 2.2 可选任务、默认分配和多发归属

- 只允许选择当前工厂在 `PUBLISHED` 订单中的派工明细；已完成订单默认不进入可选目录；
- 可发目录按合同出货时间升序、订单编号和产品稳定顺序排列；已逾期任务排在未完成任务之前，同日按订单编号稳定排序；
- 同一产品规格存在于多个订单时，默认选择合同出货时间最早且仍有未发数量的订单；工厂可以在装箱时显式改选其他订单；
- 每条装箱明细必须直接关联一个 `order_assignment_id`，产品名称、规格和工厂归属不能由客户端自由输入；
- 正常数量优先消耗所选派工的未发数量；允许超过待发数量，但多发部分必须继续明确归属到一个具体订单派工，不能形成无归属数量；
- 预览页逐订单显示本次发货数量；存在多发时显示“多发 X 件”并在最终提交前二次确认；
- 订单已发数量允许超过订单数量，未发数量下限为 0，多发数量永久按正式需求口径展示；
- 初始已发数量只参与统一已发和未发计算，不生成本系统发货单或装箱明细，也不能被 S07 修改。

### 2.3 箱号、装箱组、尾箱与混装

- 工厂先填写本次发货总箱数，系统在该发货单内生成从 `1` 开始的连续数字箱号；同一发货单箱号唯一；
- 每只箱至少包含一条正整数装箱明细，空箱不能进入预览或提交；
- 同一箱可以包含不同订单、产品和规格；同一箱内相同订单派工明细重复添加时合并数量；
- “装箱组”表示把当前箱的完整装法复制到指定数量的后续连续空箱；数据库仍保存每只实体箱和每只箱的实际明细，并记录其装箱组来源，不能只保存乘数；
- 装箱组不能覆盖已有内容的箱；需要调整的尾箱或混装箱解除该箱的组来源后单独编辑，不反向修改其他已复制箱；
- 减少总箱数时，如果将被移除的箱已有内容，必须二次确认；确认后只删除草稿箱内容，不影响任何正式发货事实；
- 提交时按 `shipment_line` 汇总全部 `shipment_box_items`，必须与发货明细数量完全一致；服务端从箱内事实重算发货明细，不接受客户端分别提交两套不一致总数。

### 2.4 凭证、备注与文件权限

- 发货凭证选填 0 至 3 张，仅接受常见图片格式；小程序先压缩再上传，后端仍校验实际 MIME、大小、数量和文件摘要；
- 凭证保存到私有对象存储，MySQL 只保存文件元数据和发货单关系；客户端不得指定对象键；
- 工厂草稿上传的凭证只允许创建者和同厂已授权用户读取，正式提交后允许管理员和所属工厂读取，其他工厂返回 404；
- 删除草稿中的凭证只解除草稿关系；对象清理由后台安全任务处理，不在请求中直接删除可能被引用的对象；
- 工厂备注选填，保存裁剪后的纯文本，不渲染 HTML；具体长度由接口模型和数据库约束统一，前后端使用同一限制。

### 2.5 提交事务、幂等和并发

提交使用 `Idempotency-Key`，在一个 MySQL 事务中：

1. 锁定草稿、涉及的订单派工和当日发货单流水号计数器；
2. 重新校验提交人、工厂归属、订单生命周期、箱号、装箱明细、文件数量和所有正整数数量；
3. 从箱内明细重算发货行，校验所有数量均有订单派工归属并标记多发结果；
4. 生成唯一正式发货单号和 Asia/Shanghai 发货日期；
5. 固化发货单、发货行、实体箱、装箱明细和凭证关系；
6. 按发货行向 `quantity_ledger` 追加唯一正向台账事件；
7. 更新或重算派工、订单的系统有效发货数量和统一进度摘要；
8. 写发货单日志、订单操作日志、审计日志和通知发件箱；
9. 将草稿改为 `SHIPPED` 后提交事务。

任一步失败整体回滚。相同用户、相同操作和相同幂等键的重复请求返回首次结果，不新增发货单、流水号或数量台账；同一草稿使用不同幂等键再次提交返回已提交结果，不重复生效。

### 2.6 订单进度、状态和完成操作

- 系统有效发货数量等于全部有效 S07 正常发货台账正向数量；S08 接入后再减作废和按发货单退回数量；
- 统一已发数量继续等于“初始已发数量＋系统有效发货数量”，订单、派工、三端页面和合同资格复用同一服务口径；
- 发货提交不自动把订单改为 `COMPLETED`；未完成或已逾期状态继续由订单生命周期与合同出货时间推导；
- 管理员网页端“确认订单完成”继续允许多发或少发，但提交前重新读取最新发货数量；
- S04 的“存在有效发货时禁止撤回或删除正式订单”守卫改接真实发货事实；
- S04 的“确认完成前不存在待处理作废申请”接口保持稳定，S07 返回无待处理申请；S08 再接入真实作废申请。

## 6. 待用户确认的原型差异与建议

### 6.1 装箱组如何落到现有四步原型

**冲突：** 正式需求和开发计划要求“装箱组”，已批准原型目前只支持逐箱录入，没有装箱组控件。

**建议采用：** 保留四步结构，在“装箱”步骤当前箱明细下增加次级操作“应用到连续箱”。点击后只填写“连续箱数”，系统把当前箱完整装法复制到后续连续空箱；尾箱或混装箱继续逐箱编辑。预览和详情仍逐只实体箱展示，不新增独立装箱组页面。

### 6.2 多发数量如何显式归属

**冲突：** 正式需求允许多发并要求显式归属订单；原型当前在超过所选订单待发数量时直接阻止添加。

**建议采用：** 装箱明细始终要求选择具体订单。超过该订单待发数量时不阻止，但在当前箱、汇总和提交预览中显示“多发 X 件”；最终提交前二次确认“多发部分归属订单 XXX”。同一规格有多个订单时仍默认最早合同出货时间，工厂可改选订单。

### 6.3 服务端草稿如何恢复

**冲突：** 开发计划和技术设计要求发货草稿，原型只保存当前页面内存，离开页面后会丢失。

**建议采用：** 第一次从箱号进入装箱时创建服务端草稿，之后每次“下一步”和返回上一步均自动保存。创建者再次进入创建流程时，如有一个未提交草稿，先弹窗选择“继续填写”或“重新创建”；重新创建会二次确认并软删除旧草稿。S07 不增加草稿列表页，也不允许多个并行草稿。

用户已确认本节三项建议，实施时将其作为正式可见交互写死；若发现新的业务规则或可见内容冲突，先同步修改本工单和必要原型并取得确认，再实施页面代码。

## 7. 数据库与领域模型

迁移和集成测试使用真实 MySQL 8、InnoDB、`utf8mb4` 和微秒时间戳。数据库时间戳保存 UTC，发货业务日期和流水号日期使用 Asia/Shanghai。

### 7.1 核心表

- `shipments`：内部 ID、正式发货单号、工厂、状态、业务日期、备注、创建人、提交人、提交时间和时间戳；
- `shipment_lines`：发货单、订单派工、实际发货数量及订单/产品/规格提交快照；
- `shipment_boxes`：发货单、箱号、稳定顺序和装箱组来源；
- `shipment_box_items`：实体箱、发货行/订单派工和正整数数量；
- `shipment_files`：发货单、私有文件和显示顺序，限制 0 至 3 张；
- `quantity_ledger`：订单派工、来源类型、来源事件、正负数量、操作人和时间；S07 只写正常发货正向事件；
- `shipment_number_counters`：Asia/Shanghai 业务日期和已分配最大流水号，用事务锁保证并发唯一；
- `idempotency_records`、`audit_logs`、`outbox_messages`：复用现有通用模型。

### 7.2 关键约束

- `shipments.shipment_no` 可空但一旦正式提交必须唯一且不可变；
- 同一发货单 `box_no` 唯一；同一箱和同一订单派工最多一条装箱明细；
- 发货行和装箱明细数量均为正整数；
- 同一发货单和同一订单派工最多一条发货行；
- 数量台账的“来源类型＋来源事件＋订单派工”唯一，防止重复生效；
- 正式发货行、箱和箱内明细不更新、不删除；后续逆向业务只能追加负向台账和状态事实；
- 所有对外查询以授权后的内部身份推导工厂和可见范围，不信任客户端提交的 `factory_id`。

## 8. API 与响应裁剪

代表性接口以 FastAPI OpenAPI 为唯一契约来源：

- `POST /api/v1/factory/shipments/drafts`：创建或返回当前用户唯一未提交草稿；
- `GET /api/v1/factory/shipments/drafts/current`：读取当前草稿；
- `PUT /api/v1/factory/shipments/drafts/{id}`：保存箱、装箱、备注和文件关系；
- `DELETE /api/v1/factory/shipments/drafts/{id}`：软删除未提交草稿；
- `POST /api/v1/factory/shipments/drafts/{id}/submit`：幂等提交；
- `GET /api/v1/factory/shipment-catalog`：返回本厂可选派工和默认顺序；
- `GET /api/v1/factory/shipments`、`/{id}`：本厂正式发货记录和详情；
- `GET /api/v1/admin/shipments`、`/{id}`：管理员网页端列表和详情；
- `GET /api/v1/mini/admin/shipments`、`/{id}`：管理员小程序裁剪后的列表和详情；
- 订单详情响应增加真实关联发货单摘要。

管理员小程序详情不返回产品图片和产品编码；工厂接口不返回其他工厂、其他工厂派工或管理员专用数据。所有列表统一分页、排序白名单和稳定次级排序。
