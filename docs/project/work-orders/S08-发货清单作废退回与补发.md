## 1. 工单目标

本工单在 S07 不可变正常发货事实之上完成四个闭环：

1. 管理员从有效发货单详情下载一张发货单对应的一份 `.xlsx` 发货清单；
2. 工厂从本厂已发货发货单详情填写原因并申请“撤回发货”，管理员在网页端审核通过或拒绝；
3. 作废审核通过后保留原发货事实，追加等量负向台账，把发货单改为已作废，并正确回退订单和工厂任务数量；
4. 管理员从有效发货单详情按规格执行退回，追加退回事件和负向台账，工厂在原正常任务中按普通 S07 发货流程补发。

S08 完成后，发货清单、作废、退回和补发均从 MySQL 中同一套不可变发货事实与只追加数量台账计算；原发货明细不被编辑、删除或覆盖，三端重新查询后看到一致状态、数量和操作记录。

## 2. 业务范围与规则

### 2.1 发货单状态与“有效发货事实”

- 发货单状态在 S07 的 `DRAFT`、`SHIPPED` 基础上增加 `VOID_PENDING`、`VOIDED`；
- `SHIPPED` 和 `VOID_PENDING` 在审核通过前仍是有效发货事实，继续计入系统有效发货数量；`VOIDED` 不再计入；
- `VOID_PENDING` 只表示存在一个待处理作废申请，不代表数量已经回退；
- `VOIDED` 只通过管理员审核作废产生，工厂不能直接删除、编辑或覆盖正式发货单；
- 发货单列表继续不增加状态列；状态、作废申请和处理记录在详情中展示；
- 有效发货单允许下载发货清单；已作废发货单不提供新的发货清单下载；历史已生成文件不作为当前有效数量依据。

### 2.2 工厂撤回申请与管理员审核

- 只有发货单所属工厂的启用用户可以对本厂符合条件的正式发货单申请“撤回发货”；
- 撤回申请不设置提交时限；已经发生部分退回的发货单仍允许工厂提交申请；
- 申请原因是裁剪后的必填纯文本，前后端使用同一长度限制；
- 同一发货单同一时间最多一个 `PENDING` 申请；重复点击、重复请求和并发申请不能产生多个待处理申请；
- 提交申请后发货单进入 `VOID_PENDING`，订单数量不变化，管理员确认订单完成的既有守卫必须真实阻止存在待处理申请的订单；
- 管理员审核通过或拒绝均必须使用幂等键并锁定发货单、待处理申请和受影响派工；只有 `PENDING` 申请可以被处理；
- 如果发货单已经存在任意已生效退回，服务端必须禁止审核通过，只允许管理员拒绝；前端可以禁用“通过”，但不能代替服务端校验；
- 审核通过时保留原发货行、箱、凭证和日志，追加与当前可作废有效数量相反的负向台账，把申请标记为 `APPROVED`，发货单改为 `VOIDED`；
- 审核拒绝时不改数量，把申请标记为 `REJECTED`，发货单恢复 `SHIPPED`；
- 重复审核返回首次结果或稳定冲突，不重复写负向台账、状态、日志或通知；
- 申请、审核通过和审核拒绝均保留申请人、申请时间、申请原因、审核人、审核时间和审核意见。

### 2.3 按发货单退回

- 只有管理员网页端可以执行；管理员小程序和工厂小程序只读展示结果；
- 只有 `SHIPPED` 且没有待处理撤回申请的有效发货单显示“退回”；`VOID_PENDING` 和 `VOIDED` 均禁止新增退回；
- 退回弹窗按已确认原型居中显示，标题下直接展示退回明细，不跳转到“返修退回”页签；
- 管理员至少选择一条可退明细；本次退回数量必须为正整数，且不得超过服务端重新计算的当前可退数量；
- 退回原因是本次选中明细共用的必填纯文本；
- 退回弹窗在产品编码前只读展示订单编号；每行固定对应工厂提交时绑定的原 `shipment_line` 和订单派工，管理员不选择或重新分配订单；
- 同一发货明细可以分多次退回，但累计已生效退回数量不得超过原发货数量；
- 事务内锁定原发货行、对应派工和订单，追加 `shipment_return_event`、逐明细退回记录及唯一负向数量台账；不修改原发货行数量；
- 退回不生成独立业务单号、独立列表、独立业务状态或工厂返修任务；
- 原发货单详情和原订单日志记录退回日期、管理员、订单、产品规格、数量、原因和数量变更前后值；
- 重复请求返回首次结果；并发退回以锁内最新可退数量校验，超量请求整体失败，不产生部分退回。

### 2.4 数量、订单状态与普通补发

- 系统有效发货数量统一等于正常发货正向台账减去作废通过和按发货单退回负向台账；
- 统一已发数量继续等于“初始已发数量＋系统有效发货数量”；未发、多发、少发、进度和合同资格继续复用同一口径；
- 作废通过和按发货单退回均使对应工厂任务未发数量增加；工厂直接从原正常订单任务进入 S07 创建发货单流程补发；
- 补发不设置专用类型、单号或页面，提交后按普通 `SHIPMENT` 正向台账重新计入；
- 受影响订单如果已完成，负向数量生效时恢复为 `PUBLISHED`，保留原完成记录和恢复原因；当前日期晚于合同出货时间时展示为“已逾期”，否则展示为“未完成”；
- 补发达到原数量也不自动完成，仍由管理员网页端重新确认订单完成；
- 作废或退回不能降低飞书导入的初始已发数量，只影响 S07 之后的系统有效发货数量。

### 2.5 发货清单 Excel

- 只从已经提交且当前有效的数据库发货事实生成，不读取小程序缓存、原型数据或前端汇总；
- 一张发货单生成一份文件，文件名为“厂家名称_发货日期_发货单号.xlsx”；文件名中的不安全字符必须稳定替换，不允许路径穿越；
- 最终工作簿只保留“发货明细”和“汇总”两个 Sheet，删除模板空白 `Sheet3`；
- “发货明细”标题写入发货日期和总箱数，表头固定为订单编号、箱号、货号、品名、颜色/规格、装箱数量、合计；
- “颜色/规格”直接使用系统组合字段，不拆分、不增加“尺码”列；
- 混装箱按多行输出相同箱号；相同装法的连续装箱组可以显示稳定箱号范围；总箱数按实体箱去重，总数量按明细小计汇总；
- 明细超过模板固定行数时，复制必要行高、边框、对齐、数字格式和打印设置后扩展，不截断；
- “汇总”表头固定为日期、名称、颜色/规格、数量，按“发货日期＋产品名称＋颜色/规格”跨订单合并；订单归属只保留在发货明细和数据库原发货记录中；
- 货号和其他业务字段使用提交时快照；产品后续修改不得改变原发货业务字段；
- 每次下载可以基于不可变发货事实重新生成；生成结果必须通过 ZIP/OOXML、合并单元格、扩展行、`openpyxl` 重新打开及 Excel/WPS 人工打开检查；
- 管理员小程序和工厂小程序不提供 Excel 下载。

### 2.6 通知、日志与审计边界

- 工厂提交撤回申请后写管理员站内通知/待办事件；S11 接入外部发送前，至少保证业务事件和发件箱记录可去重、可追踪；
- 审核通过或拒绝后通知申请人；管理员按发货单退回后通知对应工厂正常任务未发数量已增加并提示普通补发；
- S08 负责在业务事务内写入稳定通知事件或发件箱，不在本工单实现微信订阅消息授权、重试、定时提醒、运维告警或统一通知中心，这些属于 S11；
- 发货单操作日志、订单操作日志和统一审计日志均记录同一内部用户、来源终端、时间、原因、数量和前后值；
- 其他工厂读取发货单、作废申请、退回事件、凭证或导出文件统一返回 404，不泄露记录是否存在。

## 6. 已确认的正式差异与决定

### 6.1 Excel 模板结构和“颜色/规格”列

**确认决定：** 采用用户更新后的模板。模板包含 `发货明细`、`汇总` 和空白 `Sheet3`；生成文件删除空白 `Sheet3`，只保留前两个 Sheet。`发货明细` 使用订单编号、箱号、货号、品名、颜色/规格、装箱数量、合计七列；`汇总` 使用日期、名称、颜色/规格、数量四列。用户已从模板删除误留的“尺码”，实现不得重新增加。

`汇总` 按“发货日期＋产品名称＋颜色/规格”跨订单合并；由于汇总表不含订单列，订单归属只在 `发货明细` 和原始 `shipment_line` 中保留。

### 6.2 管理员作废审核交互

**确认决定：** 在发货单概览下、发货明细前增加“撤回申请”信息卡，展示申请人、申请时间和原因；右侧只提供“拒绝”“通过”。拒绝时填写必填审核意见，通过时展示影响的发货数量并二次确认，审核完成后该卡变为只读结果并同步进入操作记录。不新增作废列表、状态筛选或一级页面。

### 6.3 多订单同规格如何退回

**确认决定：** 工厂提交的每条发货明细已经绑定一个确定订单派工，退回时服务端自动扣减该原订单，不允许管理员选择订单。退回弹窗在“产品编码”前增加只读“订单编号”列，每一行对应原始 `shipment_line`；其他已确认字段、居中弹窗和底部按钮不变。

### 6.4 作废申请与已退回数量的互斥规则

**确认决定：** 工厂“撤回发货”入口保持开放且不设置时间限制。即使发货单已经发生部分退回，工厂仍可提交撤回申请；提交只进入 `VOID_PENDING`，不改变数量。存在 `VOID_PENDING` 时禁止新增退回；如果已经存在任意有效退回，管理员不得审核通过，只能拒绝。审核拒绝后恢复 `SHIPPED`，可以继续按剩余可退数量退回，也可以再次申请；只有从未发生退回的发货单才允许审核通过整单作废。审核通过后永久不再申请或退回。

本节四项决定已由用户确认，作为 S08 实现和验收规则。

## 7. 数据库与领域模型

迁移和集成测试使用真实 MySQL 8、InnoDB、`utf8mb4` 和微秒时间戳。数据库时间戳保存 UTC，发货/退回业务日期使用 Asia/Shanghai。

### 7.1 新增或扩展模型

- `shipments.status`：扩展为 `DRAFT`、`SHIPPED`、`VOID_PENDING`、`VOIDED`；
- `shipment_void_requests`：内部 UUID、发货单、申请人、原因、`PENDING/APPROVED/REJECTED`、审核人、审核时间、审核意见、幂等键和时间戳；
- `shipment_return_events`：内部 UUID、原发货单、管理员、Asia/Shanghai 退回日期、共用原因、幂等键和时间戳；
- `shipment_return_lines`：退回事件、原 `shipment_line`、正整数退回数量、派工统一已发数量变更前后值；
- `quantity_ledger`：复用现表，新增稳定 `source_type`：作废通过和按发货单退回均写负数，来源事件唯一且只追加；普通补发继续使用 S07 正向来源类型；
- `order_lifecycle_events`、`audit_logs`、`outbox_messages`：复用现有模型记录完成状态恢复、审计和通知事件；
- 发货清单导出默认按请求重新生成，不新增可变业务快照表；若实现需保存私有生成文件，只保存不可变来源摘要、模板摘要、导出人、时间和文件引用，不作为数量事实。

### 7.2 关键约束

- 同一发货单最多一个 `PENDING` 作废申请，通过数据库可执行唯一约束或等价锁内约束保证；
- 一个作废申请只能从 `PENDING` 转为 `APPROVED` 或 `REJECTED` 一次；
- 已有有效退回不阻止创建作废申请，但必须阻止该申请转为 `APPROVED`；`VOID_PENDING` 必须阻止新增退回；
- 同一退回事件和同一原发货行最多一条退回明细；退回数量大于 0；
- 作废/退回的“来源类型＋来源事件＋订单派工”在数量台账中唯一；
- 原 `shipment_lines.quantity`、逐箱事实和原正向台账不可被逆向操作更新或删除；
- 数据库约束、服务锁和 API 幂等三层共同防止重复负向数量。

## 8. API 与权限边界

建议沿用 `/api/v1` 和现有发货单资源：

| 终端 | 接口 | 作用 |
|---|---|---|
| 工厂小程序 | `POST /factory/shipments/{shipmentId}/void-requests` | 提交本厂撤回申请 |
| 工厂小程序 | `GET /factory/shipments/{shipmentId}` | 读取本厂状态、申请结果和操作记录 |
| 管理员网页端 | `POST /admin/shipment-void-requests/{requestId}/approve` | 审核通过 |
| 管理员网页端 | `POST /admin/shipment-void-requests/{requestId}/reject` | 审核拒绝 |
| 管理员网页端 | `POST /admin/shipments/{shipmentId}/returns` | 创建按发货单退回事件 |
| 管理员网页端 | `GET /admin/shipments/{shipmentId}/export` | 下载发货清单 |
| 管理员双端 | `GET /admin/shipments/{shipmentId}` | 按终端裁剪详情、状态和日志 |

- 所有 POST 使用 `Idempotency-Key`；网页写操作继续校验 CSRF；
- 服务端根据角色、终端、工厂归属、发货单状态和最新数量校验，不依赖前端按钮隐藏；
- 工厂不能调用审核、退回或导出接口；管理员小程序不能调用网页写接口；
- 生成 OpenAPI 后同步管理员网页和小程序类型，并运行双端类型漂移检查。
