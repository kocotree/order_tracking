## 1. 工单目标

本工单交付“质检单返修分批发回”的独立闭环：

1. 工厂从本厂未完成返修任务进入“发回返修品”，按产品规格选择本次发回项并填写返修数量、报废数量；
2. 页面先本地预览本次明细，确认提交后由后端一次事务创建不可变发回批次和明细；
3. 提交立即累计返修数量、报废数量和返回总数量，不设置管理员收回确认；
4. 返回总数量等于仓库退回总数量时，返修单自动变为“已完成”；
5. 管理员网页端、管理员小程序和所属工厂小程序读取同一份规格进度和历史发回记录；
6. 管理员网页端只能归档已完成返修单，归档后二次确认并从三端业务查询中隐藏，数据和审计记录继续保留。

S10 不改变正常订单、派工、普通发货单或正常发货数量台账。

## 2. 业务范围与规则

### 2.1 产品规格与数量口径

- S09 质检明细继续按 Excel 原始行保存；S10 的可发回项按同一返修单内相同 `variant_id` 汇总为一个产品规格；
- 一个规格的仓库退回数量等于该返修单内该 `variant_id` 全部质检明细的仓库退回数量之和；
- 一个规格的已返回数量等于全部有效发回批次中该 `variant_id` 的返修数量与报废数量之和；
- 一个规格的待返回数量等于仓库退回数量减已返回数量，不得小于 `0`；
- 返修单汇总满足：`返回总数量 = 返修数量 + 报废数量`，且不得超过仓库退回总数量；
- 同一提交中同一 `variant_id` 只能出现一次，不接收前端提交的产品名称、规格名称、仓库退回数量或已返回数量作为可信业务事实。

### 2.2 填写与本地预览

- 只有未完成、未归档且属于当前工厂的返修单显示“发回返修品”；
- 填写页只列出待返回数量大于 `0` 的规格，按产品名称分组；
- 工厂先勾选本次发回规格，再分别填写返修数量和报废数量；未勾选项不提交；
- 两个数量都必须是 JSON 整数和非负整数，不接受小数、负数、布尔值或数字字符串；
- 每个已选规格的返修数量与报废数量不能同时为 `0`，两者之和不得超过该规格当前待返回数量；
- 一次提交至少包含一个有效规格；
- “填写数量→预览提交”只保存在当前小程序页面内，不建立服务端草稿、不占用数量；返回修改保留当前填写，退出页面后不保证恢复；
- 页面校验只用于及时提示，后端在确认提交时按最新数据库进度重新校验。

### 2.3 确认提交、并发与幂等

- 确认提交必须携带 `Idempotency-Key`；同一用户使用同一幂等键和相同请求重复提交时返回首次成功结果，不创建第二个批次；
- 同一幂等键对应不同请求内容时返回 `409`，不得把新内容解释为首次结果；
- 事务先锁定返修单，再锁定或汇总该返修单的规格进度，串行校验并发发回；
- 两个设备同时发回同一规格时，最多只有不超过待返回数量的请求成功；后到请求按最新进度返回 `409`“返修进度已变化，请重新核对”；
- 事务内一次性写入发回批次、发回明细、返修单汇总、状态、操作日志和必要的可去重业务事件；任一步失败整体回滚；
- 发回批次和明细成功后不可编辑、删除或作废；一期不提供冲正、复检、再次返修、赔偿或扣款；
- 发货时间取后端接收并成功提交的系统时间，数据库保存 UTC；三端按 Asia/Shanghai 只显示年月日；
- 最后一个待返回数量提交成功后，返修单在同一事务中自动变为 `COMPLETED`；已完成返修单拒绝继续提交。

### 2.4 归档

- 只有管理员网页端可以归档，管理员小程序和工厂小程序均为只读；
- 只有 `COMPLETED` 且尚未归档的返修单显示“归档”；
- 点击“归档”后显示已批准原型的二次确认弹窗，确认后写入 `archived_at`、`archived_by` 和操作日志；
- 归档写接口携带 `Idempotency-Key`；同一请求重复到达不重复写日志；不同请求再次归档返回明确冲突；
- 归档不是返修状态，不新增“已归档”状态、列表、筛选、页签、恢复或取消归档入口；
- 归档后管理员网页端、管理员小程序和所属工厂小程序的列表、详情及质检附件下载业务入口均不再返回该返修单；
- 归档不删除返修单、质检明细、原始 Excel、发回批次、发回明细、归档人、归档时间或操作日志；后续统一审计能力仍可读取留存证据。

## 6. 待确认的正式决策

### 6.1 S09 同规格多行的汇总键

同一返修单内以 `variant_id` 作为规格汇总键。S09 原始质检行继续逐行保留，S10 不让工厂选择具体箱号或原始行；一次发回只针对汇总后的产品规格。产品编码、名称和颜色/规格从该返修单不可变的质检明细快照读取，不信任前端回传文案。

### 6.2 预览不建立服务端草稿

“预览提交”是小程序当前页面内的核对步骤，不创建数据库记录、不锁定数量。只有“确认提交”调用写接口。这样避免引入过期草稿、占量释放和清理任务；最终数量仍由后端事务校验。

### 6.3 批次不可变

发回批次提交即成为业务事实，一期不提供编辑、删除、撤回或冲正。发现录入错误不能手工改库或删除审计事实，需要另行定义有权限、有理由、有反向记录的纠错流程，不能静默扩入 S10。

### 6.4 归档后的附件访问

归档表示三端业务入口整体隐藏，因此通过已知返修单 ID 或文件 ID 访问详情和原始质检附件也返回 `404`。文件和关系仍保存在私有存储与数据库，后续仅能由正式审计能力按权限读取。

## 7. 数据库与领域模型

迁移与集成测试使用真实 MySQL 8、InnoDB、`utf8mb4` 和微秒时间戳。

- `repair_return_batches`：`batch_id`、`repair_id`、提交人、提交时间、幂等键、请求摘要和时间戳；同一提交人＋幂等键唯一；
- `repair_return_lines`：`return_line_id`、`batch_id`、`variant_id`、返修数量、报废数量；同一批次＋规格唯一；返修与报废均非负且两者之和大于 `0`；
- `repair_orders`：沿用 S09 的汇总、状态和归档字段；补强数据库约束，确保返回总数量等于返修与报废之和，且不超过仓库退回总数量；
- 规格仓库退回数量继续从不可变 `repair_inspection_lines` 按 `repair_id + variant_id` 汇总；不建立可被前端覆盖的第二份计划数量；
- 发回批次和明细只追加；归档只更新返修单归档字段，不级联删除；
- 迁移从 `20260826_0020` 单头继续，升级前后不得产生第二个 Alembic head。

## 8. API 与权限边界

| 终端 | 接口 | 作用 |
|---|---|---|
| 工厂小程序 | `POST /api/v1/factory/repairs/{repairId}/return-batches` | 幂等提交本厂返修发回批次 |
| 管理员网页 | `POST /api/v1/admin/repairs/{repairId}/archive` | 二次确认后幂等归档已完成返修单 |
| 管理员双端 | `GET /api/v1/admin/repairs`、`/{repairId}` | 查询未归档返修单、规格进度和发回历史 |
| 工厂小程序 | `GET /api/v1/factory/repairs`、`/{repairId}` | 只查询本厂未归档返修任务、规格进度和发回历史 |
| 授权终端 | `GET /api/v1/files/{fileId}/download` | 未归档返修单附件逐次授权下载 |

- 提交发回只允许 `mini + factory + 本厂 + 启用用户`；管理员双端、其他工厂和网页会话均拒绝；
- 归档只允许 `web + admin + CSRF`；管理员小程序、工厂用户和网页外会话均拒绝；
- 写接口都要求 `Idempotency-Key`，请求字段由 Pydantic strict 类型约束；
- 错误语义：`401` 未登录，`403` 错误终端/角色，`404` 非本厂、已归档或不存在，`409` 状态、并发进度或幂等冲突，`422` 请求数量校验失败；
- `RepairResponse` 增加按规格汇总的 `specs` 和按提交顺序返回的 `returnBatches`；原始 `lines` 保留给管理员网页质检明细；
- 生成 OpenAPI 后同步管理员网页和小程序 TypeScript 类型并检查漂移。
