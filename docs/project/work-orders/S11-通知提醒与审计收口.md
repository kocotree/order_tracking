## 1. 工单目标

本工单把 S04、S07、S08、S09、S10 已记录的业务事件收口为可追踪通知闭环：

1. 已完成业务切片产生的订单、发货、作废、退回和返修事件，可以稳定生成站内通知；
2. 站内通知不受微信授权影响，管理员网页和两类小程序均可查看本人未读数量和通知记录；
3. 管理员和工厂小程序均不提供通知设置或类别开关，管理员三类、工厂四类系统通知默认全部开启；
4. worker 消费既有发件箱事件，按接收人和通知类别去重；跟单人员和特别关注管理员的合同出货提醒外部只走飞书，工厂合同出货提醒及其他已配置微信提醒仅在平台当次订阅有效时建立待发送消息；
5. 合同出货时间前 10 天、5 天、3 天和当天通知订单对应跟单人员及订单所涉工厂全部已启用用户，另在前 3 天通知特别关注管理员“煎饼”和“核桃”；到期后不再重复提醒；站内记录保留，管理员外部通过飞书发送，工厂外部通过微信订阅消息发送；
6. 飞书或微信发送失败不回滚业务事务，worker 可以租约领取、退避重试、重启续跑，重试耗尽后留下人工处理状态并触发独立运维告警；
7. 管理员可以通过统一只读接口查询关键操作日志，工厂只能看到其已有业务页面内、本厂可见对象的操作记录；
8. 日志、通知和告警不保存或返回密钥、授权码、完整外部错误响应和其他敏感信息。

S11 不改变订单、正常发货、按发货单退回或质检单返修的数量与状态口径。

## 2. 业务通知矩阵

### 2.1 通知类别

管理员通知使用三类固定类别，不在管理员小程序提供设置或开关：

- `DUE_REMINDER`：合同出货提醒；
- `SHIPMENT`：正常发货通知；
- `REPAIR`：质检单返修通知。

工厂通知使用四类固定类别，不在工厂小程序提供设置或开关：

- `NEW_ORDER`：新订单任务；
- `DUE_REMINDER`：合同出货提醒；
- `REPAIR`：新返修任务；
- `BUSINESS_RESULT`：业务处理结果。

类别用于接收人规则和外部渠道模板映射，不替代更细的业务 `event_type`。站内通知始终生成；跟单人员和特别关注管理员的合同出货提醒外部固定使用飞书，工厂合同出货提醒及其他微信外部投递取决于平台当次订阅授权和发送资格。

### 2.2 事件、接收人与跳转

| 业务事件 | 站内接收人 | 外部提醒 | 目标页面 |
|---|---|---|---|
| 正式订单发布 | 订单所涉工厂全部已启用用户 | 工厂 `NEW_ORDER` | 对应本厂任务详情 |
| 已发布订单撤回草稿 | 订单所涉工厂全部已启用用户 | 工厂 `BUSINESS_RESULT` | 本厂任务列表；原详情不可见时安全回退 |
| 合同出货提醒 | `D-10`、`D-5`、`D-3`、`D0` 通知订单对应跟单人员和订单所涉工厂全部已启用用户；`D-3` 另通知特别关注管理员“煎饼”和“核桃” | 跟单人员及特别关注管理员使用飞书 `DUE_REMINDER`；工厂用户使用微信 `DUE_REMINDER` | 对应订单详情/本厂任务详情 |
| 工厂提交正式发货单 | 订阅管理员 | 管理员 `SHIPMENT` | 对应发货单详情 |
| 工厂提交撤回申请 | 全部已启用管理员仅生成站内待办通知 | 不外发 | 对应发货单详情 |
| 管理员通过或拒绝撤回申请 | 原申请人 | 工厂 `BUSINESS_RESULT` | 对应发货单详情 |
| 管理员按发货单确认退回 | 对应工厂全部已启用用户 | 工厂 `BUSINESS_RESULT` | 原订单任务详情 |
| 管理员确认创建质检单返修 | 所属工厂全部已启用用户 | 工厂 `REPAIR` | 对应返修任务详情 |
| 工厂提交返修发回记录 | 订阅管理员 | 管理员 `REPAIR` | 管理员小程序“发货—返修进度”详情；网页返修详情 |

- 同一业务事件对同一用户只生成一条站内通知；不同接收人分别留存；
- 用户后来停用、换厂或失去角色后，不再生成新通知；历史通知仍保留，但目标对象继续按当前权限校验；
- 点击无权访问、已删除或已归档对象的旧通知时，不泄露对象存在性，提示“内容已不可查看”并停留在安全页面；
- `repair.completed` 不额外产生第二条通知；最后一批发回通知的文案可以包含“返修已完成”，避免同一操作重复提醒。

## 3. 提醒日期与完成条件

- 所有业务日期按 `Asia/Shanghai` 计算，数据库时间继续保存 UTC；
- 提醒节点固定为合同出货时间 `D-10`、`D-5`、`D-3` 和 `D0`；到期后不生成 `D+1` 或其他重复逾期提醒；
- `D-10`、`D-5`、`D-3` 和 `D0` 通知订单对应跟单人员，并通知订单每个派工所涉工厂的全部已启用用户；同一工厂在同一订单存在多个派工或规格时，同一用户同一节点只生成一条通知；
- 特别关注管理员“煎饼”和“核桃”接收全部未完成订单的 `D-3` 提醒，不接收 `D-10`、`D-5`、`D0` 或到期后的重复提醒；
- 主订单已完成时不再生成提醒；撤销完成后只生成撤销时点之后尚未执行的节点，不补发已经过去的历史节点；
- 每个“用户＋订单＋提醒节点”使用稳定去重键。worker 重启、重复扫描和并发扫描不得重复生成站内通知、飞书消息或微信消息；
- 每日扫描任务由 worker 按配置的本地时间登记为持久化后台任务，默认建议 `09:00`；不是 FastAPI 进程内临时定时器；
- 生产配置修改执行时间只影响未来扫描，不改写既有通知和审计事实。

需求第 8.3 节明确订单发布只通知相关工厂用户。用户于 2026-08-27 确认管理员不接收该事件的站内通知或微信提醒；管理员小程序原型和正式页面删除“新订单通知”，不保留无效设置。

例：管理员发布订单 `090#` 后，相关工厂用户收到通知，发布人和其他管理员都不因“订单发布”收到通知。

### 6.3 微信订阅授权不是永久业务承诺

小程序只根据微信原生接口当次返回结果记录授权状态；“本次已授权”表示取得对应一次性模板的当次发送机会，不表示平台保证永久可发送。已启用管理员和工厂账号的登录按钮都是订阅请求触发点，但微信登录本身不会自动授予订阅消息权限，最终仍以微信原生面板中用户选择为准；拒绝或关闭不影响登录和业务使用。系统不制作自建授权弹窗，两类小程序的“我的—微信提醒授权”继续作为后续再次请求入口。真实发送次数、会员订阅资格、模板类目和拒绝后的再次授权方式，以公司小程序后台实际可用模板和微信官方规则为准。

未提供模板 ID 或真实授权方式时，开发和自动化只使用显式假适配器，并标记为本地验证；不得把假发送称为真实微信送达。

微信原生 `wx.requestSubscribeMessage` 单次最多接受 3 个模板 ID。工厂四类业务通知与微信模板采用可配置的多对一映射，不把业务类别数量直接当成模板 ID 数量；真实映射必须校验模板字段能够表达对应事件。若后台可用模板无法在 3 个以内覆盖四类业务提醒，真实联调前重新确认，不连续弹出两个原生面板，也不静默遗漏通知类别。

例：用户今天同意某个订阅模板，不代表系统以后可以无限次发送；即使页面显示已开启，微信仍可能因授权次数、模板或平台规则拒绝下一次发送。

稳定性处理分为两层：站内通知始终生成并作为可靠业务记录；微信通知只作为外部提醒加速器，通过稳定去重、持久化发件箱、可重试错误退避和发送结果留痕提高成功率，但不承诺平台外部消息必达。

### 6.4 站内通知与外部提醒分层

既有 `outbox_messages` 继续保存业务事务内写入的事件。通知模块通过一个小接口消费事件，完成接收人解析、站内通知和外部投递扇出；业务模块不直接调用飞书或微信。

外部投递作为同一发件箱中的用户级子消息处理，使用“业务事件＋接收人＋渠道”稳定去重键。合同出货提醒按接收角色分流：跟单人员和特别关注管理员使用飞书业务通道，工厂用户使用微信；其他已配置提醒按矩阵选择微信。这样业务事务、站内通知和外部渠道故障相互隔离，同时不引入第二套消息中间件。

例：工厂提交发货单后，发货数量和站内通知立即成功保存；此时微信接口超时，只重试微信消息，不撤销发货单，也不重复增加已发数量。

### 6.5 统一审计查询不新增可见管理页

S11 增加管理员网页会话可用的统一只读审计接口和必要索引，但不新增左侧导航或独立“审计日志”页面。既有订单、发货单和返修详情继续展示上下文操作记录；后续若需要全局审计页面，必须另行补原型和页面确认。

例：管理员可以通过统一接口查询“谁在什么时候作废了哪张发货单”，但网页端仍只在对应订单或发货单详情展示这条记录，不新增“审计日志”菜单。

### 6.6 运维告警渠道独立

外部消息发送重试耗尽后，先在数据库记录脱敏失败代码和人工处理状态，再调用独立 `OpsAlertNotifier` 接口。当前唯一开发与运维接收人为“煎饼”，生产适配器通过飞书私聊向煎饼发送告警，不要求建立运维群；机器人/应用配置仍使用最小权限并由用户提供。

未配置真实渠道时使用禁用适配器稳定记录“告警渠道未配置”，不能回退到业务微信通知，也不能静默宣称告警已送达。

例：一条微信业务通知连续重试耗尽后，系统把脱敏错误通过飞书私聊发送给煎饼；不能继续使用同一条已经故障的微信发送链路告警。若飞书自身故障导致告警也无法送达，数据库人工处理状态和服务器日志必须保留，不能宣称告警已送达。

需要运维告警的异常包括：服务端微信凭据失效、access token 持续刷新失败、模板被停用或字段不匹配、连续网络超时、持续限流或微信服务端错误、worker 停止或发件箱持续积压。用户主动拒绝授权、未订阅、授权次数已用完、账号已停用或目标业务对象已不可见属于预期业务结果，只记录发送结果，不触发运维告警。

## 7. 模块、接口与外部适配器

S11 使用一个深的“通知与审计”模块，调用方只需要提交既有业务事件或查询公开结果，不需要了解接收人解析、模板映射、去重、重试和脱敏细节。

模块公开接口拟保持为：

- 消费一个已领取的业务事件并产生站内通知及必要的用户级外部投递；
- 扫描一个明确的上海业务日期并登记应产生的提醒节点；
- 领取并投递一条到期外部消息；
- 读取/标记当前用户站内通知；
- 记录当前小程序用户的微信原生订阅授权结果；
- 管理员按条件读取统一审计记录。

真实外部系统只在三个接缝注入适配器：

- `FeishuBusinessNotifier`：跟单人员和特别关注管理员合同出货提醒的飞书业务消息适配器与自动化假适配器；
- `WechatNotifier`：生产微信订阅消息适配器与自动化假适配器；
- `OpsAlertNotifier`：生产运维告警适配器与自动化假/禁用适配器。

不为 MySQL 再造仓储抽象；领域和接口测试继续使用真实隔离 MySQL 8。

## 8. 数据库与迁移

迁移从 `20260827_0021` 单头继续，使用真实 MySQL 8、InnoDB、`utf8mb4` 和微秒时间戳。

- `notification_authorizations`：逐次记录用户、微信模板键、当次原生授权结果、授权时间和消耗状态；每次授权单独留痕，不以用户＋模板键覆盖历史，也不保存业务通知开关；
- `notifications`：接收人、类别、业务事件、目标类型和 ID、标题、内容摘要、目标路径、已读时间、去重键和创建时间；接收人＋去重键唯一；
- `outbox_messages`：沿用既有表，补充租约、最后错误代码、失败时间和完成/人工处理所需字段；错误内容只保存脱敏摘要；
- `audit_logs`：保留既有事实，补充按目标、操作人、来源终端和时间查询所需索引；不批量重写历史动作名称；
- 不把微信模板 ID、AppSecret、access token、告警 webhook 或完整外部响应写入以上业务表；
- 升级前后保持一个 Alembic head；降级不删除 S11 以前的事件和审计表。

## 9. HTTP 接口与权限

| 终端 | 接口 | 作用 |
|---|---|---|
| 管理员网页 | `GET /api/v1/admin/notifications` | 分页读取当前管理员通知记录 |
| 管理员网页 | `GET /api/v1/admin/notifications/unread-count` | 读取顶部未读数量 |
| 管理员网页 | `POST /api/v1/admin/notifications/{notificationId}/read` | 标记本人一条通知已读 |
| 管理员网页 | `GET /api/v1/admin/audit-logs` | 统一只读查询审计记录 |
| 管理员/工厂小程序 | `GET /api/v1/mini/notifications` | 分页读取当前用户通知中心记录 |
| 管理员/工厂小程序 | `GET /api/v1/mini/notifications/unread-count` | 读取“我的—通知中心”入口未读数量 |
| 管理员/工厂小程序 | `POST /api/v1/mini/notifications/{notificationId}/read` | 进入目标详情后标记本人通知已读 |
| 管理员/工厂小程序 | `POST /api/v1/mini/notification-authorizations` | 记录微信原生订阅授权的当次结果 |

- 网页通知和审计接口只允许 `web + admin + CSRF（写接口）`；
- 两类小程序通知和授权结果接口只允许 `mini + 已启用用户`；
- 所有通知 ID 都必须同时校验接收人，不能通过已知 ID 读取他人通知；
- 工厂用户无统一审计接口，既有业务详情日志继续按本厂对象权限裁剪；
- 目标跳转参数只允许服务端定义的页面类型和内部 ID，不接受任意 URL；
- API 错误不返回微信原始错误体、模板 ID、access token、告警地址或堆栈；
- OpenAPI 生成后同步管理员网页和小程序 TypeScript 类型并检查漂移。
