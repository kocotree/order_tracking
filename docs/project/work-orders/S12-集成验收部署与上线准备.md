## 1. 工单目标

S12 不新增一期业务功能，而是把 S01 至 S11 已实现的跟单管理系统收口为可验收、可回滚、可试运行的完整系统：

1. 补齐共享测试和生产所需的真实外部适配器与受控配置；
2. 建立 ECS 共享测试与生产的隔离 Compose、Traefik HTTPS、迁移、日志、健康检查和回滚入口；
3. 先在共享测试环境使用多角色、真实但非生产业务样例走通一期全流程；
4. 完成 MySQL 与私有附件的备份恢复、应用回滚、监控告警和安全验收；
5. 形成 2 至 3 家工厂试运行及正式切换检查表，但不因 S12 完成而自动上线生产。

### 2.2 当前缺口

- 根目录 compose.yaml 仅用于本地 MySQL 开发/测试，尚无 ECS 共享测试和生产 Compose；
- 尚无 Traefik 路由、发布迁移、健康验证、日志轮转、备份、恢复和回滚脚本；
- worker 中聚水潭产品源和产品图片存储仍为禁用适配器；
- 管理员小程序头像在非 local_demo 环境仍为禁用存储；
- worker 中飞书业务通知和飞书运维告警仍为禁用适配器；
- 真实飞书人员映射、聚水潭 OpenAPI 字段/分页/限频/增量语义、真机微信授权与送达、OSS Bucket/RAM 权限尚无共享测试环境证据；
- 本地 OSS 独立集成测试因未配置 `S12_OSS_*` 隔离测试资源而跳过；它不影响本地假客户端测试，但共享测试验收前必须补齐。

### 2.3 公司部署说明在本项目的适用结论

1. 共享测试环境首轮采用公司教程的 Git 部署方式，不把 CI/CD 自动部署作为上服务器的前置条件；
2. 首次由服务器使用公司 GitHub 仓库的只读凭据将项目克隆到经负责人确认的独立目录；服务器 SSH 登录公钥和 GitHub 仓库拉取凭据是两套不同权限；
3. 后续更新由本地推送公司 GitHub，远程 CI 通过并经确认后，再登录服务器执行 `git status`、`git pull --ff-only`、`docker compose up -d --build`、状态/日志/健康检查；普通 GitHub push 本身不自动改动服务器；
4. 服务器真实 `.env` 只保存在服务器并限制为当前部署账户可读；`git pull` 不得覆盖真实 `.env`，新增变量通过 `.env.example` 提示后再在服务器单独补齐；
5. 共享测试每次部署记录确切 Git commit；生产切换时不盲目跟随 `main` 最新提交，而是部署事前批准的不可变 Git tag/commit，并保留上一个已验证版本作为回滚点；
6. 域名可以先登记并确认 DNS，但服务器先用内部健康检查验证容器；认证方式、Traefik 路由和 HTTPS 准备好后才开放域名入口，真机小程序与飞书 OAuth 联调前必须完成该入口验收。

## 3. 包含范围与执行阶段

### 3.1 A 阶段：只读环境盘点

1. 只读核对 ECS 系统版本、资源、Docker/Compose、Traefik、网络、端口、时区和现有服务；
2. 只读核对 MySQL 8 版本、容量、备份方式和项目独立数据库/账号条件；
3. 只读核对阿里云 OSS 地域、内网 Endpoint、测试/生产 Bucket、RAM 权限和独立备份目标；
4. 确认共享测试与生产各自的同源网页/API 域名、DNS 修改人、小程序请求域名和 HTTPS 条件；
5. 确认飞书、聚水潭、微信、OSS 测试账号及允许的真实消息接收人范围；
6. 盘点完成前不安装软件、不改端口/DNS、不创建数据库/桶、不重启服务。

验收结果：形成脱敏环境盘点、端口与域名路由、变量清单、外部缺口和后续写操作确认清单。

### 3.2 B 阶段：部署与真实适配器补齐

1. 新增根目录 deploy/，只保存 Compose、非敏感环境示例、发布/回滚/备份/恢复脚本和说明；真实环境文件必须被 Git 忽略；
2. 建立共享测试与生产两套 Compose 项目，至少包含 admin-web、api、worker 和一次性 migrate；
3. API 与 worker 共用同一个 server 镜像但使用不同启动命令；
4. 两套环境使用不同 Compose 项目名、网络、数据库、最小权限账号、私有桶、环境文件和域名；测试容器不持有生产凭据；
5. Traefik 继续独占宿主机 80/443；MySQL 管理端和容器内部端口不暴露公网；OSS 使用同地域 HTTPS 内网 Endpoint；
6. 共享测试环境按已通过远程 CI 的确切 Git commit 在 ECS 本地构建；普通 main push 不自动部署，服务器更新仍使用独立确认门；
7. 按公司 Git 部署链路补齐首次克隆、Compose 校验/构建/启动、后续更新、迁移、健康检查和回滚脚本；本轮不新增 GitHub Actions SSH 自动部署；
8. shared_test 和 production 使用独立部署目录、Compose 项目名和服务器环境文件；每次服务器更新前记录当前与目标 commit，生产只部署事前批准的 tag/commit；
9. shared_test 和 production 不得以随机临时密钥、必需的禁用适配器或演示数据启动；
10. 补齐并接线聚水潭产品源、产品图片存储、管理员头像存储、飞书业务通知和飞书运维告警真实适配器；
11. 沿用现有飞书 OAuth/订单来源和微信身份/订阅消息适配器；私有文件改为 OSS 原生 SDK，并补齐生产级配置检查和必要错误分类；
12. 容器日志配置轮转；健康检查使用 /health/live 和 /health/ready；凭据、授权码、Cookie、手机号和完整外部错误响应不进入日志。

验收结果：配置、适配器和部署文件按失败测试先行完成；完整 CI、Compose 静态解析、镜像构建、非敏感配置检查和本地演练通过。本阶段不操作 ECS、DNS 或真实外部发送。

### 3.3 C 阶段：共享测试环境发布

1. 操作前再次确认确切 ECS、独立项目目录、测试域名、数据库、桶和已通过远程 CI 的目标 Git commit；
2. 使用受控 ECS 环境文件配置 ORDER_TRACKING_APP_ENV=shared_test，小程序状态使用 trial，微信真实发送总开关保持 false；
3. 经用户确认后登录 ECS，首次使用只读仓库权限克隆，后续使用 `git status` 和 `git pull --ff-only`，然后执行发布前检查、备份、`alembic upgrade head`、Compose `up -d --build`、健康检查、HTTPS 和网页/API 冒烟验收；
4. 验证服务与 worker 重启、日志轮转、磁盘及容器异常重启可观测性；
5. 发布失败时停止切换并按已验证的上一个镜像版本回滚，不默认执行 Alembic downgrade。

验收结果：测试域名 HTTPS 可访问，API 存活/就绪检查通过，网页与 API 同源，数据库和桶不公开，重启不丢数据，且未发送真实业务消息。

### 3.4 D 阶段：真实外部联调与真机

1. 飞书 OAuth：管理员网页登录、已验证手机号、内部身份映射和持久会话；
2. 飞书订单源：只读获取指定多维表格/视图，核对字段、分页、幂等和不回写；
3. 聚水潭：先以受控只读账号核对六分类、启用状态、分页、限频和增量时间语义，再允许 worker 首次同步；
4. OSS：使用共享测试私有 Bucket 和最小权限 RAM 凭证验证头像、产品图片、合同和质检附件的上传/下载/删除/跨工厂拒绝；
5. 微信真机：用户本人分别以管理员和工厂身份完成允许、拒绝和再次授权；
6. 每类飞书业务提醒、微信提醒和运维告警第一次发送前，再次征求用户确认，只向批准的测试接收人发送；
7. 外部发送覆盖一次成功、一次平台拒绝或授权不可用和一次受控重试，不通过打扰未授权人员制造失败。

验收结果：各外部系统分别记录“配置完成、契约通过、真实送达、尚未验证”，不使用单一“联调成功”掩盖证据差异。

### 3.5 E 阶段：一期全流程与安全验收

1. 按 V1.56 第 11 节建立每条验收标准到自动化、共享测试、真机、Excel/WPS 或用户确认的证据映射；
2. 使用最高管理员、普通管理员、工厂老板、工厂员工和不同工厂账号验证身份、停用、跨端和隔离；
3. 使用真实但非生产业务样例走通飞书获取、候选、导入、草稿、派工、发布、合同、正常发货、撤回/退回、返修、完成、通知和审计；
4. 用越权请求验证角色、工厂、文件、通知和审计隔离；
5. 用 Excel 与 WPS 分别核对发货清单和加工合同的 Sheet、公式、图片、文件名和历史快照；
6. 演练服务/worker 重启、重复请求、并发冲突、外部失败和重试耗尽；
7. 确认测试容器、账号和桶不能访问生产数据。

验收结果：V1.56 验收矩阵全部有证据；未通过项完成修复复验，或由用户明确接受为有边界的遗留问题。

### 3.6 F 阶段：备份恢复、监控与应用回滚

1. MySQL 每日全量备份和用于时间点恢复的增量日志复制到独立存储；
2. OSS 项目 Bucket 的增量备份、版本保护与独立恢复目标须与源 Bucket 隔离，并执行实际恢复演练；
3. 备份包含时间、环境和校验值，不进入 Git 或公开目录；
4. 在独立恢复库和恢复桶实际执行一次 MySQL 与附件恢复，并抽查身份、订单、数量、合同和质检附件；
5. 告警覆盖 API/worker、连续 5xx、任务积压/重试耗尽、外部接口、MySQL/OSS、备份、磁盘/内存/重启和 HTTPS；
6. 使用上一个已验证镜像版本演练应用回滚；仅在已证明可逆时才执行数据库 downgrade。

验收结果：备份能实际恢复，告警只向批准的测试接收人送达，应用回滚后健康检查和关键读取正常。

### 3.7 G 阶段：试运行与正式切换准备

1. 生成生产检查表，覆盖域名、HTTPS、微信请求域名、账号、初始数据、备份、恢复、告警、回滚和切换日期；
2. 用户另行批准后选择 2 至 3 家配合度较高的工厂试运行；
3. 试运行只导入至少一个颜色/规格原始发货进度严格小于 50% 的完整订单，同一订单不在新旧系统同时维护；
4. 试运行稳定并复验后，由用户另行批准统一正式切换日期；
5. S12 完成、生产检查表通过或 GHCR 镜像发布均不等于生产上线批准。

验收结果：形成脱敏试运行结果、问题清单、正式切换和回滚检查表；是否正式切换由用户另行决定。
