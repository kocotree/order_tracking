## 生产发布

1. 确定 Issue/PR、目标 SHA、版本号、迁移影响和配套小程序／Plugin版本；完成该 SHA的完整 main push CI。
2. 检查环境配置、磁盘、备份目录、上一版本镜像及 schema兼容性，准备业务验收样例。
3. 用户明确授权创建并推送新 `v*` 标签。已发布标签保持不可变；普通main推送不触发生产发布。
4. Release核验同一SHA的main CI后发布 server、admin-web两个GHCR镜像；两镜像成功后自动调用生产部署，无需单独手动CD。
5. 服务器独立任务检查镜像revision、备份MySQL和OSS、执行Alembic、更新容器并等待健康及四角色worker；全部通过才记录版本。SSH断开后任务继续，Actions重连查询同一任务。
6. 检查外部HTTPS、本人登录、四角色worker、关键查询与业务样例，填写[发布记录](版本发布记录.md)和[验收记录](验收记录.md)。

GitHub配置名称：`PROD_SSH_HOST`、`PROD_SSH_PORT`、`PROD_SSH_USER`、`PROD_SSH_PRIVATE_KEY`、`PROD_SSH_KNOWN_HOSTS`、`PROD_DEPLOY_DIR`。Release使用内置`GITHUB_TOKEN`；服务器不需要个人Token。部署包保存在 `DEPLOY_DIR/releases/<commit>/<run-id>-<attempt>/`，各次上传独立，旧版本保留原目录布局；受控配置在 `DEPLOY_DIR/deploy/.env.production`。

服务器前提：Docker Compose支持`--wait`，Python3.8+、mysqldump、flock、ossutil2.x、支持flock的Linux本地部署目录、受控备份目录及已核验SSH主机密钥。固定镜像为 `ghcr.io/kocotree/order-tracking-server:<version>` 与 `ghcr.io/kocotree/order-tracking-admin-web:<version>`，API和worker使用相同server版本。禁止使用`latest`。

### 断连后的任务核验（Issue #235，待发布）

任务按不可变版本注册并绑定精确revision，状态在 `DEPLOY_DIR/runtime/deployments/<version>/` 持久保存。`state.json`记录原部署目录、起止时间和最终退出码，`stage`记录阶段，`events.log`记录带时间的阶段及结果。日志不保存外部命令原始输出，避免凭据回显。任务目录权限700，文件600；临时GHCR配置在拉取镜像后删除，正常失败也清除。

通过已核验SSH连接执行只读查询，参数中的registry-user为非秘密GitHub用户名：

```bash
python3 <release-dir>/deploy/scripts/deploy-task.py status <DEPLOY_DIR> <version> <40-character-commit> <registry-user>
cat <DEPLOY_DIR>/runtime/deployments/<version>/events.log
```

| 结果 | 含义与处理 |
|---|---|
| `running` | 任务或其部署子进程仍持有租约；继续等待，同版本重跑不重复执行 |
| `succeeded` | 该version/revision已完成全部步骤且退出码0；重跑返回原结果，当前运行版本和外部HTTPS仍按发布巡检核实 |
| `failed` | 保留失败阶段与退出码；先核实备份、schema、镜像及容器，再明确修复动作，禁止自动重放 |
| `unknown` | 状态残缺或损坏、进程被强制终止、主机重启等导致最终结果缺失；不得推断成功或强制重启任务 |
| `absent`／`identity-conflict` | 未找到任务目录／同一版本绑定了不同revision；检查精确版本、路径和记录 |

Actions每10秒查询，单次最多60秒，连续12次通信失败或总等待超过3小时报告“结果未确认”；远端任务继续。重新执行deploy job会识别原任务，不覆盖其运行脚本。取消Actions也不会停止服务器任务。原生产部署锁继续约束其他版本与定时备份；成功任务结果可跨Actions重跑核验。

失败和未知状态均保留原记录。不得删除目录绕过幂等保护，也不得直接重跑迁移或部分容器切换；恢复操作需明确授权。强制终止发生在登录、拉取或备份阶段时，受控任务目录可能保留临时凭据文件，确认进程结束后再按授权清理。未增加自动版本恢复、数据库降级、日志归档或业务数据清理。

共享测试沿用 Git＋Compose：[preflight](../../../deploy/scripts/preflight.sh)→独立备份→[release.sh](../../../deploy/scripts/release.sh)→健康和HTTPS。旧Git/build发布脚本用于共享测试；生产使用镜像CD。标签授权不包含真实通知、小程序上传或正式发布。

## 日常巡检

在目标release的`deploy/`目录，以受控环境文件执行只读检查：

```bash
docker compose --env-file .env.production -f compose.production.yaml ps
docker compose --env-file .env.production -f compose.production.yaml top worker
docker compose --env-file .env.production -f compose.production.yaml logs --since 30m api worker
```

核对外部 `/health/live` 和 `/health/ready`；执行[health-check.sh](../../../deploy/scripts/health-check.sh)时从对应release的`deploy/`目录传`production`。记录时间、版本、状态及脱敏错误，避免复制整段含私人数据的日志。

| 项目 | 健康判断与证据 |
|---|---|
| 容器 | api、worker、admin-web健康；实际镜像version和revision与发布记录一致 |
| worker | `sync`、`incoming`、`notification`、`shipment`全部存活并有各自`worker.started`；只看worker容器Up不足以确认子进程 |
| 自动订单 | 最新`order_import_runs`完成时间、失败项；`audit_logs`中的`source_terminal=system`及`order.detail_dispatched`；按订单＋工厂核查 |
| 图片 | SKU缓存状态与失败码，OSS对象可读取；合同／箱贴首次导出前检查所选颜色有可用代表图 |
| 来货出入 | 批次状态、图片OCR、当前核对表版本、待确认行、登记记录和对应流水；模型候选与正式记录分开 |
| 通知 | outbox状态、重试／最终失败、站内记录、平台送达证据；关注`deliveryId`及`manual_review_required` |
| 数据与容量 | MySQL连接、锁等待、磁盘、备份目录、OSS容量；记录阈值和告警负责人 |

四个worker默认各有独立连接池，每池5个常驻加10个溢出连接，默认最多共60个连接，容量规划再加API池；该值为配置上限，实际连接量需实测。任务日志使用`role`、`workerId`、`jobId`、`jobType`、`deliveryId`定位。普通任务在角色启动时恢复已过期5分钟的租约，订单自动同步使用专用锁恢复；角色过滤同时覆盖领取和恢复。子进程退出导致整组重启；优雅退出等待30秒，Compose停止窗口45秒。四角色已随 PR #232 合并，v1.1.10 Release及生产部署步骤通过；本轮未独立核验生产进程或容量。

## 常见故障处理

| 现象 | 检查顺序 | 处理边界 |
|---|---|---|
| 登录失败／无权限 | 环境、飞书手机号权限、用户启停、白名单、微信绑定、会话／共同授权 | 不直接修改内部身份绕过手机号或停用校验 |
| 来源订单缺失／不自动派工 | 最新同步批次→95%门槛→采购关联→产品／工厂／人员／日期→人工撤回暂停 | 来源错误先给逐条证据；修复、重跑或生产改写需明确范围 |
| 图片缺失／导出失败 | SKU来源、缓存revision与对象→所选分组→首次固定快照→requestId | 不用其他款／颜色图片代替；历史导出快照保留 |
| MCP无法连接／文件失败 |公开HTTPS、resource/client配置→本人OAuth→停用和PKCE→允许文件主机、DNS、20MiB、格式 | 不放宽为任意域名；记录客户端真实兼容限制 |
| 机器人只回卡片／无文件 |应用已发布权限→事件／卡片校验→资源下载→incoming角色任务→模型→outbox投递 | 回调、下载、识别、投递及正式登记各自核验 |
| 收货／差异数量不符 |原报箱项→收货确认→退回／撤回→初始基线→来货及调整流水→当前归属 | 禁止直接覆盖汇总或反复提交制造补偿 |
| worker任务停滞 |四子进程→角色任务领取／恢复→锁租约→外部超时→失败状态与错误码 | 手工重试先检查幂等和原动作结果；通知失败不重做业务提交 |
| 部署失败 |失败阶段→实际镜像、容器、schema、备份→外部健康 | DDL和部分更新无法假定自动恢复，检查状态后制定修复动作 |

## 备份、恢复与版本恢复

部署和每日00:00定时任务运行同一[backup-production.py](../../../deploy/scripts/backup-production.py)，共享部署锁。保留最新30份MySQL和3份OSS快照，仅清理脚本自己的`production-<stamp>`文件；实际cron安装、时区、成功时间、离机保存和容量须巡检。

MySQL备份包括摘要，OSS保存对象快照。数据库文件索引与对象须取一致备份批次；备份完成只能证明产物存在，恢复演练还需验证表、数量、附件和应用可用。

恢复演练先创建独立空库、独立Bucket和最小权限账号，将受控恢复配置放Git外。明确授权后，使用[restore-mysql.sh](../../../deploy/scripts/restore-mysql.sh)传备份文件与受控配置文件；使用[restore-oss.sh](../../../deploy/scripts/restore-oss.sh)传OSS备份目录与`-restore` Bucket。确认变量为`ORDER_TRACKING_RESTORE_CONFIRMED=restore-test-only`。验证摘要、schema、代表性数据、私有文件读取和隔离环境业务流程，记录恢复耗时及问题；不得对生产目标演练。

服务器应用恢复到旧版本前，确认旧代码兼容当前schema和新增数据，获得具体版本操作授权。使用保留的上一release与精确镜像版本、设置`ORDER_TRACKING_DEPLOY_VERSION`，按部署说明执行Compose`up -d --no-build --wait api worker admin-web`及production健康检查。禁止执行Git回滚或自动Alembic downgrade；`0049`已有未派工数量记录时会拒绝降级。若涉及数据恢复，另行批准目标、备份批次及数据损失范围。完成后核对HTTPS、登录、worker和业务并更新版本记录。

## 出货阶段汇总回填（Issue #227）

Issue #246 仅向空白阶段单元格写入，已有值含0全部保留并记跳过。日志 `verified` 为已写入且回读验证行数，`skipped` 为已有值跳过行数，`verified_quantity` 为已验证行的冻结数量合计；`quantity` 仍为全部冻结统计量。跳过行与验证成功行均不再次自动处理，后续清空已跳过单元格也不会自动补写。远端成功但本地确认中断后，重试读到已有值按跳过记录，不能据此推断人工或系统来源。

飞书记录更新接口未公开原子条件写入能力，写前复查无法消除最后一次读取至 PUT 之间的人工编辑窗口。本地任务锁只约束本系统进程；维护期间应避免同时编辑目标阶段单元格。上线前须明确此边界，不能宣称完全杜绝并发覆盖；本次未验证真实 Base 并发操作。

本节描述启用与运维方式，本轮未在生产执行。Issue #231 将到期扫描和 `shipment_writeback` 从 `sync` 迁入同容器的 `shipment` 进程；`sync` 保留订单与产品六类任务，其他角色职责不变。沿用迁移 `20261006_0051` 保存的提交事实、冻结阶段、根单归属、行结果与接管控制，#231 不新增迁移。API 在提交、撤回、重提的同一事务保存事实，即使回填开关关闭也保留后续接管证据。

启用必须完成对应版本发布授权和以下核验：

1. 保持 `ORDER_TRACKING_SHIPMENT_WRITEBACK_ENABLED=false`，完成迁移并确认全部 API 实例使用新版本，旧进程的提交事务已退出，再准备历史。不能在混用旧 API 的期间声明历史完整。
2. 使用既有 `ORDER_TRACKING_FEISHU_ORDER_*` 应用身份与来源范围。确认字段读/建/更新、记录读/更新权限以及文档编辑权限，目标仅为已批准下单表；核验字段容量。
3. 在 server 运行 `uv run python -m scripts.shipment_writeback inspect`，只读取得总数字段 ID 与原生公式。输出仅存受控配置，禁止复制进 Git 或共享日志。核对确为批准的历史 `ROUND(SUM(IFBLANK(...,0),...),0)` 公式，设置 `ORDER_TRACKING_SHIPMENT_WRITEBACK_TOTAL_FIELD_ID`、`ORDER_TRACKING_SHIPMENT_WRITEBACK_BASELINE_FORMULA`，保留表达式原样及正确环境文件引号。
4. 运行 `uv run python -m scripts.shipment_writeback history`，根据正式副本及 outbox 核验并登记10月6日起的存量事实；不写飞书、不改订单数量、不发通知。缺失历史或状态不一致时退出失败，解决证据问题后原命令重试，禁止伪造数量绕过。
5. 在授权环境验证建列、原生公式保存与回读、代表性来源行和总数；已有自动化测试使用模拟 HTTP，不能替代此项。维护公式期间避免人工并发修改，接口无远端原子比较更新保证。
6. 上述核验与生产启用均获授权后设开关为 `true` 并按发布流程重启 worker。每分钟检查到期工作，首轮补排10月以来未完成任务；月初建当月列，阶段末日北京时间22点触发。调度延迟不改变截止时间。

日志和恢复（server 工作目录）：

```bash
uv run python -m scripts.shipment_writeback logs
uv run python -m scripts.shipment_writeback schedule
uv run python -m scripts.shipment_writeback retry --job-id <失败任务ID>
```

`logs` 读取数据库执行日志，含执行 ID、任务 ID、尝试次序、截止点、开始结束、状态、行数、数量、排除原因和错误。`schedule` 幂等补排到期任务；`retry` 只重置本功能的失败任务，保留字段绑定、创建幂等令牌、冻结数量和成功行进度。两种操作均要求启用开关。worker 沿用最多3次尝试和30秒重试间隔；持续错误保留为失败，由运维处理后显式重试。

进程恢复沿用 worker 的 stale job 领取机制，`shipment` 按任务类型恢复旧 `sync` 中断的汇总任务，复用原任务 ID、幂等键和快照，无需迁移已排队任务。外部执行锁防止同时写同一目标。新尝试获得锁后将同任务未结束的日志标记为 `INTERRUPTED`。已冻结阶段不会因补录或撤回重算，后续阶段在前序未冻结时失败并等待处理。关联缺失或公式漂移禁止猜测覆盖；不得删除归属记录来“重新统计”。

关闭回填开关并重启 worker 后，`shipment` 保持存活但不扫描或外部写入，事实仍继续保存；已排队任务沿用缺少写入目标时失败与有限重试的既有行为。已执行的飞书更改不会自动撤销。版本恢复须保留新增表和既有事实；`0051` 在已有事实、冻结阶段或字段绑定时拒绝降级删除，涉及恢复数据或公式须单独授权。
