# 部署与运维手册

适用全系统 API、网页、worker、MySQL、OSS、MCP和飞书机器人。运行基线：2026-09-30，`v1.1.6`、迁移 `20260930_0049`。操作脚本及参数以[部署目录说明](../../../deploy/README.md)、[Compose](../../../deploy/)和[配置定义](../../../server/app/settings/config.py)为准。本文描述操作流程；本轮未执行服务器巡检或生产改动。

Issue #222 待发布变更包含迁移 `20261006_0050`：发货状态约束移除 `VOID_PENDING`。升级前检查旧待审核发货单、待处理申请和未完成审批通知；任一存在则停止升级，不自动清理或改数量。历史申请表、已作废单和审计保留。确认处理存量问题后再执行原发布流程；API、网页和小程序同步移除旧审批展示，运行基线以实际部署核验为准。

## 环境和受控资源

| 环境 | 用途 | 配置与隔离 |
|---|---|---|
| 本地开发／测试 | 开发及自动化 | 独立 `mysql-dev`、`mysql-test`；假适配器仅指定演示模式可用 |
| 共享测试 | 外部联调及业务验收 | `compose.shared-test.yaml`、`.env.shared-test`；独立数据库、账号、Bucket、外部身份与域名 |
| 生产 | 正式业务 | `compose.production.yaml`、`.env.production`；公司 ECS、MySQL8、私有 OSS及生产域名 |
| 隔离恢复 | 备份演练 | MySQL库名以 `_restore` 结尾，OSS Bucket以 `-restore` 结尾；禁止使用生产目标 |

受控环境文件权限设为 `600`，不能提交到 Git、聊天、日志或交接文档。数据库、OSS、飞书、聚水潭、微信、模型、GitHub和域名必须明确维护责任与授权转移流程，核验表见[维护与交接](维护与交接说明.md)。

## 配置分组

以下列出必要配置组；默认值和完整名称查看配置源文件。配置示例只作名称参考，生产模板需补齐实际启用能力所需字段。

| 分组 | 关键配置（均带 `ORDER_TRACKING_` 前缀） | 配置检查 |
|---|---|---|
| 基础 | `APP_ENV`、`DATABASE_URL`、`ADMIN_WEB_BASE_URL`、`WEB_COOKIE_SECURE` | 环境正确、独立非root数据库账号、HTTPS、生产安全 Cookie |
| 身份保护 | `IDENTITY_TOKEN_SECRET`、`PHONE_ENCRYPTION_SECRET`、`PHONE_DIGEST_SECRET` | 使用受控强随机值；随意更换会影响既有会话、手机号和匹配 |
| 飞书身份 | `FEISHU_IDENTITY_APP_ID`、`FEISHU_IDENTITY_APP_SECRET`、`FEISHU_IDENTITY_REDIRECT_URI`、`FEISHU_SUPER_ADMIN_SUBJECTS` | 登录回调及白名单，不能复制真实人员标识到仓库 |
| 飞书来源 | `FEISHU_ORDER_APP_ID`、`FEISHU_ORDER_APP_SECRET`及其余 `FEISHU_ORDER_*` | 来源范围已确认、字段映射合法、应用授权与分页正确 |
| 聚水潭 | `JST_*` | Token缓存指定持久路径，例如 `/var/lib/order-tracking/jst/token.json`；权限、限流与续期 |
| 微信 | `WECHAT_*`、`WECHAT_NOTIFICATION_MINIPROGRAM_STATE` | 同环境AppID、模板和合法域名；共享测试`trial`、生产`formal` |
| OSS | `OSS_*` | 私有Bucket、RAM最小权限、Region／Endpoint一致 |
| MCP | `MCP_PUBLIC_URL`、`MCP_CLIENT_ID`、`MCP_FILE_HOSTS` | URL和客户端必须成对配置，路径`/mcp`，公开HTTPS，文件主机精确白名单 |
| 来货出入 | `FEISHU_BOT_ENABLED`、`FEISHU_BOT_VERIFICATION_TOKEN`、`FEISHU_BOT_ENCRYPT_KEY`、`INCOMING_DIFF_VISION_API_KEY`、`INCOMING_DIFF_VISION_BASE_URL`、`INCOMING_DIFF_WORKBOOK_SIGNING_SECRET` | 机器人回调验签、模型可用、强签名密钥；不得使用测试签名默认值 |
| 外发与告警 | `WECHAT_NOTIFICATIONS_ENABLED`、`FEISHU_NOTIFICATIONS_ENABLED`、`OPS_ALERTS_ENABLED`、`OPS_ALERT_RECIPIENT_USER_ID` | 逐项登记开关及责任人，首次真实发送单独授权并验收 |

飞书机器人复用订单来源应用，增加消息、卡片和资源权限后还须发布应用版本；回调返回成功不能证明图片下载、识别、核对表投递或业务登记成功。最高管理员、来源范围、外发开关、Plugin配置的实际值与核验日期记录在受控运维资料，仓库只记脱敏结论。

## 生产发布

1. 确定 Issue/PR、目标 SHA、版本号、迁移影响和配套小程序／Plugin版本；完成该 SHA的完整 main push CI。
2. 检查环境配置、磁盘、备份目录、上一版本镜像及 schema兼容性，准备业务验收样例。
3. 用户明确授权创建并推送新 `v*` 标签。已发布标签保持不可变；普通main推送不触发生产发布。
4. Release核验同一SHA的main CI后发布 server、admin-web两个GHCR镜像；两镜像成功后自动调用生产部署，无需单独手动CD。
5. 部署检查镜像revision、备份MySQL和OSS、执行Alembic、更新容器并等待健康；成功才记录版本。
6. 检查外部HTTPS、本人登录、三角色worker、关键查询与业务样例，填写[发布记录](版本发布记录.md)和[验收记录](验收记录.md)。

GitHub配置名称：`PROD_SSH_HOST`、`PROD_SSH_PORT`、`PROD_SSH_USER`、`PROD_SSH_PRIVATE_KEY`、`PROD_SSH_KNOWN_HOSTS`、`PROD_DEPLOY_DIR`。Release使用内置`GITHUB_TOKEN`；服务器不需要个人Token。部署包保存在 `DEPLOY_DIR/releases/<commit>/`，受控配置在 `DEPLOY_DIR/deploy/.env.production`。

服务器前提：Docker Compose支持`--wait`，Python3.8+、mysqldump、flock、ossutil2.x、受控备份目录及已核验SSH主机密钥。固定镜像为 `ghcr.io/kocotree/order-tracking-server:<version>` 与 `ghcr.io/kocotree/order-tracking-admin-web:<version>`，API和worker使用相同server版本。禁止使用`latest`。

共享测试沿用 Git＋Compose：[preflight](../../../deploy/scripts/preflight.sh)→独立备份→[release.sh](../../../deploy/scripts/release.sh)→健康和HTTPS。旧Git/build发布脚本用于共享测试；生产使用镜像CD。标签授权不包含真实通知、小程序上传或正式发布。

## 日常巡检

在目标release的`deploy/`目录，以受控环境文件执行只读检查：

```bash
docker compose --env-file .env.production -f compose.production.yaml ps
docker compose --env-file .env.production -f compose.production.yaml top worker
docker compose --env-file .env.production -f compose.production.yaml logs --since 30m api worker
```

核对外部 `/health/live` 和 `/health/ready`；执行[health-check.sh](../../../deploy/scripts/health-check.sh)时从对应release的`deploy/`目录传`production`。记录时间、版本、状态及脱敏错误，避免复制整段含私人数据的日志。

| 项目 | 健康判断与证据 |
|---|---|
| 容器 | api、worker、admin-web健康；实际镜像version和revision与发布记录一致 |
| worker | `sync`、`incoming`、`notification`全部存活并有各自`worker.started`；只看worker容器Up不足以确认子进程 |
| 自动订单 | 最新`order_import_runs`完成时间、失败项；`audit_logs`中的`source_terminal=system`及`order.detail_dispatched`；按订单＋工厂核查 |
| 图片 | SKU缓存状态与失败码，OSS对象可读取；合同／箱贴首次导出前检查所选颜色有可用代表图 |
| 来货出入 | 批次状态、图片OCR、当前核对表版本、待确认行、登记记录和对应流水；模型候选与正式记录分开 |
| 通知 | outbox状态、重试／最终失败、站内记录、平台送达证据；关注`deliveryId`及`manual_review_required` |
| 数据与容量 | MySQL连接、锁等待、磁盘、备份目录、OSS容量；记录阈值和告警负责人 |

三个worker默认各有独立连接池，默认最多共45个连接，容量规划再加API池；该值为配置上限，实际连接量需实测。任务日志使用`role`、`workerId`、`jobId`、`jobType`、`deliveryId`定位。普通任务过期租约5分钟后恢复，订单自动同步使用专用锁恢复；角色过滤同时覆盖领取和恢复。子进程退出导致整组重启；优雅退出等待30秒，Compose停止窗口45秒。

## 常见故障处理

| 现象 | 检查顺序 | 处理边界 |
|---|---|---|
| 登录失败／无权限 | 环境、飞书手机号权限、用户启停、白名单、微信绑定、会话／共同授权 | 不直接修改内部身份绕过手机号或停用校验 |
| 来源订单缺失／不自动派工 | 最新同步批次→95%门槛→采购关联→产品／工厂／人员／日期→人工撤回暂停 | 来源错误先给逐条证据；修复、重跑或生产改写需明确范围 |
| 图片缺失／导出失败 | SKU来源、缓存revision与对象→所选分组→首次固定快照→requestId | 不用其他款／颜色图片代替；历史导出快照保留 |
| MCP无法连接／文件失败 |公开HTTPS、resource/client配置→本人OAuth→停用和PKCE→允许文件主机、DNS、20MiB、格式 | 不放宽为任意域名；记录客户端真实兼容限制 |
| 机器人只回卡片／无文件 |应用已发布权限→事件／卡片校验→资源下载→incoming角色任务→模型→outbox投递 | 回调、下载、识别、投递及正式登记各自核验 |
| 收货／差异数量不符 |原报箱项→收货确认→退回／撤回→初始基线→来货及调整流水→当前归属 | 禁止直接覆盖汇总或反复提交制造补偿 |
| worker任务停滞 |三子进程→角色任务领取／恢复→锁租约→外部超时→失败状态与错误码 | 手工重试先检查幂等和原动作结果；通知失败不重做业务提交 |
| 部署失败 |失败阶段→实际镜像、容器、schema、备份→外部健康 | DDL和部分更新无法假定自动恢复，检查状态后制定修复动作 |

## 图片与产品受控维护

使用[现有运维工具](../../../server/scripts/enqueue_product_sync.py)，从`server/`运行；容器内使用`/app/.venv/bin/python -m scripts.enqueue_product_sync`。真实环境执行须明确授权目标和范围。

```bash
uv run python -m scripts.enqueue_product_sync targeted --i-id '精确款号'
uv run python -m scripts.enqueue_product_sync targeted --i-id '精确款号' --commit '预览digest'
uv run python -m scripts.enqueue_product_sync images
uv run python -m scripts.enqueue_product_sync images --commit '预览digest'
```

默认只预览；来源或目标变化拒绝旧digest。记录环境、匹配／复用／下载／缺失／失败／未匹配的逐SKU证据，失败退出码不得当作完整成功。SKU图片独立保存；旧对象和订单、合同快照保留。产品全库游标、定向补拉和图片补齐用途不同，操作前查看`--help`。

## 备份、恢复与版本恢复

部署和每日00:00定时任务运行同一[backup-production.py](../../../deploy/scripts/backup-production.py)，共享部署锁。保留最新30份MySQL和3份OSS快照，仅清理脚本自己的`production-<stamp>`文件；实际cron安装、时区、成功时间、离机保存和容量须巡检。

MySQL备份包括摘要，OSS保存对象快照。数据库文件索引与对象须取一致备份批次；备份完成只能证明产物存在，恢复演练还需验证表、数量、附件和应用可用。

恢复演练先创建独立空库、独立Bucket和最小权限账号，将受控恢复配置放Git外。明确授权后，使用[restore-mysql.sh](../../../deploy/scripts/restore-mysql.sh)传备份文件与受控配置文件；使用[restore-oss.sh](../../../deploy/scripts/restore-oss.sh)传OSS备份目录与`-restore` Bucket。确认变量为`ORDER_TRACKING_RESTORE_CONFIRMED=restore-test-only`。验证摘要、schema、代表性数据、私有文件读取和隔离环境业务流程，记录恢复耗时及问题；不得对生产目标演练。

服务器应用恢复到旧版本前，确认旧代码兼容当前schema和新增数据，获得具体版本操作授权。使用保留的上一release与精确镜像版本、设置`ORDER_TRACKING_DEPLOY_VERSION`，按部署说明执行Compose`up -d --no-build --wait api worker admin-web`及production健康检查。禁止执行Git回滚或自动Alembic downgrade；`0049`已有未派工数量记录时会拒绝降级。若涉及数据恢复，另行批准目标、备份批次及数据损失范围。完成后核对HTTPS、登录、worker和业务并更新版本记录。
