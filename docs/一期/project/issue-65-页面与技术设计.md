# Issue #65 页面与技术设计

用户已确认业务与页面方案并授权本地实施，按 GitHub Issue #65 的最终规则执行。

## 规则与页面

- 本厂启用用户可撤回未收货、未发生有效退回的有效发货单。撤回立即扣回有效数量，保留原单号及正式历史。重新提交仍使用原单号。
- 撤回草稿只允许该次正式提交人和本次撤回人读取、编辑、重新发货。每次撤回重新确定权限；普通草稿仍按个人账号隔离，二者互不覆盖。
- 复用发货记录、详情及装箱页面；原卡片显示“已撤回·待修改”，授权者从原详情“继续修改”。撤回必填原因，确认成功直接进入“修改发货单”；草稿恢复原箱、凭证、备注，自动保存，最终按钮为“重新发货”。退出重进恢复同一份保存内容。
- 保存、文件修改和提交校验版本；过期请求拒绝覆盖。用户确认放弃本页未保存修改后才重新加载。已重新提交后不能继续保存。
- 管理员只读正式历史，不看未提交修改；去掉新流程审核入口。核对草稿在撤回后失效并留审计，旧页面保存/确认提示“发货单已撤回”。
- 管理员小程序及通知同步结果与状态，订单数量刷新，不扩展其他布局。

## 技术方案与顺序

原正式 Shipment 新增 WITHDRAWN 状态；撤回复制不可变历史行和编辑草稿，以 source_shipment_id 关联原单，普通列表排除派生行。编辑草稿不占用个人普通草稿。原单内容在重新提交前不变；重新提交后更新原单，派生草稿固化为隐藏历史。

箱、行、文件关系复用既有模型。附件允许多单引用同一 StoredFile，历史引用不可被草稿删除。下载接口逐个关联单鉴权。草稿写操作先锁原单再锁草稿；版本必须匹配，附件变更也增加版本。

每轮提交以派生草稿 ID 作为独立流水源，撤回以操作 ID 为独立冲销源。通知每轮独立去重并固定事件事实，避免延迟消费读到下一轮内容。撤回前记录收货核对快照，清空当前核对明细并递增版本，拒绝旧页面保存与提交。

顺序：资料同步 → 现有发货 API/MySQL 测试 → 模型迁移及事务 → 通知 → 三端页面 → 后端、网页回归与静态检查 → 本地提交停止。
