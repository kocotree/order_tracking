# Issue #68 本地实施记录

## 范围与依赖

本轮按用户 2026-09-09 授权，只执行首页与订单列表优化、必要本地测试和本地提交；不运行 Playwright 或其他浏览器检查，不推送、建 PR、合并 main、部署或关闭 Issue。

工作区分支 `codex/issue-68-order-pagination`，基线为最新 main `e0b81a4` 及范围/设计记录 `ef81a3c`。依赖 #71 的轻量完整工厂选项契约 `a23a483`，已在本分支应用为 `2689c81`；后续 PR 应明确此依赖，集成后重新生成统一 OpenAPI 类型。没有新增依赖、数据库字段或迁移。

## 实现

- 首页订单与通知请求独立启动；通知慢或失败不阻塞订单和统计展示。原通知内容、排序和操作保持。
- 管理员订单读取在 SQL 中完成全局筛选、派工日期/状态判断、排序、计数与分页。工厂筛选使用 EXISTS 避免一对多重复；只批量读取当前页的明细、派工和数量台账。详情快照组装与工厂角色旧路径保留。
- 数量排序先分别聚合台账、派工和订单明细，避免连接放大数量。进度使用整数商/余数保持 Python 的五成双取整，避免 MySQL 小数除法把接近半值的百分比截断后排错。
- 订单列表原排序来自后端 Python 字符串顺序，因此使用二进制 NO PAD 排序保留大小写、中文、数字文本及末尾空格顺序；不改成另一种自然排序。产品按完整明细 ID 顺序拼接，工厂按完整工厂 ID 顺序拼接并保留同工厂最后的快照名，日期空值始终最后。拼接/排序上限使用查询级提示，不修改连接或全局设置。
- 首页最近订单仅取 10 条；逾期统计全局可见正式订单，已完成和草稿排除。今日发货按北京时间业务日期，含有效 `SHIPPED` 和历史 `VOID_PENDING`，排除 `DRAFT`、`VOIDED`、最新 #65 的 `WITHDRAWN`、删除记录及独立返修发回。
- OrdersPage 使用 #71 的完整轻量工厂选项，与订单请求独立；保留列表请求序号、分页越界回退及原样式，不增加可见内容。卸载时使旧订单响应失效。

测试仅使用本机独立 `order_tracking_issue68_test`，未修改开发库、共享测试或生产数据。

## 性能证据

只在本机隔离 MySQL 8 使用同一数据集比较；每个订单一条产品明细、一个派工，读取第 2 页、每页 10 条，包含服务内管理员校验。旧方法从共同基线 `ef81a3c` 的 `OrderService.list_visible` 加载，新旧快照逐项完全相等。各组连续运行三次，耗时为服务调用中位数：

| 订单数 | 排序 | 旧 SQL 次数 | 新 SQL 次数 | 旧耗时 ms | 新耗时 ms |
|---|---|---:|---:|---:|---:|
| 25 | 默认优先级 | 77 | 6 | 28.39 | 5.70 |
| 25 | 产品名称升序 | 77 | 6 | 30.15 | 4.45 |
| 25 | 工厂升序 | 77 | 6 | 26.83 | 3.66 |
| 105 | 默认优先级 | 317 | 6 | 107.23 | 4.36 |
| 105 | 产品名称升序 | 317 | 6 | 114.75 | 3.72 |
| 105 | 工厂升序 | 317 | 6 | 105.92 | 4.01 |

快照 JSON 字节数新旧相同：25 单组 13,705 字节，105 单组 13,712 字节。订单 API 原来已经返回分页内容，本轮主要减少服务器读取和组装；不声称该接口返回体缩小。

EXPLAIN 发现最初的关联逾期 EXISTS 可能逐订单全扫派工；最终改为非关联的派工/台账集合，计划由 `DEPENDENT SUBQUERY` 改为 `SUBQUERY`，台账走 `ix_quantity_ledger_assignment`。日期汇总使用 `ix_order_lines_order` 和派工唯一索引；产品汇总使用订单明细索引，工厂窗口汇总使用派生表索引。订单全局扫描/排序和工厂派生表仍会随数据增长，不能把固定 6 条 SQL 描述为数据库计算量恒定。本轮未据小样本新增索引。

这些是本机服务查询与快照量测，不是正式接口、浏览器首屏或线上提速承诺。真实数据规模的延迟、浏览器视觉、远程 CI、共享测试和生产发布未验证，留给下一阶段。
