## 2. 数据边界与不变量

采用“来源明细完整保存，派工成功才建立执行记录”。保留现有发货、箱明细、数量账本和合同所引用的执行 ID，避免重建历史发货链。

1. 订单来源明细是管理员详情的行身份；使用稳定 `detailId`，不用当前序号、SKU、工厂名或候选行自增 ID 作为更新身份。
2. 原始资料、已确认来源版本、人工日期和已派工快照分开。来源抓取成功不等于管理员接受更新。
3. 未派工数量可为空，原文原样保存；正式派工数量必须满足整数范围及业务约束，不接受布尔、小数、截断或溢出。
4. 派工明细对应一个确定工厂；同一来源明细最多一条当前有效执行关联。派工后工厂、产品、下单量和初始基线不可普通编辑或来源覆盖。
5. 已派工明细统一已发＝固定初始基线＋现有有效发货账本；未派工只展示已接受的来源已发。两者不可重复相加。
6. 所选明细全成功或全失败；更新来源和派工是两次独立确认。已确认来源更新后再取消派工，保留前一次已确认更新；取消来源更新本身不落业务数据。
7. 所有日期使用现有 Asia/Shanghai 业务日期规则。来源日期只减四个自然日一次，人工日期不减。

## 3. 拟议存储结构

字段名是实施约定草案；最终迁移版本号在实施时从最新 Alembic head 分配。

### 3.1 新增 `order_details` 来源明细表

| 字段组 | 拟议字段和约束 |
|---|---|
| 身份 | `detail_id` 主键；`order_id` 外键；`source_record_pk` 可空外键；`origin` 为 feishu/legacy/manual；`sort_order` 稳定展示顺序 |
| 来源唯一性 | 飞书来源 `source_record_pk` 唯一绑定一个系统明细；订单号仍按现有唯一规则去重，不能跨订单挪动来源 |
| 已接受资料 | `accepted_raw_fields` JSON，`accepted_source_modified_at`，`accepted_source_hash`；只保存业务来源字段，不存连接凭据 |
| 解析结果 | SKU/名称/规格/工厂原文；可空 `matched_variant_id`、`matched_factory_id`、`order_quantity`、`source_shipped_quantity`、`source_tracker`、`source_contract_ship_date`；`parse_issues` |
| 日期 | 可空 `contract_ship_date`；`date_override_enabled` 区分无覆盖和主动清空；来源更新保留覆盖值，包括空值 |
| 派工 | 可空 `assignment_id`；`dispatch_state` 为 UNASSIGNED/ASSIGNED；`dispatched_at`、`dispatched_by`、`dispatch_batch_id` |
| 并发审计 | `version`、创建/更新时间；变更写现有 `AuditLog` |

不把校验缓存当作权限依据：产品/工厂/账号状态在预检查和最终事务中重新读取。只读详情按需要计算问题，不在表格单元格堆叠原因。

### 3.2 现有执行表

- `orders.tracker` 允许空；新增 `tracker_locked_at`。所有来源值保存在明细，不用假的合法跟单人占位。首次派工锁定唯一合法订单跟单人；后续未派工来源必须与锁定值一致，不能随刷新更换已执行订单的负责人。
- `order_lines` 保留订单＋产品唯一及正数量约束，作为已派工执行聚合。飞书新草稿可暂时无执行行。派工时按产品创建或锁定聚合行，其 `order_quantity` 仅汇总执行分配，不能用它代替管理员所见整单来源数量。
- `order_assignments` 保留 ID、正分配数量、非负初始基线及账本引用。移除 `assigned_quantity >= initial_shipped_quantity`，保留其他校验。
- 新增 `detail_id` 可空唯一外键及 `is_active`；将原行＋工厂唯一约束改为普通索引。新来源每条独立执行关联，允许同 SKU、同工厂分批派工且不同日期；旧关联不拆分，不改 ID。
- 来源明细与执行关联的双向一致性由同一事务保证，增加集成测试及迁移核对；不得形成一行多份有效基线。
- 同 SKU 同厂多来源的新规则采用逐来源明细派工，覆盖旧按同 SKU/工厂强制合并日期规则；已有历史聚合不追溯拆分。本规则以一期需求Issue #87最终确认专节为准，覆盖旧按SKU/工厂聚合日期的冲突说明。

### 3.3 预览和幂等

新增短期 `order_change_previews`：预览 ID、订单/操作者、用途（refresh/dispatch）、订单版本、明细版本和有序选择集合、服务器抓取的来源值及 hash、创建/过期时间、消费状态。建议有效期五分钟，超时重新检查；这是技术配置，不增加页面字段。

复用现有幂等记录能力并补充请求 hash、结果批次引用。派工 `Idempotency-Key` 以操作者＋订单＋动作限定；同 key 同内容重试返回原批次结果，同 key 不同内容返回冲突。数据库事务内同时写派工、批次审计、幂等和现有 outbox。

## 4. 导入及来源更新

### 4.1 导入

候选确认锁定候选并验证版本、管理员权限、稳定来源身份和订单号去重，一次保存订单及全部来源明细、日期人工覆盖，标记候选 IMPORTED。产品、数量、日期、账号和跟单资料的问题只记录，不阻止保存。不得调用旧 `_replace_lines` 的严格构建路径，也不生成发货账本、工厂任务或派工通知。

来源适配器与候选 DTO 同步支持未知数量；未知参与的对应合计返回 null，前端显示“—”，不能通过 `sum(value or 0)` 给出伪完整总数。纯技术读取失败、缺稳定记录身份或无法确定订单归属要明确失败，不生成猜测订单。

用户最新确认：同一订单任一来源明细的出货总数÷下单数严格小于95%，即整单进入候选，拉取全部明细；等于95%不满足条件，其他行超发不影响合格行触发整单入选。比较原始精确数量，不能按页面四舍五入后的百分比判断。数量异常无法计算时不伪造进度，用户已确认这类订单也进入候选，允许先导入、派工时再校验；仅全部数量合法且每行进度均≥95%时按进度门槛跳过。

### 4.2 更新未派工明细

1. 读取当前订单的稳定来源集合，仅针对未派工明细从飞书读最新资料；来源适配器增加按已知记录集合读取能力，不触发全库发现，也不依赖只扫描新记录的游标。
2. 在数据库事务外完成网络请求，校验完整返回和来源身份。不自动追加、删除或挪单；非预期缺行/订单号变化返回来源冲突，保留现有资料。
3. 重新匹配系统产品、工厂，生成当前值与新值的服务器端预览；人工日期不进入待覆盖字段。系统资料新匹配结果同样作为差异展示。
4. 确认时锁订单，核对订单和每行版本及仍未派工，只应用服务器保存的预览；不接受客户端提交任意工厂、数量等业务值。
5. 记录前后差异、操作者、来源版本、被保护日期；订单/明细版本递增。取消或失败不应用差异。

来源新值可以更不完整，确认后仍保存并在派工校验拦截。未派工刷新不能修改已锁定订单跟单人，冲突只作为后续该批派工问题。

### 4.3 日期保存

仅管理员网页、仅未派工明细允许更新日期；接口白名单只含日期和版本，额外业务字段拒绝。失焦自动保存，期间禁用派工/刷新；成功后使用服务器返回版本和汇总，失败明确提示并保留可重试输入。清空可保存但不能派工，写入人工覆盖标志；不新增恢复来源日期按钮。

## 5. 分批派工协议

拟议新增路径均位于 `/api/v1/admin/orders/{orderId}`，复用 Web 会话、CSRF、管理员权限和统一错误结构。

| 方法与相对路径 | 请求重点 | 返回与副作用 |
|---|---|---|
| `PATCH /details/{detailId}/contract-date` | `version`、`detailVersion`、可空日期 | 保存日期，返回新版本和详情摘要 |
| `POST /source-refresh/preview` | 订单版本 | 读飞书并生成差异预览，不改业务资料 |
| `POST /source-refresh/confirm` | previewId、版本、幂等 key | 原子应用尚未派工资料，返回详情 |
| `POST /dispatch/preview` | 订单版本、有序去重 detailIds | 先检查未派工来源；有差异返回更新预览，否则返回逐行校验与派工预览 |
| `POST /dispatch/confirm` | dispatchPreviewId、版本、幂等 key | 最终校验，整批派工或无业务写入 |

派工前来源检查与“更新未派工明细”共用读取能力。已确认更新后生成新的派工预览，保留用户选择，但重新校验；不复用旧版本。

最终确认流程：先在事务外按本次选择重新读取来源并比对业务 hash，再进入短事务；锁订单→按 ID 顺序锁明细→按固定顺序读取/锁相关产品、工厂与审核通过启用账号→核对版本/来源预览/日期/跟单→写执行行、初始基线、明细状态和批次事实→写 outbox/审计→提交。相关账号/产品停用事务必须遵守相同锁顺序，避免检查通过与停用之间穿透。

任一选中明细已派工、不可匹配、数量无效、缺日期、工厂/账号不合格或跟单冲突，整批返回结构化问题（detailId、字段、错误码、中文原因），不得静默跳过。推荐409用于版本/来源/状态冲突，422用于业务校验，502/503用于来源读取失败。失败保持选择，弹窗显示原因。

飞书和 MySQL 没有跨系统事务，不能保证飞书在最后读取后的瞬间不再改变。合同约定是固定最后一次核验并确认的快照，后续已派工来源变更不覆盖；记录核验时间/hash，不宣称分布式强一致。网络请求不能占用 MySQL 行锁。重复提交优先命中已完成幂等结果，不能因之后飞书变化把已成功请求报告为失败。

## 6. 数量、状态与查询

每条已派工明细：`shipped = initial + effective_ledger`；`pending = max(order_quantity - shipped, 0)`。未派工用已接受来源已发计算展示值；未知保持 null。整单未发＝逐条未发之和；任一未知则该合计未知。不能先汇总下单、已发再相减。

| 情形 | 管理员整单显示 |
|---|---|
| 零条有效派工 | 草稿，全部页签包含 |
| 至少一条已派，仍有未派工或欠量明细 | 未完成；有未交完明细有效日期已过则已逾期 |
| 未派工明细缺日期 | 不据此判逾期，但阻止整单完成 |
| 单条超发/恰好发完并派工 | 明细完成、未发0，不进入待发选单 |
| 全部已派且逐条完成 | 具备整单完成条件，仍须管理员手动确认 |

未派工但来源数量已经交足的行仍阻止整单完成，其日期不因未派工本身被判交货逾期。判断顺序明确为草稿→已确认完成→有逾期→其他未完成。

管理员详情新增 `details`、派工计数及可用操作；保留既有 `lines/assignments` 供执行端兼容，不能同时加总。管理员订单列表、首页、日期筛选、工厂选项和状态计数改为全量来源/执行联合口径，SQL先筛选排序计数再分页，空值排末，不新增列表列宽或派工状态列。

工厂列表、详情、数量、日期汇总、可发货选单仅取本厂 `is_active=true` 执行记录；未派工来源明细和其他工厂资料不得出现在响应中。发货保存/正式提交/撤回重提逐项重新校验，不信任客户端 assignmentId。管理员小程序保持既有权限与展示范围，新增宽松草稿处理仍在网页端，不新增小程序编辑入口。

## 7. 现有功能兼容推荐

### 完成与重新打开

用户已确认保留管理员“确认订单完成”，增加全部已派且每条 pending=0 的服务端条件；不允许一条超发抵扣另一条欠量，不允许未派工行绕过。保留“重新打开”及原因日志。发货撤回、退回、收货差额继续走既有有效账本与恢复处理，新增派工完整性检查；不删除历史完成日志。不改为自动整单完成。

### 按工厂撤回与删除

不保留整单撤回入口或接口，也不建设不存在的历史整单撤回兼容。管理员在订单内选择一个当前已派工工厂，一次撤回该工厂的全部有效派工；其他工厂的派工、数量、合同和发货保持不变。所选工厂存在有效系统发货时禁止撤回。撤回将对应 assignment 标记为 `is_active=false`，来源行恢复未派工；执行行、数量账本、操作历史和已有合同不物理删除。最后一个工厂撤回后订单回到草稿，否则保持已发布。

撤回时保留当前数据，不主动重读飞书；重新派工沿用正常来源检查、差异确认和派工校验协议。若实际读到变化，走已有差异确认，不静默覆盖。涉及已有历史账本的执行关联必须确保有效数量只计一次。


删除沿用现有权限和软删除限制，同时撤销有效任务；已完成/有有效系统发货的订单继续禁止删除。来源唯一绑定保留，避免删除再导入重复登记；不提供新清理入口。

### 加工合同

用户最新确认：订单只要有一个工厂已派工，即可导出该已派工工厂的合同，不要求整单全部派工，也不再以统一已发为零作为资格条件。已发生发货或初始超发都不阻止合同导出；完成状态不能再作为零出货限制的替代拦截。尚未派工的工厂不生成合同。既有工厂法定合同资料要求未被本次明确取消，继续保留。

导出内容以所选工厂当前已派工明细为范围，不包含其他工厂及未派工行。用户说明同一订单不会出现该厂合同导出后再追加该厂明细的情况，本次不建设合同内容修订、多版本业务流程或合同补充机制；保留既有订单＋工厂编号、首次合同快照和重复导出规则。该说明不撤销此前同厂部分明细可先派的已确认能力，也不新增全厂必须一起派工的校验。

### 通知与提醒

复用 outbox/worker。每次成功派工按批次＋工厂唯一记录事件，载荷固定本批 assignmentIds、日期和数量；worker 不按执行时整单范围重新组装，防止后派明细混入前批通知。同 key 重试不重复通知，来源更新和导入不外发。

到期提醒保留已确认的角色、节点和渠道，只对当前有效派工且欠量明细发送；管理员页面的未派工逾期不自动新增外发提醒场景。延迟消息消费时复核有效任务及接收人权限，按工厂撤回后不发送该工厂失效任务。新增派工事件不得向未选工厂或未派工行广播。真实外发验证另行授权。

## 8. 历史迁移与发布顺序

1. 实施前在获授权环境统计候选、草稿、正式/已完成订单、历史人工完成欠量、合同、已撤回发货及同 SKU/工厂聚合情况。本次不读取生产数据，不能断言没有例外。
2. 新表/可空字段先增量创建，再移除仅阻止超发的约束、调整派工唯一约束和来源解析结构。不删除原始字段或执行记录。
3. 新建订单采用来源逐条模式。历史正式/已完成订单按已有 assignment 创建 legacy detail，保留 ID、分配量、初始量、日期、日志及合同；不要按当前飞书值重算历史。
4. 历史草稿按现有执行分配建立未派工明细和 inactive 关联；来源可唯一核验映射时才连接来源。历史聚合对应多条来源不能凭 SKU/厂名猜成一对一，迁移前输出异常清单并明确处理方式。无可靠来源的历史/手工行保留快照，不提供伪来源刷新。
5. 用户明确正式环境没有“已手动完成但仍欠量”的订单，不建设该历史状态特例或批量重开流程；这是用户提供的业务事实，本轮未查询生产验证。后续完成统一执行全部已派且逐条交足。迁移不产生通知、发货账本或新合同。
6. 核对迁移前后订单数、assignment ID集合、每笔有效账本及其关联、初始量合计、合同 ID/编号/hash一致；新明细映射全覆盖、无多重有效派工、无孤立引用。
7. 发布切换时暂停订单/发货相关写入和 worker，按批准流程备份→迁移→升级 API/网页/worker→核对→恢复；新旧接口不得同时对同一飞书订单执行不同规则。
8. 新飞书订单旧 `save_draft/publish` 入口拒绝绕过，仅走新日期/派工协议；历史手工流程保留但共用有效派工和完成检查。旧小程序保持执行响应兼容，并由服务端拒绝失效派工 ID。
9. 新数据含超发/未匹配资料或部分派工后，旧程序不能安全直接回滚。回滚前检查新写入；有新业务时优先前向修复，若必须恢复备份，需要明确期间数据补录与单独授权，不能执行有损 downgrade。

## 11. 最终确认结论

用户已完成本轮规则确认，无遗留业务选择；正式开发计划与执行Ticket另行准备和确认。

1. **完成**：保留手动确认，必须全部派工且逐条交足。用户说明生产无历史已完成但欠量订单，不建设此类兼容例外。
2. **合同**：有工厂已派即可导出该厂合同，不要求整单全派或已发为零；用户说明不发生该厂导出后再追加明细，沿用现有编号和首次快照，不建设合同修订。
3. **撤回**：删除整单撤回，改为选择一个已派工工厂并撤回该厂全部有效派工；有有效系统发货时禁止。其他工厂不受影响，最后一个工厂撤回后订单回草稿；保留当前值和历史，再派走正常来源检查及差异确认。
4. **候选**：任一来源明细精确出货进度<95%，整单全部明细进入候选；数量缺失或错误导致无法判断时也进入候选。只有全部数量正常且每条进度均≥95%才按进度门槛跳过。异常原值保留，派工时校验；不绕过稳定来源身份、订单归属和去重。
