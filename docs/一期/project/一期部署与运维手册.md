# 一期部署与运维手册

整理日期：2026-09-08；脚本基线：本地 `3b2c90d`。面向维护人员，使用前确认目标环境和实际部署目录。本文整理已有流程，本轮没有执行服务器命令、发布、恢复或真实通知。

## 环境与前提

| 环境 | 配置与用途 |
|---|---|
| 本地 | 根目录 Compose、被忽略的 `.env`；开发库与测试库隔离，启动见 [README](../../../README.md) |
| 共享测试 | `deploy/compose.shared-test.yaml`、受控 `.env.shared-test`；Git/build 发布脚本 |
| 生产 | `deploy/compose.production.yaml`、受控 `.env.production`；固定 GHCR 版本镜像、标签触发 CD |

正式目标为独立数据库、最小权限账号、独立 OSS 与身份配置。但 [Issue #58](issue-58-生产CD接入与首次部署.md)记录首次部署接受测试／正式共用 MySQL 账号，数据库与桶独立。账号级隔离不能标记已完成，后续需单独整改与验证。

生产维护需要确认 SSH 主机指纹、受控配置和备份目录。依赖及 Secret 名称见 [部署入口](../../../deploy/README.md)，不复制真实值到文档、日志或聊天。服务器部署不等于小程序发布。

## 发布步骤及成功标准

1. 确认目标 PR 已合并；取得该精确 SHA 的 main push 完整 CI 成功证据，不能只看分支或 PR CI。
2. 确认新版本号未使用、上一版本镜像及配置仍保留，核对迁移与回滚兼容性。当前已记录 v1.0.0，不照抄旧示例再次创建它。
3. 用户批准创建／推送具体 `v*` 标签后执行；普通 main 推送不部署。标签推送授权该版本自动生产部署。
4. 观察 Release：核验同 SHA 的 CI → 两类镜像发布 → 自动调用生产部署。前置阶段失败不得跳过门禁继续。
5. 部署自动核验镜像 revision、备份 MySQL/OSS、执行迁移、启动 API／worker／网页并检查健康；完成后记录版本。
6. 对照目标标签 SHA、镜像 revision、`ORDER_TRACKING_DEPLOY_VERSION`、受控发布记录与运行容器。再验证外部 HTTPS、登录及本次变更的业务流程，分别记录结果。

只读工作流查询（仓库目录）：

```bash
gh run list --workflow ci.yml --limit 5
gh run list --workflow release.yml --limit 5
gh run view <run-id>
gh run view <run-id> --log-failed
```

以上为手册示例，本轮未运行。日志对外分享前脱敏。发布失败可能已执行 DDL 或替换部分容器，不能认为“失败即恢复原状”。

共享测试另走 [deploy/README.md](../../../deploy/README.md) 的 preflight、备份、release 顺序；不要用旧 Git/build 脚本回滚生产。

## 日常巡检

在已确认的部署目录运行与环境匹配的命令；生产使用保留的对应 release 目录及其受控配置，不随意混用源码目录配置。

```bash
bash deploy/scripts/health-check.sh production
```

该脚本检查 Compose 状态、API `/health/live` 与 `/health/ready`、网页容器 `/healthz`，只证明内部健康。外部域名 HTTPS、登录、数据库备份新鲜度、worker 积压和真实消息送达应分别检查。

查看生产容器和最近日志的模板：

```bash
docker compose --env-file deploy/.env.production -f deploy/compose.production.yaml ps
docker compose --env-file deploy/.env.production -f deploy/compose.production.yaml logs --since 15m --tail 200 api worker admin-web
```

每次记录时间、环境、版本、现象和脱敏 requestId。不要输出 `.env` 内容或完整敏感业务附件。

## 常见故障处理

| 现象 | 首先检查 | 下一步与恢复判断 |
|---|---|---|
| 网页打不开 | 外部 HTTPS、入口路由、admin-web 容器 | 内部健康与外部访问分别确认；避免通过重部署掩盖域名问题 |
| API 就绪失败 | API 日志、数据库可达性、迁移版本 | 定位连接／结构原因，修复后 ready 成功；不自动 downgrade |
| 登录失败 | 会话、环境回调地址、第三方错误、账号启停 | 记录脱敏 requestId；不能靠重新授权绕过账号停用 |
| 飞书获取失败 | import run 状态、worker 日志、来源字段匹配 | 已导入／排除标记和人工日期不得清空；恢复后核对获取统计 |
| 通知未送达 | 业务事件、outbox 状态、worker、外发开关、接收人授权 | 站内生成与外部送达分开；不得删除去重记录后重发，真实补发单独授权 |
| 数量不一致 | 原报、确认结果、退回／作废台账、初始已发基线 | 按派工重建证据；先定位，不直接 UPDATE 数量字段 |
| 文件下载失败 | 业务访问权限、stored_files、OSS 对象和适配器日志 | 用有权限账号核验，不将私有桶改为公开 |

## 备份与隔离恢复

发布前备份与定时备份是两件事。已有首次 MySQL 恢复证据见 Issue #58；每日调度、告警和持续恢复演练仍需核实，不能因有脚本就视为已配置。

| 操作 | 现有入口 | 成功判断 |
|---|---|---|
| MySQL 备份 | `deploy/scripts/backup-mysql.sh production` | 受控目录存在非空压缩备份与 SHA256；记录源版本、时间和 schema |
| OSS 备份 | `deploy/scripts/backup-oss.sh production` | 受控备份与对象清单按脚本完成；数据库文件引用与备份对象可对应 |
| MySQL 恢复演练 | `deploy/scripts/restore-mysql.sh <backup-file> <protected-restore-env-file>` | 目标名必须以 `_restore` 结尾；需 `ORDER_TRACKING_RESTORE_CONFIRMED=restore-test-only`；校验和及恢复后业务抽查通过 |
| OSS 恢复演练 | `deploy/scripts/restore-oss.sh`，先按脚本检查参数和独立凭据 | 目标桶以 `-restore` 结尾；核对数量与内容，不覆盖业务桶 |

备份目录通过既有环境变量指定，脚本及参数见 [scripts](../../../deploy/scripts/)。演练前先批准隔离目标和资源；恢复完成后核对迁移版本、核心表计数、订单数量关系及附件内容。保存结果与耗时，再按批准范围清理临时资源。生产恢复属于另一次高影响操作。

## 生产应用回滚

前提：已批准目标旧版本，上一 release 目录、镜像、配置可用，且旧代码兼容现有数据库结构。先记录失败版本与实际 schema；若不兼容，停止直接回滚，制定数据恢复或前向修复方案。

在上一 release 目录中，确认受控配置已就位，将 `ORDER_TRACKING_DEPLOY_VERSION` 设为批准的旧标签，然后执行：

```bash
docker compose --env-file deploy/.env.production -f deploy/compose.production.yaml up -d --no-build --wait api worker admin-web
bash deploy/scripts/health-check.sh production
```

这里不运行迁移或 Alembic downgrade。健康后核对外部 HTTPS 与关键业务，更新受控版本／发布记录，保留旧镜像及备份。回滚命令不可用来自动撤销业务写入。
