# 发货自动收货开发计划

状态：待确认。更新：2026-10-10。工单：[Issue #240](https://github.com/kocotree/order_tracking/issues/240)。

需求及本次原型已确认；本计划与[专题技术设计](发货自动收货技术设计.md)一同待确认。确认后进入正式实施；当前未开始业务编码、服务器转换或发布。依据为[一期需求第4.3节及验收](../requirements/一期需求文档.md)，原型和现有本地检查见[交接](发货自动收货需求与原型交接.md)。

## 1. 工单、分支和依赖

沿用Issue #240，覆盖自动收货、连续修改、撤回期限、通知退役、历史转换及网页订单详情精简。以一个可独立验收的PR交付完整闭环，不为内部任务另建功能Issue。需求／原型提交保留，实施前核对当前main、已有分支及未提交修改，按根目录[项目规则](../../../AGENTS.md)选择独立分支或worktree并保护已有工作。

前置能力为 #44 核对快照及差额、#65 自主撤回、现有通知outbox和出货阶段事实记录。不得改动来源初始已发、来货出入、返修或阶段回填的业务口径。共享文件由同一执行者写入；本计划不安排并行Agent。

正式开工前记录当前提交、隔离测试库与受影响现有测试的基线结果；核对最新调用方，确认待删除接口没有新增共用依赖。原型页面逐项读取脚本、公共组件、样式和对应规范后再实施正式前端。

## 2. 实施顺序与可验证结果

每步先补相应失败用例，再完成最小修改；步骤共享同一Issue和PR。任务顺序按数据／服务依赖推进，最终一并发布完整流程。

| 步骤 | 交付内容与主要位置 | 完成证据 |
|---|---|---|
| 1 数据与转换预检 | `server/app/db/models.py`、Alembic迁移；专用历史转换命令及脱敏fixture；首次提交证据、系统快照身份和连续版本 | 空库及旧schema升级、模型一致；只读模式不写库；真实草稿差异／时点缺证时失败；历史样本转换前后对账与重复执行通过 |
| 2 保存即时生效 | `server/app/modules/shipments/service.py`：迁入差额、目标行、完成恢复、审计；新增保存幂等；旧确认函数退役 | 连续差额、净零实际修改、同值、0、跨归属、上限与非法值、同键异参、版本冲突、事务失败及并发用例通过 |
| 3 自动提交与撤回 | 首次提交／重提自动建快照；首次时间保留；撤回冲销当前数量并重置活动核对；计算 `canWithdraw` | 首次提交一次入账，修改后撤回正确冲销，同号重提正确入账；7天前／恰好7天／超过7天及重提不续期通过；退回互斥和阶段事实保持原口径 |
| 4 修改通知与旧通知退役 | `server/app/modules/notifications_audit/`：新修改事件固定差异；删除收货通知生成；旧事件、投递和重试终结 | 自动／历史不通知，同值不通知；连续修改逐次内容正确；旧事件在新消费者中无法发送，其他工厂状态通知不受影响 |
| 5 API与MCP契约 | `server/app/api/shipments.py`、`server/app/mcp/shipments.py`：PUT幂等、撤回资格、确认入口删除；MCP只读核对边界；清理表格专用查询 | 权限／CSRF／幂等测试通过，退役HTTP路径和MCP工具不存在；生成OpenAPI并更新两个客户端类型，无手工改生成文件 |
| 6 网页与小程序 | 发货详情持续保存、冲突／重试、退回只读；网页订单详情删关联表格及全部专用请求／跳转／样式；工厂详情按服务器资格撤回和自动收货提示 | 客户端组件／API测试、类型及构建通过；保留数量同步、原报下载及其他入口；两个小程序订单关联入口保持现状 |
| 7 完整检查与资料 | 扫描死代码／旧文案、相关测试fixture、交付正文、管理员／工厂手册及MCP能力说明 | 需求验收逐条映射到测试或人工检查；本地必要检查、原型对照、PR审查与完整CI、main最终提交完整CI分别有证据 |
| 8 授权发布与转换 | 不可变版本、维护窗口、备份、最终预检、schema升级、业务转换、数量复查及健康检查；小程序版本协调 | 经相应授权后执行；历史有效单收货状态正确、所有数量及原报不变、已有退回单限制保持、无补发收货通知；部署和业务验收分别记录 |

步骤1先用历史fixture验证转换方案，步骤2至5完成后联测同一服务实现；上线转换使用最终版本脚本。不得提前在正式环境试写，测试不得发送真实微信或飞书通知。

## 4. 检查与交付门

按现有工具链执行：

- 后端：`uv run ruff check .`、`uv run mypy app`、隔离MySQL下的相关 `uv run pytest`，完成必要后端回归及 `uv run python -m scripts.export_openapi --check`。
- 接口变更：按现有导出命令更新OpenAPI，两客户端分别执行 `pnpm generate:api`；核对生成差异与接口删除一致。
- 客户端：各自执行 `pnpm lint`、`pnpm typecheck`、`pnpm test --run`、`pnpm build`；检查原报下载、订单数量、保留导航和错误处理。
- 正式页面实施后，按[网页表格规范](../../shared/管理员网页端表格视觉规范.md)、[小程序复刻规范](../../shared/小程序原型复刻规范.md)完成实际浏览器／微信开发者工具原型对照。自动化和人工页面证据分别记录；需使用视觉工具时遵守用户当前授权。
- PR关联Issue #240，完整CI及审查通过后合并；核对main最终提交完整CI。合并和CI不授予标签或生产转换权限。

交付正文只在对应实现完成后更新实际行为；验收和发布记录仅填已执行结果。记录原型与正式页面任何有意差异，涉及可见业务规则时先确认。

## 5. 发布、数据转换与停止条件

发布准备时确认旧工厂小程序会以“存在收货结果”隐藏撤回入口：新版本必须配套更新该条件；上传、审核和发布各按授权执行，不能只发布后端就宣称工厂撤回体验已交付。旧版核对快照结构保持兼容，服务端期限与退回保护始终生效。

发布步骤遵守[技术设计第7节](发货自动收货技术设计.md#7-历史转换与切换)和[运维手册](../../shared/delivery/部署与运维手册.md)。维护窗口内暂停发货相关写入并停止旧API／worker，等待发送退出后备份；发布后保留入口限制，执行最终转换和只读对账，全部通过后恢复。记录备份、目标版本、转换清单、事务结果、旧通知退役数量、API／worker健康和未完成验收。

预检发现未生效核对差异、首次时间无法证明、未知状态、在途旧进程或对账不一致时，停止写入并报告具体单据／原因；不得猜测丢弃草稿、补数量或重发通知。转换事务失败不保留部分业务修改；schema与业务恢复分别核查，恢复数据或版本需明确授权。
