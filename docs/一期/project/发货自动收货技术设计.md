# 发货自动收货技术设计

状态：待确认。更新：2026-10-10。工单：[Issue #240](https://github.com/kocotree/order_tracking/issues/240)。

依据：[一期需求第4.3节及验收](../requirements/一期需求文档.md)、[已确认需求与原型](发货自动收货需求与原型交接.md)。用户已确认进入技术设计和开发计划阶段；本文确认后，按[开发计划](发货自动收货开发计划.md)实施。本次文档更新未修改正式业务代码或生产数据。

## 1. 范围与实现基线

源码核对基线：`fe4f4e0`；需求与原型本地提交：`d36326e`、`80219c7`。现有工厂提交已记入 `QuantityLedger`；收货保存只存草稿，人工确认追加差额；撤回会冲销有效数量、生成历史副本和撤回草稿，重提会改写 `submitted_at`。

本次复用 `ShipmentReceipt`／`ShipmentReceiptItem` 保存当前有效核对结果，复用现有数量台账、订单完成恢复、退回、原报导出和通知设施。删除人工确认步骤及专用代码，保留工厂草稿、撤回草稿和历史事实。管理员网页订单详情移除关联发货单区块；两个小程序的订单关联入口保持原状。

| 边界 | 设计结论 |
|---|---|
| 自动收货 | 首次正式提交与同号重提均建立已确认快照；只沿用提交的一次正向入账 |
| 编辑 | 仅有效、无退回的正式根单可在管理员网页编辑；数量、同厂同产品的订单归属和规格沿用现有限制 |
| 保存 | 每次保存立即生效，以前次有效快照计算差额；原报装箱记录不改写 |
| 撤回 | 首次正式提交未满7天、无退回、本厂有效根单可撤回；冲销当前有效数量 |
| 历史转换 | 有效未收货正式根单转为已收货；数量、退回、原报与既有已确认结果不变 |
| 排除项 | 不增删箱子或箱内项，不开放退回后编辑，不改变初始已发基线、来货出入或独立返修 |

## 2. 数据与身份

新增一条 Alembic schema 迁移：

- `shipments.first_submitted_at`：可空 `DATETIME(6)`，按现有 UTC 存储约定。个人草稿为空，首次提交写一次，撤回和重提保留。历史副本继承根单值，资格判断始终使用根单；`submitted_at` 继续表示本次提交时间。
- `shipment_receipts.saved_by` 允许空值。自动建立快照及历史转换由系统执行，`saved_by`、`confirmed_by` 均为空；不创建虚构用户。已有人工确认人和时间保持原值。
- 沿用 `DRAFT`／`CONFIRMED` 存储状态：有效正式单快照为 `CONFIRMED`，撤回清空活动核对明细后保留 `DRAFT` 头记录用于版本连续；工厂草稿与核对状态分别处理。

新自动快照版本从1开始；管理员实际修改、撤回重置、重提交重建均递增核对版本，禁止重置为旧版本。`saved_at` 记录最近快照写入时间；自动确认时间为本次提交时间，后续管理员修改不覆盖原确认人和确认时间。历史补建的确认时间记录转换时间，审计明确“历史转换”，不表示实际到货时间。

接口保留现有收货结构；系统确认的 `confirmedByName` 保持空值，不合成“系统自动确认”人名。两个小程序隐藏收货状态及确认人／时间，不展示系统确认文案；管理员网页保留收货状态及筛选。已有人工确认人、时间和历史审计在后台保留；最近修改人、时间及明细前后值通过现有修改审计表达。

历史首次提交时间按根单汇集可验证的首次提交证据：`shipment_submitted` 审计（含订单审计的 `shipmentId`）、正式历史副本的 `submitted_at`、首次提交事实的 `occurred_at`。采用最早的有效提交时点；无撤回或重提证据的单据可使用本单 `submitted_at`。禁止用草稿 `created_at` 计算期限；存在重提而首次时点无法证明、证据冲突或未来时间时，预检失败并列出单据，明确处理后再转换。

## 3. 数量、事务与版本

### 3.1 自动提交与重提

在现有提交事务内完成原报保存、单号、一次 `SHIPMENT` 入账、提交审计和提交通知，随后按本次原报全部箱内项建立 `CONFIRMED` 核对快照。自动收货不追加 `SHIPMENT_RECEIPT` 台账，不产生收货通知。

同号重提沿用现有原报历史副本与草稿复制逻辑；先移除引用旧活动箱内项的核对项，再替换原报内容并建立引用新箱内项的快照。保留核对版本连续、原单号和首次提交时间。提交／撤回／重提继续在事务内调用既有出货阶段事实记录；管理员核对修改及历史收货转换不伪造工厂提交事实，也不改变阶段冻结与原报回填口径。

### 3.2 管理员保存

保留 `PUT /admin/shipments/{shipment_id}/receipt`，新增必需的 `Idempotency-Key`；请求继续包含核对 `version` 及完整 `items`。

1. 校验有效管理员网页会话、CSRF和服务入口权限，锁定当前账号有权访问的正式根单。
2. 先核验已有幂等记录；新请求读取前次有效快照并校验状态与核对版本。拒绝历史副本、草稿、撤回、作废及已有退回的单据；版本冲突返回409，不保存部分项目。
3. 校验箱内项集合完整且不重复；数量为 `0..2147483647` 的整数；目标派工沿用同厂同产品、有效订单及规格规则，拒绝停用、删除或不合法目标。未变更归属归一为明确的原派工ID。
4. 分别按派工汇总前次与本次快照：`本次差额 = 本次汇总 - 前次汇总`。以现有 `_load_assignments(..., lock=True)` 顺序锁定受影响订单与派工；每个非零差额追加 `SHIPMENT_RECEIPT` 台账。100→95→98依次为-5、+3；跨归属分别扣旧、加新。
5. 复用原确认流程的目标 `ShipmentLine` 建立、订单审计和完成恢复逻辑。新增正数量目标行支持后续退回；零数量不创建违反正数约束的行，已被历史引用的行保留。有效展示与退回仍以 `_effective_line_quantities` 计算。
6. 更新核对快照，保持 `CONFIRMED`；核对版本和发货单版本同时递增，保存操作审计及修改通知事件。所有写入一起提交；失败则整个事务不生效。

箱内项归属或数量有实际变化，即使全单总数或各派工净差额为0，也更新版本、审计和通知；没有差额的派工不写零值台账。完全同值保存保持版本不变，不写业务审计、数量或通知。

订单以本次各订单净差额判断完成恢复：净减少且已完成时，沿用现有恢复为已发布、清除完成信息及完成恢复审计；不自动把增加后的订单标记完成。初始已发与人工覆盖规则继续由现有订单数量服务处理。

### 3.3 幂等与互斥

复用 `IdempotencyRecord`，保存作用域为 `shipment.receipt.save:{actor_id}`；请求哈希包含单据ID、预期版本及按箱内项ID排序后的完整归属和数量。同键同参数返回首次保存的结果快照，同键不同参数返回409；结果与业务写入在同一事务保存。无变化保存也记录该键的结果，保证重试稳定。同键重放不再次应用旧数据；客户端重放成功后重新读取当前详情。

保存先核验当前单据访问权限，再识别已完成的幂等请求；新的请求校验状态和版本。保存、撤回和退回共享根单行锁，状态检查在取得锁后执行；撤回与保存竞争时，后执行者看到新版本或新状态并拒绝旧操作。跨单修改共用现有按订单ID、派工ID排序的加锁顺序；幂等记录唯一键冲突必须整事务失败并按原请求查询结果，不吞掉数据库错误后继续写入。

提交、撤回与重提保留现有 `lock_facts` 在根单锁之前的顺序；保存不写出货阶段事实，无需取得该控制锁。事务内不进行微信、飞书或文件下载等外部调用。

## 4. 撤回与退回

撤回服务移除“已确认禁止撤回”分支，保留本厂权限、发货单版本、原因、幂等和已有退回限制。服务器使用同一次 UTC 当前时间判断 `now < first_submitted_at + 7天`，恰好满7天即拒绝；首次时间缺失直接报数据冲突。

撤回按当前有效核对数量冲销，复用订单完成恢复；历史审计保存原报与当前核对快照。活动核对项清空后，核对头改回 `DRAFT`、版本递增、清除活动确认人及确认时间，防止旧已确认结果泄漏到重提。撤回草稿沿用原报装箱和既有编辑权限，不把管理员的零数量结果强塞入要求正数的工厂装箱规则。

发货详情响应新增服务器计算的 `canWithdraw`，供工厂端展示按钮；`canEditWithdrawal` 继续表示可编辑撤回草稿，两者独立。`canWithdraw` 需本厂有效正式根单、无退回、未超期；管理员查询不授予工厂撤回权限。服务端每次动作重新校验，不能信任客户端布尔值。

退回继续按最新生效派工和可退数量处理。任一退回事件存在后，服务器与页面禁止装箱修改和撤回，不开发退回后的重新分配逻辑。

## 5. 通知及旧事件

实际修改保存产生 `shipment.receipt_adjusted` 事件，去重键含单据ID和核对版本。载荷固定保存修改版本、时间、操作人、箱内项修改前后归属／数量和按派工差额；消费时不从当前快照反推早先修改，避免连续保存后通知内容被后一次覆盖。

沿用工厂站内通知、差异展示及微信 `factory_status` 模板，表达“装箱明细已修改／数量调整”；复用现有收件人工厂权限复核和订阅授权处理。按箱或归属变化但净总数不变也通知。删除 `shipment.receipt_confirmed` 的产生、专用通知构建和发送逻辑；提交、撤回等其他通知保持现状。

历史未发送的旧收货事件及通过 `source_event_id` 关联的未发送投递记录统一终结，记录退役原因并清除租约，保留原记录；已发送通知及历史审计保留。新通知消费者在业务事件入口及投递入口均识别旧收货事件并终结，防止历史转换脚本执行前或旧任务重试时补发；这段代码仅承担旧事件退役，不保留旧通知生成逻辑。转换预检同时核对未完成事件、投递和后台重试任务。

## 7. 历史转换与切换

schema变更与业务转换分开：Alembic只增加兼容字段并放宽系统快照的保存人约束；`server/scripts/` 下提供本次专用转换命令，默认只读预检，显式执行模式才写入。预检通过明确选择现有列兼容升级前schema；执行模式要求目标schema已就绪。复用SQLAlchemy及现有事务工具，不新增通用迁移平台。转换命令在隔离库测试并纳入本Issue的PR。

预检输出符合条件的根单、已有已确认单、退回单、排除单、核对草稿差异、首次提交证据和旧未发送通知统计；不输出私人载荷和凭据。之前的43／61张及用户已处理3张只作为历史背景，执行时重新核对。

执行要求：

1. 先完成只读预检；尚未生效的核对草稿如有真实数量或归属差异，整次转换拒绝执行，列明并获得处理决定；空草稿或与原报相同的草稿可按原报建立快照。
2. 经发布及数据转换授权，按[运维手册](../../shared/delivery/部署与运维手册.md)安排维护窗口，暂停发货相关写入入口并等待旧API事务及通知发送退出，停止旧API和worker后进行备份。维护限制在新版本与转换核验完成前保持；不允许新旧写入进程混跑。
3. 使用不可变版本发布和schema迁移；新消费者已具备旧事件退役保护。转换命令执行时再次预检并锁定目标根单，在单事务内补齐可证明的首次提交时间、建立缺失的已确认原报快照、退役旧未发送通知并写系统转换审计。已有已确认快照不覆盖，草稿／撤回／作废／删除／历史副本不转换。
4. 前后逐项核对所有受影响订单的已发、未发及进度，台账记录／合计、退回事实和原报不变；已有退回单仍显示退回且不可改／撤回。转换不追加数量台账或出货提交事实，不产生新业务通知。任何数量或事实核对失败则事务失败。
5. 提交后独立只读复查，再恢复入口并核验API、通知和其他worker。重复执行只报告已完成，不重写已确认结果或重复审计；预检到提交期间发生数据变化则拒绝本次执行。

使用限定根单范围、明确前置条件与前后对账保证可复核。备份、转换清单和执行结果保存在受控运维目录；仓库仅保留脚本和脱敏测试。历史首次时间补齐覆盖曾正式提交的根单，包括已撤回根单，以保证其未来重提仍沿用原期限。

维护窗口中断保持入口限制，先核查事务、迁移和进程状态，依据备份及审计确定恢复动作。新数据产生后不能仅切旧镜像恢复旧语义；数据库恢复和版本恢复均需明确授权，不执行破坏性自动降级。

## 8. 验证与完成条件

核心服务、数量、权限和迁移按TDD在隔离MySQL验证。覆盖首次提交／重提不重复入账，100→95→98、同值、零数量、跨订单／规格、净零箱内变化、非法目标与数量，保存重试、同键异参、并发保存／撤回／退回，修改后撤回再重提及首次7天边界。

历史样本覆盖未收货、已收货、空草稿、真实未生效草稿、已有退回、撤回待重提、作废、历史副本、首次时点缺证与通知在途；验证原报清单／日汇总、台账及订单数量不变，重复执行安全，失败无部分业务转换。通知验证连续修改的不可变差异、同值不通知、旧业务／投递／重试任务不外发及其他模板正常。

客户端覆盖持续编辑与刷新、冲突和重试提示、退回只读、按服务器期限撤回，以及订单详情关联区块和专用请求消失、保留入口和数量展示正常。两个小程序验证收货状态／确认信息／系统确认文案消失，提交与重提不强调自动收货，撤回／作废／退回和修改差异保持；网页收货状态与筛选保持。接口删除验证HTTP路径和MCP工具确实退役、生成契约无残留。

本地检查、PR完整CI与审查、main最终提交完整CI、页面／小程序验证、生产切换、真实通知及业务验收分别留证。具体任务和停止点见开发计划。
