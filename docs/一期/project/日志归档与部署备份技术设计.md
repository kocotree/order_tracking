## 已确认口径与时间边界

- 五张指定表的可归档内容：产生后最近 30 天留 MySQL，超过 30 天上传私有 OSS，产生满 180 天到期。
- 每轮固定 UTC 时间 `now`，数据库时间按现有 UTC 无时区约定比较。展示包含 `created_at >= now - 30 days`，迁出使用严格小于；到期使用 `created_at <= now - 180 days`。运维输入日期明确时区。
- 未完成、失败待处理、外键引用、同步游标、防重及其他运行必需内容继续留存；保护判定不受 180 天限制。解除依赖后按原始产生时间重新判断。
- 已满 180 天的可清理数据库记录同样经过上传、读回核验和事务清理，之后再删除到期对象；重试不延长到期日。
- MySQL 定时和部署前备份共保留最新 7 份；OSS 快照最新 3 份。日志归档使用独立前缀与到期规则。
- Docker 程序日志保留既有每容器 10 MB × 5 文件配置。

## 依赖核查与处理边界

以下依赖已在模型与业务调用中确认，实施时补齐全部调用检索与回归测试。

| 表 | 已确认依赖 | 归档和保留处理 |
|---|---|---|
| `audit_logs` | 出货回填按 `shipment_withdrawn` 计数；`shipment_writeback.execute` 用于执行次数和中断恢复；发货撤回按 request、actor 查幂等；`shipment_submitted` 用于补写判断；自动订单同步按 request 汇总数量和错误详情 | 这些业务动作及未终结导入 request 对应记录完整保留。普通审计经依赖检查后归档整行并删除；未知业务依赖不得进入删除清单 |
| `order_import_runs` | 来源记录 first/last run 外键、来源游标 run 外键；`idempotency_key`；自动同步恢复依赖 `sync_result`，定时调度读取最近运行时间 | 活跃及失败记录完整保留。成功记录可迁出 `sync_result` 执行详情及错误详情，保留原行 ID、状态、时间、计数、request、幂等键和全部外键目标，避免重放及破坏游标 |
| `product_sync_runs` | staged variants 外键带 CASCADE；最新成功运行的 `success_cursor` 是增量游标；失败运行可继续读取 checkpoint | 活跃、失败、有暂存引用的记录完整保留；保留最新成功游标记录。其他成功且无依赖的记录归档整行后删除，不触发级联清理暂存数据 |
| `background_jobs` | `(job_type,dedupe_key)` 唯一键防重复；worker 恢复使用状态、租约和 payload；业务调度可能重新访问原 job | 仅已完成且不存在业务 payload 读取依赖的任务迁出 payload、last_error；原行及防重键、类型、状态、时间、attempts 保留。pending/running/failed 完整保留；逐 job_type 明确资格 |
| `outbox_messages` | dedupe_key 防重；通知 delivery 通过 source_event_id 读取原事件 payload 校验资格；回填历史准备读取发货 submitted/withdrawn 事件；部分重试和失败通知读取状态 | 仅确认终结且无待执行关联 delivery 的可归档消息迁出 payload 和错误详情。发货回填所需事件完整保留；未完成、manual_review 或其他待处理失败完整保留。原行、source_event_id、防重键、状态及计数继续保留 |

不改数量账本、订单、发货、收货、退回及返修事实，不清理 notifications 或登录记录。
运行信息保留不会允许旧日志绕过展示时间过滤。原始归档保存完整行，字段迁出仅发生在读回核验之后，不改变新日志写入内容。

## 部署迁移判断与备份

1. 在目标 server 镜像内运行独立迁移检查入口，使用 Alembic `ScriptDirectory`、`MigrationContext` 读取目标迁移图与数据库当前 revision；不解析 Alembic 控制台文本。
2. 目标为单 head，数据库为同一祖先链的单 revision，或确认为空的新库。数据库已有业务表但无版本表、多 head、未知 revision、版本领先或分叉、连接失败均停止。
3. 结构化检查结果只允许 `current` 或 `pending`；未知、空结果及非零返回码停止。`pending` 执行 MySQL 备份成功后才迁移；`current` 跳过备份和迁移。容器更新继续遵循原健康检查流程。
4. `backup-production.py` 提供明确的 MySQL 单项模式，部署只调用该模式；每日任务保留独立的 MySQL 和 OSS 备份入口，沿用部署 flock。
5. 新备份写入临时名称，完成命令、压缩读取和摘要核验后才发布成功名称与校验文件，再清理同机制成功备份。失败产物不占保留名额，也不能触发清理。
6. 清理严格匹配已管理的命名与成功标记，拒绝符号链接和异常类型；MySQL 7 份、OSS 3 份分别清理，人工历史文件不动。归档 OSS 前缀不参与快照份数计算。
7. 备份沿用现有受控配置读取方式，不扩展其配置语法；新归档入口使用已安装的 Settings/dotenv。配置与外部命令内容不得写入日志。

## 归档事务与恢复

- 独立运维 CLI 和定时入口，不挂在 API 启动、worker 主循环或部署过程。生产启用另行授权。
- 使用 MySQL 命名锁实现跨进程互斥；限定批量与总处理量，每个批次提交后可重新执行。
- 新增专用归档清单表，保存来源表、原始主键、原始产生时间、对象 key、格式版本、SHA-256、字节数、状态、到期时间；来源表与主键唯一。只保存检索和恢复所需元数据，不复制正文。
- 需要留防重原行的表增加归档完成标记，用于避免过期清单删除后再次归档已迁空的正文；普通审计和可删除同步记录不留空壳。
- 每条记录对应一个 gzip JSON 对象，路径限定在版本化专用前缀，含来源表、原始日期和主键。精确按记录到期，避免混合日期文件提前删除或延迟保留。
- 上传前在事务中锁定候选、重新核查状态及依赖并建立待处理清单。上传完整原始行，保存 UTC 时间和格式版本，使用标准 JSON/gzip 库；不得自行解析成熟格式。
- GET 读回后校验摘要、字节数、版本、原始主键、时间及完整内容。再次锁定来源行，核对原始内容与依赖未变化，才在同一数据库事务中执行规定的删除或字段迁出并将清单置为完成。
- 状态或内容变化则本轮不清理；废弃上传对象按清单恢复流程删除后重新生成，禁止用旧快照覆盖新状态。核验失败保留数据库原文并报告错误。
- 上传成功但未提交、中途断线、数据库提交失败均能通过清单定位并核验重跑；数据库提交成功后重试不得再次修改业务内容。
- 到期仅删除本清单拥有且已完成的对象；删除失败保留清单重试，确认对象不存在后清理清单。待处理清单先恢复处理，禁止先删其唯一归档副本。
- 归档对象强制私有；使用独立受控归档凭据与前缀权限。API 凭据不增加归档删除权限。完整原文不打印到执行日志。

## 查询、页面与运维检索

- 通用审计、订单审计、候选审计、发货操作记录及面向用户的运行记录入口逐一增加 30 天过滤；分页数据与总数复用同一截止时间和条件。
- MCP 继续调用现有业务查询服务，复用相同时间过滤、身份权限与脱敏。内部任务恢复、幂等、回填计数、源数据游标读取不加展示过滤。
- 网页订单和发货操作记录、小程序发货操作记录等现有日志区域增加已确认文字“仅展示最近 30 天的操作记录”，不新增按钮或页面。旧的空列表合成提交记录需遵守同一时间边界。
- 发货 `returnEvents` 仍为业务事实；若在“操作记录”区域展示，应仅对该区域按事件时间筛选，不能影响退回数量与剩余可退数量计算或其他业务入口。
- 运维检索 CLI 必须指定表及时间范围，可按原主键定位；先查清单，再 GET、核验和解压。输出沿用审计脱敏规则；原始正文仅在明确受控恢复流程中可读取，不增加客户端 OSS 查询。
- 交付权限、命令参数、失败恢复、定时入口与启用前检查说明；真实账号、Bucket 和数据库年龄分布不写入仓库。
