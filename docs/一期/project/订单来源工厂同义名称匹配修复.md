# 订单来源工厂同义名称匹配修复

2026-11-28，Issue #263。用户已明确确认两组同厂名称，并要求用于后台同步且保留已有派工和发货记录。沿用[来源增量对账设计](订单来源明细增量对账设计.md)的事务、唯一采购身份和执行事实保护；本修复不放宽跨厂或采购归属变更规则。

## 已确认范围与验收

- `千与`与`邯郸千与`、`昱斌`与`昱斌服饰`分别是同一家工厂，双向识别。
- 新订单来源匹配、未派工来源更新及已派工完整对账复用同一个匹配入口。来源文字与原始资料保留，不批量改名。
- 已派工行继续引用原`factory_id`和`assignment_id`；仅同厂名称变化不新建、撤回或迁移派工，不改变下单数、初始已发、合同出货时间、发货/装箱/收货、数量台账、来货出入及冻结快照，不重复派工通知。
- SKU、采购主/子单身份、人工覆盖、暂停、完成和删除保护保持原规则。真实跨厂或采购归属变化不能被别名匹配绕过。

## 技术实现

在`OrderImportService._match_dependencies`的工厂查询中使用有限同义名称集合。两组已确认名称各自形成一个集合，其余名称仅使用自身，不进行前后缀、地域、相似度或其他模糊推断。

对集合查询启用的工厂档案，最多读取两条：仅当恰好一条时返回该档案，并继续检查其启用工厂账号。没有命中或同时命中多个启用档案均沿用`FACTORY_NOT_MATCHED`，已有派工对账沿用冲突保护；不按查询顺序或名称精确程度猜选，不合并档案和账号。

已派工完整对账使用解析出的同一工厂ID建立采购身份索引，保留行通过原有ID校验后接受来源记录。其历史assignment及固定基线不进入未派工更新路径。来源读写接口、数据库结构和客户端无变化，也不引入新的可见状态或权限。

## 开发计划与验证

1. 在独立本地MySQL先复现双向别名导入/派工失败、未派工匹配失败以及带真实发货和来货出入的完整对账失败。
2. 实现有限唯一匹配；验证多个启用别名档案、停用工厂、无启用账号及未知名称仍被保护。
3. 通过完整自动同步入口连续运行两轮，比较已有assignment、发货、装箱、收货、台账、来货出入、冻结事实和派工事件，确认数据、工厂可见数量及通知不重复。
4. 运行相关原回归、后端静态检查和OpenAPI一致性检查，通过PR完整CI。发布新版本标签仍须独立明确授权。

测试数据仅使用虚构订单、SKU、数量和账号，真实业务订单及来源资源标识不进入仓库。生产库不用于回归测试。
