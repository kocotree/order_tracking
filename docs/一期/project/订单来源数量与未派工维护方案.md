## 1. 当前问题与证据

当前代码基线为 `main` / `605dd19f452b96cb175a4ccfb4b76b56dd15bbb8`，起始工作区干净。未在本轮刷新远程 CI、共享测试或生产状态。

- `order_import/service.py` 根据已发量计算精确95%门槛；候选和手动“更新未派工明细”使用同一数量来源，派工只使用系统当前已保存值。

- `orders/dispatch.py` 以唯一跟单人员及首次派工锁定校验阻止不同跟单人员明细共同派工；列表筛选、到期提醒及发货相关通知也使用单人字段。
- 当前待导入/来源草稿日期有人工保护；订单详情工厂和已发量只读。现有 `AuditLog.changes` 可存修改前后值，候选操作已有日志目标类型，不需要新日志系统。

## 3. 技术实施方案（Issue #145 脱钩边界已确认）

### 3.1 一次匹配与数量计算

在现有来源读取链路加入采购数量补全，首次获取、读取指定来源记录及手动更新未派工明细共用它。更新确认直接应用该次预览快照，派工不调用该来源读取链路。应用服务器只读取飞书下单表并调用受控的聚水潭只读 API，不直接访问飞书采购明细底表，也不依赖 Agent 插件运行；插件仅用于验证。无需新增定时任务、持久化采购仓库或第二业务数据库。

1. 飞书下单表提供“采购子订单号-人工确认”“采购子订单号-映射”和最终“采购单号”；业务字段通过环境配置的 `field_id` 解析当前字段名并校验类型，字段改名不改变绑定。
2. 按人工确认优先取唯一子订单号，人工为空时只接受唯一自动映射；与唯一采购单号组成 `poi_id + po_id`。新来源缺少唯一关联时不猜测；已有订单在下单表为空或多匹配时复用 MySQL 已保存关联，有效的新关联覆盖旧关联。
3. 对本次读取的采购主单去重后每批最多20个查询全部相关分页（聚水潭采购接口限制）；使用 `poi_id` 精确定位明细。一次操作内复用同一主单结果，不逐行重复查询；不建设跨任务缓存。
4. 精确匹配后直接使用单据明细 `qty` 作为下单数量、`inQty` 作为已发数量，来源未发为 `qty - inQty`；`return_qty` 不参与本需求数量计算。库存 `purchase_qty` 为SKU范围的查询结果，不直接分配到各订单。
5. 严格校验数量及匹配唯一性。其他缺失/非法量、映射多值、缺主单、子单不存在或来源SKU不一致时，不生成猜测数量。保留已有接受数据，明确失败；新来源未知数量沿用宽松导入和派工校验机制。
6. `inQty` 大于 `qty` 时保留真实超发，页面未发下限为0，不截断或伪造已发数量。

沿用现有飞书增量发现和整单回查范围，不增加“聚水潭一变化就主动扫描全部飞书订单”的能力；来源刷新对指定明细重新查采购数量，即使飞书文本本身未变。首次获取的95%筛选使用补全后的来源数量，已保存人工覆盖不能被新获取覆盖。

飞书下单表及字段真实资源标识只从运行环境受控配置取得，仓库不记录 Base Token、表/记录/字段 ID 或带资源标识的内部链接。复用现有聚水潭认证、签名、限流和重试机制，不复制整套认证或引入通用网关。服务器现有凭据是否具有采购查询权限须在获准环境最小调用验证，插件成功不能代替该验证。

### 3.2 原始来源与生效值

保留现有 source record / `accepted_raw_fields`，其中数量来源改为采购查询快照，至少保留匹配子单/主单、SKU、采购数量、已入库数量及读取时间。原始值只用于核对，手工修正不篡改该快照。

差异哈希只包含稳定业务值，不包含本次查询时间、请求ID等每次变化的元数据；采购数量相同的重复读取不得生成无意义变化或让派工预览永久失效。

候选按稳定来源行保存工厂、日期和已发数量三项人工覆盖；未发输入只按下单数量反算同一个已发字段，不新增独立数量字段。复用/扩展已有日期覆盖存储；来源草稿使用显式字段覆盖标记和现有生效字段，避免把清空日期、0已发或与原值相等的人工输入误判为“未修改”。覆盖只保护被保存的字段，其他字段继续更新。候选导入时将覆盖、原始快照和日志关联带到 `OrderDetail`。

保存接口校验普通管理员权限、候选/订单和明细归属、订单/明细版本及未派工状态。工厂严格使用系统 ID；已发为非负整数且允许超发；日期保持人工直接使用、来源减四天一次的既有规则。校验、覆盖、生效值、汇总、版本和日志同事务保存。失败保持已有值；无实际变化不重复记修改日志。

复用现有 source preview / dispatch preview：差异计算区分原始来源变化和生效值变化，手工覆盖不会被确认来源更新清除。source preview 仅读取一次外部来源，确认使用服务器快照；dispatch preview / confirm 只读系统值。前端保存与刷新/派工互斥，旧请求不能覆盖新页面。派工固定当前生效已发为基线；后续仍按基线＋系统有效发货计算，冻结明细不再外部重算。

### 3.3 多名跟单人员

保留来源明细人员，按全部明细的稳定顺序去空去重汇总；首次派工不能只拿本批所选明细来决定整单人员。移除“不同人员＝不一致”的拦截，保留既有人名合法性与所选明细缺失人员校验。不开放跟单人员手工编辑，不把姓名拼接字符串用于身份匹配。

建议在订单/候选保存JSON人员数组，查询输出显式集合；历史单人转换为单元素数组，没有可靠来源的历史订单保留原人员。筛选用精确成员判断，数据库筛选、计数、排序后再分页；排序使用稳定的人员集合排序键及订单编号作为并列键。来源刷新维护未派工明细汇总，已派工明细的人员快照继续保留，不能通过刷新改写历史执行归属。

查遍 `Order.tracker` / `candidate.tracker` / `source_tracker` 的所有消费，包括手工订单、列表、合同/导出展示、管理员小程序类型及通知。单人旧响应可暂作兼容输出，但新业务不能依赖只取第一个人的旧字段。共用API类型的兼容调整必要；小程序新增编辑入口或独立视觉改版不在本次确认范围。

到期提醒、已有发货相关跟单通知均按订单人员集合查当前启用管理员，接收人ID去重；D-3特别关注管理员仍沿用既有规则。延迟消息发送前也必须按集合复核，不只改变首次生成通知的查询。节点、渠道、工厂范围和账号权限不扩张。

### 3.4 迁移与已有数据

采用增量迁移保留执行ID、数量账本、合同快照、人员和原日志。历史单人可确定转换；存在多来源的正式订单由已有接受明细去重汇总，不自动重读飞书覆盖历史人员。升级后第一次获取完整重读待导入来源，使旧候选按明细重新汇总多人跟单并采用新数量规则；不批量重算已派工/已完成数量。

任何真实数据修复、采购权限验证、共享测试/生产迁移或历史批量回填均须独立确认具体范围；本轮未读取生产，也不能声称不存在异常历史。

## 4. 实施顺序与检查（计划待确认）

本次一个功能Issue统一跟踪订单资料维护，不预先建立更多框架或重复台账。开发时保持一个可验收PR，内部依次完成：

1. 采购只读补全与统一来源数量：适配器检查和精确95%门槛先建立失败用例，再实施。
2. 候选→来源草稿人工覆盖、未发联动输入与三字段保存：隔离MySQL事务测试覆盖转入、刷新、日志和派工冻结。
3. 多跟单集合打通导入、派工、列表查询及通知；维护生成API类型和必要兼容。
4. 逐页原型确认/制作后实现已确认网页内容，实际浏览器与原型对照，再完成整体回归、迁移检查和发布前核对。

执行正式代码前确认具体技术设计和开发计划，按已确认 Issue → 独立分支/Worktree → 本地检查 → 提交/PR → PR完整CI与审查 → main最终CI。资料阶段不因建票自动开始编码或发布。

| 必测行为 | 通过标准 |
