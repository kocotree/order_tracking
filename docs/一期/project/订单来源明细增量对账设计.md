# 订单来源明细增量对账设计

2026-11-27，Issue #260。用户已确认新增唯一来源明细自动补齐，并允许已有发货的工厂拆分在下述校验全部通过后自动调整。

现行每20分钟自动同步只为新订单导入来源，并只更新已有未派工明细。此次将完整来源发现用于已导入草稿和已开始派工订单，修复新增规格遗漏与工厂拆分未同步。沿用 MySQL、现有派工服务、版本、幂等和通知机制。

完整发现保留各订单的来源记录集合。比较已接收资料后仅为来源集合或资料变化的已派工订单安排对账；未派工订单继续读取采购数量，避免重复逐行读取全部已派工订单。旧的运行中任务允许按原持久化阶段完成，下一轮进入新流程。

新增来源记录按来源作用域及记录 ID 唯一追加。已导入订单不重新应用新订单95%获取门槛。资料不全的新增行沿用宽松草稿规则，保存问题并等待既有派工校验通过。人工覆盖、人工撤回暂停、已完成、删除和排除保护继续生效。

已有派工优先以持久化采购 `po_id + poi_id`、SKU 和工厂 ID 唯一匹配当前来源保留行，不能只按旧来源记录 ID 认定工厂。来源重绑与追加在同一订单事务完成，重复或歧义身份使本订单回滚。

已有发货的工厂拆分要求原工厂仍有明确来源行、目标数量足以承接当前有效已发量、采购关联唯一、同 SKU 总量守恒且无人工覆盖冲突。原 assignment、初始已发基线、发货、装箱、退回和数量台账保留原工厂归属，仅调整获准的下单数量。新工厂由其精确采购明细建立初始已发基线，不能再次把原工厂系统发货算作来源已发。

原始“下单数”变化也作为拆分校验信号，不能被采购补全后的旧数量掩盖。拆分SKU的未派工目标无论本轮新追加还是原已存在，都必须有精确采购主／子单、SKU对应及有效初始已发基线；缺少采购的默认0不得当作可自动拆分依据。“下单明细ID”变化参与发现比较，并触发身份冲突保护。

已有来货出入的保留行必须保持工厂、SKU 和采购主／子单身份不变；原记录与台账关联不迁移到新工厂。历史合同、箱贴和已冻结出货阶段快照保留原版本。后续回填仍映射原工厂对应采购来源行，歧义时停止。

来源删除、SKU归属无法确定、来源数量不足、数量不守恒及已有执行事实的整行改厂等情况进入可追溯冲突，继续由已授权的差异检测任务筛选并提醒。没有执行事实的工厂变更也先要求唯一采购及来源对应，禁止按名称猜测归属。

网络读取及商品补齐在业务写事务外。写入锁定订单并重验版本、来源及执行数量，原子提交数量扣减、来源重绑和新增未派工明细。随后复用自动派工；对账提交后退出的任务重试只派工仍未派工的明细。单订单失败隔离，失败订单本轮不派工。

备选方案为新增明细自动补齐、已有发货拆厂由管理员逐次确认。用户选择安全校验通过后自动调整，以减少重复人工修复。数据库字段和客户端页面沿用既有结构，未引入新的价格、状态或权限。

验证采用匿名化数据及独立本地 MySQL，覆盖新增明细、全单派工、新单95%边界、采购独立变化、工厂拆分及来源重绑、历史发货与来货出入保留、冻结回填快照、人工保护、冲突原子回滚、并发及重试。按现有 PR 与完整 CI 交付；发布和生产批量操作独立授权。
