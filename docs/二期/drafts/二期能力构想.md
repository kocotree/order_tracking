> **版本：** V0.3
>
> **更新日期：** 2026-09-08
>
> **状态：** 需求建设中。方向已经确认，具体业务口径及验收标准待评审。
>
> **范围声明：** 本文不替代一期 V1.59，不是二期完整需求、原型、技术方案或开发授权。后续按[二期需求建设计划](../project/二期需求建设计划.md)完成确认门。V0.1 的仓库员工、仓库小程序、扫码与箱贴实施路线已取消，历史内容由 Git 保留。

## 1. 已确认方向

2026-09-08 用户确认：

1. 内部同事向飞书机器人发送来货出入资料，由系统识别、匹配后登记到 MySQL；不建设仓库人员使用入口。
2. **匹配无歧义时自动正式登记并影响对应订单进度，异常再人工处理**，不要求每笔正常结果人工确认。
3. 按订单明细回填现有飞书表的每周出货列；取消每周、每个工厂、每个 SKU 的汇总导出，不新建周汇总 Base 表。
4. 月账单首版只汇总正常来货、来货出入、质检/客退等数量分项。用户最新确认暂不加价格，聚水潭结算取价、金额计算、费用和税费不纳入本次需求。
5. 工厂分析与库存预警保留原构想：月度工厂复盘、每日库存风险，确定性规则计算指标，AI 解释和起草建议。

MySQL 8.0 继续是正式业务事实库，OSS 保存受控原始凭证。飞书机器人通过后端登记，Base 是指定结果的协作出口。二期回填属于新增的有限输出能力，需要在二期正式需求中明确覆盖一期“上游只读、不回写”的对应边界，不改变一期现行约束。

## 2. 当前基线与复用边界

当前一期 V1.59 和已合并的 Issue #44 已支持管理员网页按箱核对、保存草稿、整单确认收货。确认数量减原报数量形成收货差额，事务内追加一次数量变化；原报数量和发货清单保留，确认后锁定。旧版构想关于“一期不支持收货确认”的描述已过期。

现有流程仍不录入实际到货日期，不支持用一条模糊差异消息直接确认整张发货单。收货确认和月账单差异可能指向同一件事，必须关联、去重，不能各扣一次。

当前已有飞书身份、只读订单来源、出站通知、私有附件、任务与审计基础。消息接收/识别和周报写 Base 不是已有功能；不能直接冒用网页 Cookie/CSRF 接口完成机器人操作。需在技术阶段设计业务应用身份映射、事件认证与去重，再复用业务服务。

质检单返修仍不关联原订单或正常发货批次，不能直接计算真实批次次品率。初始已发数量只有导入基线，没有逐笔发货日期，不能拆成虚构的历史周出货。

## 3. 飞书机器人来货出入登记

### 3.1 业务流程

内部同事发送资料 → 保存原始凭证 → 识别结构化内容 → 严格匹配与校验 → 无歧义自动正式登记并更新对应订单数量／异常交人工处理 → 可查询登记结果和来源。

文本、图片及聊天截图是首版待评审的输入形式；私聊机器人还是群内 @、是否支持 Excel 或语音、跨消息补充材料如何归并，需结合样本确认。发送消息属于使用入口，不意味着机器人拥有全部管理员权限。

### 3.2 自动登记的候选判定

“无歧义”必须在需求评审中定义为可验证条件，而不是只看模型置信分数：

- 发送者是已启用且获准登记的内部人员，归属与权限可核实；
- 工厂、SKU 及受影响的订单/派工明细唯一匹配，数量、正负方向、业务类型和账期完整；
- 原文、图片中存在相应证据，不由模型补造日期、采购单或入库单号；
- 需要来源单据的场景能唯一匹配，且没有失效来源、相互矛盾或已确认数据冲突；
- 同一事件重投不重复登记，同一凭证重发/跨渠道录入可识别；
- 同一少货事实如已在收货确认中生效，只建立关联，不再次生效。

不满足时保留识别结果并转异常处理。人工修正后重新校验，正式记录更正保留原值、修正值、操作者与原因。异常处理是在飞书卡片还是网页完成，后续原型阶段确认。

### 3.3 建议登记字段

| 字段组 | 候选内容 |
|---|---|
| 业务归属 | 工厂、SKU、名称/颜色规格快照、差异方向、差异数量 |
| 时间 | 业务发生日期、结算月份、登记时间，三者分别保存 |
| 来源 | 采购单号、入库单号集合、系统订单/派工及发货单/箱明细关联（影响进度必须明确归属） |
| 凭证 | 原始消息/附件关联、识别文本、匹配结果、发送者及登记渠道 |
| 处理 | 待识别、待处理、已登记及更正关系；具体状态机待确认 |

多货记正、少货记负，符合账单样例。日期未知、采购单未知、一个凭证对应多个入库单均需明确处理，不按登记当天或第一张入库单自动填补。

### 3.4 与订单数量的关系（方向已确认）

用户确认来货出入正式登记需要影响对应订单进度。二期不能仅登记一份账单差异而不调整订单；无歧义自动登记的判定必须包含订单及具体派工明细的唯一归属。

多货/少货如何追加到有效已发数量、是否改变订单完成状态，以及原发货单已经确认、退回或作废时怎样处理，需在正式需求中逐项明确。局部差异登记不默认等同于整张发货单收货确认，不能因为影响进度就把其他未核对明细标为已收货。无系统订单、多个候选订单或无法关联发货明细时，不能为了自动登记而伪造来源或任意分配，转人工处理；是否允许先记账单待关联后生效需另定。

同一差异只允许生效一次：如已由网页收货确认计入有效数量，机器人识别后建立关联，不再次增减；机器人先登记后再进行网页收货确认时，也须识别已经生效的差额。并发提交、更正和撤销需要有一致的数量与审计结果。

月账单与订单共用可追溯的差异事实。若正常来货基数已包含差额，月账单不能再加一遍；若基数保留原报，可单列差额一次。已有确认记录、重复转发、历史无系统订单和确认后发现错误分别列验收样例。

## 4. 工厂履约与质量分析

### 4.1 分析节奏

工厂履约和质量分析以月度复盘为主，每日或每周可补充严重延迟和高风险异常。

候选指标：

| 指标 | 候选口径 |
|---|---|
| 数量及时率 | 截止合同出货时间已有效发货数量 ÷ 应发数量 |
| 整单及时率 | 合同出货时间前全部发完的订单数 ÷ 当期到期订单数 |
| 来货差异率 | 多货和少货绝对数量 ÷ 验收实收数量 |
| 次品率 | 质检次品数量 ÷ 同口径质检实收数量 |
| 报废率 | 报废数量 ÷ 次品数量 |
| 返修完成周期 | 返修完成时间 − 仓库退回时间 |
| 重复问题率 | 同工厂、商品/规格和次品原因的重复出现情况 |

上述口径均为候选。特别是次品率、来货差异率和返修完成周期，需先补齐验收批次关联、质检分母和明确完成时间后才能正式计算。仅收集差异消息不能证明全量验收分母；没有数据时显示不可计算，不填 0。及时率按合同截止时点的历史事实计算，不拿今天调整后的数量倒推当时履约。

### 4.2 后端处理原则

1. 定时任务按日和月生成不可变的指标快照；
2. 指标模块按已确认公式计算比率、同比/环比和工厂排名；
3. 规则模块识别连续延期、次品率上升、同类原因反复出现等可证明异常；
4. AI 只接收结构化指标、变化幅度和证据标识，生成原因解释和改进建议草稿；
5. 管理员确认后才将建议标记为正式报告，报告保留公式版本、快照时间、模型版本、提示词版本和证据链接。

### 4.3 管理员网页候选页面

管理员网页候选新增“数据分析”一级导航：

- **经营概览**：日期筛选、工厂比较、趋势和异常概览；
- **工厂分析**：单个工厂的交付、来货差异、次品、返修、报废和问题原因趋势；
- **AI 月报**：月度问题、证据、建议草稿、人工确认状态和导出。

首版不以自由聊天框为核心，先确保指标、证据、报告和下钻链路可验证。

### 4.4 Agent 升级边界

只有当系统能够按周期读取指标、根据风险选择进一步查询、跟踪建议是否执行，并经人工确认后创建协同任务或起草消息时，才视为向 Agent 转变。

首版定位为“AI 分析助手/月报工作流”，默认只读，不自动评罚工厂、修改业务数据或对外发送通知。

## 5. 聚水潭库存风险与催货建议

### 5.1 分析节奏与目标

库存风险以日分析为主，与工厂月度质量复盘分开：

| 能力 | 频率 | 目的 |
|---|---|---|
| 库存风险与催货建议 | 每日 | 识别当天应优先跟进的 SKU、采购单和工厂 |
| 工厂交付异常 | 每日或每周 | 识别可能延期的订单和持续不改善的异常 |
| 工厂质量与履约分析 | 每月 | 复盘及时率、来货差异、次品、返修和报废 |

每日库存报告不应等同于“库存低于固定数量就报警”。候选计算需组合当前库存、销售速度、待处理订单、采购进度、计划交期、实际入库和历史交付表现，生成未来 7/14/30 天风险。

### 5.2 聚水潭只读数据口径

| 数据对象 | 用途与约束 |
|---|---|
| 实际库存 | 使用库存明细的 `qty`，按 SKU 展示并去重后汇总；缺失数量不当作 0 |
| 销售订单 | 用于构建受控时间窗口内的销售速度、季节性和订单需求 |
| 采购单 | 使用采购数、已入库数、退货数、剩余未交数、计划交期和工厂/供应商信息 |
| 实际采购入库 | 实际入库数量和入库时间必须来自采购入库记录，按 `io_id` 去重，按实际入库时间使用 `date_type=2` |
| SKU 和款式资料 | 使用 SKU 连接库存、销售、采购与入库；款号用于管理层的款式汇总 |

实际库存、锁定量、订单占有数和仓库待发数应分开展示。在没有正式确认业务计算口径前，不自行相减并声称得到“可用库存”。

### 5.3 每日处理流程

1. 在固定时点只读获取目标范围内的聚水潭数据，记录查询时间、页数、数量和字段覆盖；
2. 去重、校验空值和异常值，保存不可变的每日数据快照；
3. 在已确认口径下计算 SKU 未来 7/14/30 天需求、库存覆盖天数、预计缺货日期、在途覆盖和交期风险；
4. 用规则或统计/机器学习模型生成风险等级和催货排序；
5. 大模型只基于风险结果、采购单和入库证据解释原因、组织日报和起草催货建议；
6. 第一阶段只展示和导出，不回写聚水潭、不自动创建任务、不自动向工厂发送催货消息。

正式分析必须先确定 SKU 覆盖范围、时间窗口和字段字典，再通过固定快照、历史回测和人工复核评估误报与漏报。

### 5.4 管理员网页候选页面

“数据分析”下候选增加：

- **库存预警**：SKU 风险列表、款式汇总、库存/销售/在途下钻、风险变化和筛选；
- **每日分析**：高风险 SKU、新增风险、已解除风险、预计缺货、交期冲突和今日建议跟进清单；
- **采购/催货证据**：查看相关采购单、剩余未交、计划交期、实际入库及历史变化。

日报优先展示与前一份快照相比发生变化的高风险项，避免每天反复罗列全量正常 SKU。

### 5.5 日报候选结构

每条高风险记录至少包含：

- SKU、款号、商品名称和颜色/规格；
- 原始库存、锁定/占有/待发等已定义字段；
- 7/14/30 天需求与预计缺货日期；
- 相关采购单、采购数、剩余未交数、计划交期和工厂/供应商；
- 经去重的实际入库数量和入库时间；
- 风险等级、触发规则、与前日差异和建议动作；
- 查询范围、截止时间、数据快照和公式版本。

### 5.6 向库存与催货 Agent 升级

当日报的数据口径、风险计算和历史回测稳定后，可分阶段增加：

1. 针对高风险 SKU 自动选择需要深查的采购单和实际入库记录；
2. 生成指定负责人、建议截止时间和证据链接的待办草稿；
3. 次日重新检查风险是否改善，区分未处理、已缓解和已解除；
4. 经人工单独确认后，再创建内部待办或起草催货消息。

即使升级为 Agent，也默认保持对聚水潭只读，不自动修改库存、采购单或入库单。

## 6. 现有 Base 每周出货回填

### 6.1 实际字段核验（2026-09-08）

只读核对用户指定的“生产部--下单表以及成品进度表-外协填写”，共 91 个字段，指定视图名为“总表（误删）”。表内有 33 个期间出货数字字段，本轮未读取业务记录或执行写入。

| 现有字段 | 类型与用途 |
|---|---|
| 订单编号 | 文本，参与定位订单明细 |
| 工厂、商品名称 | 选项字段，匹配时仍须核对唯一性和组合 |
| 产品颜色&规格 | 文本 |
| 产品编码 | 数字；不能仅凭名称就当作系统 SKU，需核对编码语义 |
| 产品编码（他是唯一码）、下单颜色编号、款号 | 查找引用，需确认与本地 SKU 的对应关系，不写入 |
| 下单明细ID | 自动编号；真实记录标识及现有导入来源关联需要在技术阶段核对 |
| 26.9.1-9.6出货、26.9.7-9.13出货等 | 数字，目标可写列 |
| 出货总数 | 公式，汇总现有期间出货列，不直接写入 |
| 未出数量、出货进度 | 公式，分别依赖下单数和出货总数，不直接写入 |

回填出货列会间接影响未出数量、进度和引用它们的看板/提醒。只核实字段结构尚不能证明订单行、SKU、权限和历史接管已满足自动写入要求。

### 6.2 回填粒度

只回填现有表的周出货列，不提供每周 × 工厂 × SKU 汇总导出。

**现有表回填：** 每个期间 × 来源订单明细行。不能把跨订单合计填到多行；同厂同 SKU 也不能省略订单归属。优先研究已有来源记录关联，缺失或多匹配时不写入。

现有列并非统一周一至周日：例如“26.8.24-8.31出货”“26.9.1-9.6出货”按月拆段，“26.4.6-4.19出货”覆盖两周，“26.7.6-7.10出货”和“26.7.11-7.12出货”还拆分一周。回填应使用明确日期区间映射，并检查区间重叠和遗漏，不能只按列名中的周序号推断。

### 6.3 待确认的输出与接管规则

1. 回填是否沿用现有列实际期间，以及新期间列的维护方式；时间统一按上海时区解释。
2. 归期用发货业务日期、确认日期还是实际到货日期；建议普通出货使用发货业务日期，实际到货不可由确认时间代替。
3. 数量用原报出货、确认数量还是扣退回后净数量；跨周确认、退回和作废如何调整原周或本周。
4. 正常出货和返修发回是否分项；初始已发基线和未导入订单如何保持原有人工记录。
5. 从哪一期、哪些订单行接管；已有人填写的目标值如何核对，系统值与人工值冲突时由谁处理。

候选同步方式为按来源行与期间重算目标值后更新，而非每次累加。需要保留上次写入值、输出版本、来源范围、重试状态与回读结果；发现人工更改、匹配异常、缺列或期间缺口时停止该项并记录冲突，不能将未知数据写成 0，也不自动清空历史列。首次接管采用明细预览 → 批准写入 → 回读核对。

Base 的资源标识、字段标识和内部链接只放受控配置，不写入仓库；业务列白名单和输入订单字段分开，不能将同步输出再次当作新的初始已发基线。

## 7. 月账单数量汇总

### 7.1 样例结构

本轮只读“锦诚 26.8已核普票.xlsx”的 Sheet1，未改写或重新保存源文件：

- A1:H1：日期、名称、规格、数量、单价、总金额、采购单号、入库单号；I 列含凭证图片。
- 第 86–112 行：来货出入，含正负数、未知单号以及同组多个入库单号。
- 第 113–274 行：标注次品退回的负数量明细。

### 7.2 首版边界与待核实来源

| 分项 | 数据基础与待确认点 |
|---|---|
| 正常来货/发货 | 系统发货与聚水潭实际入库不是同一事实；样例带采购/入库单号，需确认账单基数采用哪种 |
| 来货出入 | 已确认收货差额和飞书登记应关联去重，只对同一事实记一次 |
| 质检退回 | 现有质检返修可提供仓库退回事实，但结算月份、是否所有退回都应扣账仍待确认 |
| 客退 | 用户要求纳入；本样例只明确标注次品退回，不能将其全部视为客退，客退来源和区分规则待补 |
| 返修发回/报废 | 与正常发货分开，是否增加结算数量、报废是否再扣须确认，防止重复扣减 |
