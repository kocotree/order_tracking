## 1. 已核验基础

基于 main `583756b`：

- `server/app/modules/shipments/service.py` 的正式提交保存原报明细与 `submitted_at`；撤回保存历史副本，重提复制明细回根单并改写 `submitted_at`。直接查询当前 `SHIPPED` 集合无法还原任意截止点。
- `Shipment.source_shipment_id` 指向根发货单；历史副本、重提记录必须折叠到根身份。
- `OrderDetail.source_record_pk` 关联 `OrderImportSourceRecord`，后者保留来源范围、记录 ID、下单明细 ID、订单编号。优先复用该关联。
- `server/app/modules/order_import/auto_sync.py` 与 `server/app/worker/` 已有到期检查、数据库任务、幂等键、角色领取、失败与重试能力。#231 将汇总任务和到期扫描从 `sync` 完整迁到同容器内的 `shipment` 角色。
- `server/app/adapters/order_source.py` 已具备应用身份鉴权和读字段/记录能力。回填增加定向写适配能力，保留订单读取接口的只读职责；不另建调度服务。

## 2. 阶段与调度

使用标准库 `calendar`、`datetime`、`zoneinfo.ZoneInfo("Asia/Shanghai")` 生成月内周段、合并短片段。本地业务边界转换为 UTC 后持久化；展示和日志明确时区。10月采用需求指定区间，不泛化解释历史不规则字段。

复用 worker 的 maintenance 到期检查，按持久化计划生成月初准备任务和阶段结束任务，唯一幂等键采用任务类型＋目标范围＋月份/阶段。日期检查只决定是否到期，执行仍以22:00截止点为准；无需设置每周日 cron，也不使用桌面会话自动化运行生产业务。

检查包含所有未完成到期任务，按阶段顺序恢复。建列失败阻止依赖它的写入，不能丢弃统计事实。重复 worker 依靠数据库唯一约束及现有领取机制处理。结构修改在同一目标范围内串行执行。

### Issue #231：独立汇总进程

现有 supervisor 启动 `sync`、`incoming`、`notification`、`shipment` 四个子进程。`sync` 保留自动订单同步、订单导入、导入重校验、产品初始同步、产品增量同步和图片缓存六类任务；`shipment` 独占 `shipment_writeback` 及每分钟到期扫描。其他角色职责不变。

各角色独立创建数据库池及所需外部客户端，汇总进程无需初始化聚水潭、OSS、识别或通知客户端。领取与启动时的过期恢复均按所属任务类型过滤，旧 `sync` 已领取但中断的汇总任务由 `shipment` 按原五分钟过期边界恢复。复用原任务 ID、幂等键、冻结快照、三次尝试、30秒重试及日志，无数据库迁移。

关闭既有回填开关时保留进程，不执行到期扫描或飞书写入；已排队任务沿用缺少写入目标时失败、有限重试的既有行为。任一子进程异常退出仍终止整组，交由 Compose 重启；健康检查要求四角色齐全。连接池容量与关闭流程见[运维手册](../../shared/delivery/部署与运维手册.md)。

## 3. 截止事实与事务边界

### 3.1 最小持久化职责

复用现有 `BackgroundJob` 保存执行和重试，`AuditLog` 保存每次尝试的结果；新增业务存储只承担以下必要职责，名称在实施时遵循模型规范：

| 存储 | 内容与约束 |
|---|---|
| 发货汇总事实 | 根单、事实版本、正式提交/撤回类型、生效时间、原报明细和来源关联快照；业务幂等键唯一，已写事实不改 |
| 阶段 | 标签日期、连续统计起止时间、冻结状态、目标字段 ID、公式核验信息；目标范围＋阶段唯一 |
| 阶段发货归属 | 根单、阶段、选用事实和原报明细快照；根单唯一，冻结后保留归属，避免失败期间被后续阶段重复领取 |
| 阶段行结果 | 来源行、绝对合计、目标字段、写前值、写入/回读状态；阶段＋来源行唯一 |
| 接管控制 | 单行事务同步点、历史证据准备状态、来源范围、已绑定字段及公式更新意图；网络操作期间不持有该行锁 |

每次尝试的日志通过阶段 ID 和任务 ID 关联上述结果。月初准备任务记录字段创建、公式旧值/新值及回读结果。日志只保存必要业务标识与错误码，禁止记录凭证或完整外部响应。

### 3.2 不漏记的同步点

提交、撤回、重提与汇总事实在同一 MySQL 事务完成；写事实失败使本次业务事务失败。不可使用异步通知是否成功作为事实是否存在的判据。

所有影响汇总的状态变更和阶段冻结共用一个数据库同步点。业务操作先取得该锁，再确定生效时间并写事实，持锁至事务提交；冻结同样先取得该锁，再读取截止前事实并落盘。锁内不访问飞书、不发送通知。

该同步点保证：截止前已取得锁并生效但尚未提交的操作，会在冻结取得锁前完成；截止后取得锁的操作，其生效时间自然归下一窗口。不能沿用请求进入时、等待数据库锁之前采样的时间。提交日期、正式提交时间和汇总事实使用同一个生效时间，避免各自跨日。

实现需统一锁顺序，在提交、撤回、重提共同入口先取得同步锁，再取得发货单及派工锁，避免互锁。单目标表采用一个短事务同步点即可；须用并发集成测试验证等待、超时、回滚和22点边界。

按截止点选取每个根单最新的有效事实，排除截止前撤回/作废以及已有阶段归属的根单。同一截止点后发生的改变对已冻结阶段无效。冻结归属与行快照一次事务提交；跨阶段重复领取由根单唯一约束阻止。

### 3.3 首次接管的存量事实

10月6日起已有提交可能先于功能部署。启用前只读核验 `Shipment`、历史副本、提交/重提 outbox 与撤回审计，能唯一还原的事实按原始时间一次性登记，并保存证据引用；不得触发通知或变更订单数量。

现有撤回会保存旧正式内容，重提 outbox 含事实副本身份，但是否覆盖全部存量须实际核验。缺失历史时停止受影响阶段，列出缺失证据，不用当前状态填补。存量重建属于首次接管准备，与日后补录业务重算分开。切换时使用同一同步锁确定水位，先启用事务内事实记录，再完成水位前的存量登记，防止准备期间的新提交丢失。

## 4. 飞书字段、公式和行写入

### 4.1 配置与权限

目标 Base、表和必要字段 ID 由受控环境配置提供，仓库使用无真实资源标识的示例。核验后台应用身份拥有读字段、建字段、更新公式和记录权限；用户 CLI 可读不等于后台应用可写。

写入白名单限定目标表、接管阶段数字字段与“出货总数”。飞书应用实际授权、字段容量、分页和批量限制在实施前按官方 API 核验并记录；本设计不把未验证的 API 限额或参数写成事实。

### 4.2 字段识别和月初准备

完整读取分页字段元数据，按受限字段命名格式提取日期，用标准日期类型验证。该识别只处理本项目字段名称，不实现通用公式或成熟文件格式 parser。月份内区间必须唯一、无重叠/缺口，类型必须是数字。

按“核验现有列 → 创建缺列 → 重新读取并固定 ID → 扩展公式 → 回读”的顺序执行。创建请求超时或进程中断先按区间重查，不立即重建；发现两个同区间列停止处理。新增列写入意外类型时不自动改类型。

总数公式以批准的原始表达式和历史引用集合为基线。只对已知 `ROUND(SUM(IFBLANK(...,0),...),0)` 形式做受控扩展，不引入通用公式解析器。若官方读回值使用内部字段引用，先验证其实际表示，再固定适配规则；不猜测字段 ID 与显示名称的转换。

每次写公式前重新读取并与本次预期旧值比较，新引用排重，保留历史引用和舍入语义；不一致立即报错。外部接口如无条件更新能力，“写前检查＋写后回读”无法保证并发人工编辑完全不被覆盖，因此结构维护期间需避免人工并发改总数公式，此限制纳入运维说明。不能声称实现了远端原子比较更新。

### 4.3 冻结与回填

从事实快照沿派工、订单明细和来源记录聚合；发货原报明细为数量来源，禁止复用有效数量台账的净数。写前校验远端行仍对应原订单明细；已删除行不能以同名行替换。

整阶段先核验本地来源关联，再冻结完整来源与行结果；本地关联缺失时保留原始事实并报错，不能冻结残缺合计。冻结后逐行校验飞书身份并写入，失败前已确认的行保留进度，重试继续未完成行。整体任务只有所有预期项成功才成功。根单即使跨多行且部分失败也保留阶段归属，后续阶段不能重复计入。前一阶段尚未冻结时，后续阶段拒绝提前领取发货。

每行只更新本阶段单元格的绝对值，回读一致才标记成功。远端成功而本地记录失败时，重试先回读；相同值直接确认，不同值按原快照重写。批量接口如有部分失败，按逐行结果记录，不以 HTTP 成功代替业务成功。

禁止因重试重新查询最新数量、释放冻结归属或重新分配到下一阶段。成功阶段不自动巡检覆盖后续人工改值；技术重试仅针对未完成任务。

## 5. 失败与可观测性

外部失败在出错步骤直接抛出明确错误，由既有 worker 边界记录。沿用最多3次尝试、30秒间隔的有界重试；结构漂移、权限问题、关联缺失和历史证据不足在每次尝试中直接终止，持续失败后等待人工处理。不能捕获后写0、换列或猜行。

每次任务尝试记录开始/结束、计划截止、阶段、状态、尝试次数、成功/失败行数、数量、排除原因及安全错误信息。结构准备与汇总分别记录。复用现有结构化日志和数据库审计，运维按阶段或执行 ID 查询；本需求不新增日志页面、消息推送或通用任务平台。

实施时在部署手册提供查询日志和重试原任务的受控命令；重试命令复用原任务 ID 和快照，不能悄悄创建新的统计口径。无限重试及失败任务自动当作成功均不允许。

## 6. 实施计划和验证

用户已明确要求按 TDD 实施。每个业务切片按“一个失败测试 → 最小实现 → 测试通过”推进，保留失败原因与通过证据；禁止先批量写全套测试再集中实现。使用项目现有 pytest、隔离 MySQL 与锁文件，不引入新测试框架。

以下公共测试边界已在会话明确列出并由用户确认：

| 测试边界 | 可观察结果 |
|---|---|
| 月份阶段规划的公共入口 | 输入月份，返回需求中的日期段、字段名和连续截止窗口；预期值使用独立日历样例 |
| 现有发货提交/撤回/重提接口与汇总执行入口 | 经真实业务提交后执行阶段，观察输出数量、排除原因、重复执行结果和执行日志；覆盖并发22点截止 |
| 飞书写适配器的公共方法 | 在 HTTP 边界模拟字段、公式和记录响应，验证最终远端状态及可观察错误；不 mock 内部业务函数 |
| worker 到期执行与受控重试入口 | 重启、重复领取和部分失败后结果一致，日志可追溯，已成功发货不重复计入 |

时间和飞书 HTTP 使用可控边界，数据库事务使用隔离真实 MySQL。测试不调用私有方法，不以内部调用次数代替业务结果，不为测试新增产品页面或无用接口。迁移通过既有 Alembic 检查及数据库约束验证。

需求、技术设计及本计划已确认，功能实施由 Issue #227 跟踪，按一个可独立验收的完整功能 PR 交付。依赖按下列顺序实现，不将残缺回填流程单独启用：

1. 阶段算法、10月接管配置与验收样例：覆盖月初/月末1、2、3天，周一/周日，跨年、闰年和连续截止窗口。
2. 事实、冻结归属及迁移：覆盖正常提交、撤回重提、同根重复、同SKU跨订单、并发截止、延迟执行和存量重建。使用隔离 MySQL，验证约束和事务失败。
3. 飞书适配与任务编排：测试字段分页、复用/新建、公式漂移、行关联异常、超时结果未知、部分成功和进程恢复。普通测试使用模拟适配器，不写真实 Base。
4. 串联后台调度、日志与受控重试；同步数据字典、接口与外部集成、部署运维和验收记录。确认自动订单同步不会把本功能输出重新当作初始已发基线。
5. 本地后端检查、迁移检查、完整 PR CI和必要审查；业务验证使用需求验收矩阵。真实应用权限、字段/公式读回及写入效果在获授权环境验证，单独记录证据。

目前无新增页面、客户端接口或交互，无页面原型任务。后续如新增可见入口，须另过页面确认门。
