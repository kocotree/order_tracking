## 切片 1：数据模型、整批确认事务与登记查询

执行 Issue：[#123](https://github.com/kocotree/order_tracking/issues/123)。依赖：无执行 Issue 前置；以已确认需求、设计与 #111 的采购关联字段为基线。

### 范围

- 五张新表的迁移（批次、图片、Excel 版本、正式记录、调整审计），迁移版本号在实施时从当时最新 Alembic head 分配。
- `quantity_ledger` 新增 `INCOMING_DIFF` 取值，不改表结构，不新建第二套数量口径。
- 整批确认事务：设计 §7.2 的七步固定顺序，含幂等占位、批次行锁、按 `order_assignment_id` 升序锁派工行、下限重算、记录与账本与审计写入、outbox、终态回填。
- 候选匹配（只读）：候选派工恰好 1 个才唯一，不用相似度、不猜测。
- `GET /api/v1/orders/{orderId}/incoming-differences` 一条路径按角色投影，工厂强制按 `factory_id` 过滤，排序固定 `registered_at, record_id` 正序。
- `incoming_diff.registered` consumer：逐工厂用户建站内通知，微信复用 `factory_status`，不新增第 4 个工厂模板。
- `batch_no` 生成：`IN` + 年月日 + 当日两位序号，按上海时区。

预计文件范围：`server/app/db` 模型与迁移、来货出入服务模块、`orders` 查询与 API、`notifications_audit` consumer、OpenAPI 导出与 `admin-web/src/api/generated.ts`、后端测试。

### 验收

覆盖 AC-08、AC-09、AC-11、AC-12、AC-13、AC-15、AC-17；核心事务、权限与数量按 TDD 用隔离 MySQL 8 验证；迁移正反向执行通过；不接真实飞书与模型服务。

## 切片 2：已登记记录的数量调整与调整通知

执行 Issue：[#124](https://github.com/kocotree/order_tracking/issues/124)。依赖：#123 完成并验证。

### 范围

- `PATCH /api/v1/admin/orders/{orderId}/incoming-differences/{recordId}`，按设计 §7.3 的乐观锁、差额账本、下限校验与审计顺序实现。
- `delta == 0` 不写账本行；乐观锁冲突回 409；下限被突破回 422 且保持原值。
- `incoming_diff.adjusted` consumer 与站内/微信文案。
- 产品、规格、采购关联、订单归属不提供编辑入口；不提供删除或撤销。

预计文件范围：来货出入服务与 API、`incoming_diff_adjustments` 读写、`notifications_audit` consumer、生成类型、后端测试。

### 验收

覆盖 AC-14；`delta == 0`、409、422 三条边界各有测试；工厂角色调用被拒绝；多次调整后统一已发始终等于 `initial_shipped_quantity + SUM(quantity_delta)`。

## 切片 3：管理员订单详情表格与工厂小程序折叠区

执行 Issue：[#125](https://github.com/kocotree/order_tracking/issues/125)。依赖：#123（查询接口）、#124（调整接口）完成并验证。

## 切片 4：Excel 核对表生成、隐藏标识签名与回传校验

执行 Issue：[#126](https://github.com/kocotree/order_tracking/issues/126)。依赖：#123（批次、图片、工作簿表与 `line_snapshot` 结构）。

### 范围

- 生成：一批一个工作簿、每工厂一个 Sheet、工厂不明进「待确认」Sheet；可见业务列固定 8 列，单价/总金额/入库单号留空；图片等比压缩后每行重复嵌入同一原图，行高列宽以 `docs/reference/来货出入核对表样例.xlsx` 为视觉基线。
- 技术标识：隐藏 Sheet `_核对标识`、隐藏列 `_line_token`、`HMAC-SHA256` 签名；密钥只从服务端 settings 读取。
- 回传解析复用 `repairs/workbook.py` 的加固上限，逐项校验后返回 `(Sheet, 行号, 原因)`。
- 支持的行级改动只有改行、删行、跨 Sheet 移动；**没有 token 的数据行判失败**（需求 V1.2 §4.2：不允许手工新增行，漏识别明细重新拍照）。
- 通过校验即写新版本并更新 `current_workbook_id`，旧版本保留且不可再确认。

预计文件范围：来货出入 Excel 生成与解析模块、`stored_files` 写入、settings、后端测试与夹具工作簿。

### 验收

覆盖 AC-07 与「新增行判失败」；签名篡改、版本过期、`batch_id` 不匹配、token 越批次四种拒绝各有测试；五项加固上限各有超限拒绝测试；生成结构与样例列顺序一致；签名密钥不出现在夹具、日志与审计 `changes` 中。

## 切片 5：识别适配器、后台作业与离线固定样本回归

执行 Issue：[#127](https://github.com/kocotree/order_tracking/issues/127)。依赖：#123（图片表与批次状态）。真实调用的外部输入：模型服务 Key。

### 范围

- `server/app/adapters/vision.py`：Protocol + Fake + Disabled + 真实实现；一次调用一张图，线上固定 `qwen3.5-flash` 与纳入 `server/` 版本控制的 v12 提示词。
- 服务端解析 `boxes`、`diffNoteText`、`lines`，严格校验 JSON、方向及正整数绝对数量并归一化正负数；未知字段保留待确认。不识别图片日期，新记录的 `source_business_date` 为空，历史值原样保留。
- 工厂＋货号或品名＋颜色/规格精确定位 SKU，再查有效派工及已保存采购关系；按统一已发口径计算未发，多候选按合同出货时间升序取首个未发大于 0 的订单，零未发跳过，无法确定则待确认。
- 后台作业 `incoming_diff.recognize`（`dedupe_key=batch_id`）：HTTP 只落库，识别在 worker 跑；失败走现有重试，超上限进终态失败，不静默降级。
- 每张图片持久化 `recognition_model` 等字段；`content_sha256` 查重与「继续核对」确认。
- 离线固定样本回归复用现有人工标注与评分逻辑，先核对标注完整性，再输出逐字段正确率、错误样例和重复运行稳定性。

预计文件范围：`server/app/adapters/vision.py`、worker handler 注册、图片服务、评测脚本与标注样张夹具、后端测试。

### 验收

覆盖 AC-01 ~ AC-03、AC-10；识别结果只形成候选，任何路径不直接生成正式记录；用 Fake 完成 TDD 且测试不发起真实网络调用；隔离 MySQL 验证匹配顺序、零未发、正负数量、失败重试和重复图片；评测脚本产出可复核的逐字段结果；模型 Key 不入仓库、文档、日志与审计。

## 切片 6：飞书机器人入站端点与卡片出站闭环

执行 Issue：[#128](https://github.com/kocotree/order_tracking/issues/128)。依赖：#123、#126、#127 完成并验证。外部输入：飞书应用扩权与机器人凭据。

### 范围

- 两个免登录端点：`POST /api/v1/integrations/feishu/events`、`POST /api/v1/integrations/feishu/card-actions`。
- 入站固定顺序：验签 → challenge → 事件去重 → 身份解析（管理员且已启用）→ 落库 → 冻结并投递识别作业 → 确认。
- 复用现有飞书应用，只加机器人能力与消息事件订阅；回调先按 `event_type` 与 `chat_id`/`open_id` 过滤，其他事件丢弃并回 200。
- 出站复用 outbox `delivery` 通道与现有卡片发送能力，文案与按钮严格按需求附录 A.1、A.2。
- 新增 `feishu_bot_enabled`、`feishu_bot_verification_token`、`feishu_bot_encrypt_key`；未配置返回 503 且不写业务数据。
- 图片与 Excel 下载带 tenant token、大小上限与超时；失败按附录 A.2 回复并标记该图片失败。

预计文件范围：`server/app/api` 集成路由、飞书发送组件抽取、来货出入编排服务、settings、后端测试。

### 验收

验签失败/超窗/解密失败三种拒绝、`challenge` 正确、`event_id` 重推不重复处理、非管理员只收「无权限」、无关事件被过滤；覆盖 AC-16、AC-17；全流程集成测试用 Fake 飞书发送器与 Fake 识别器跑通「发图 → 生成 → 回传 → 确认」；开关关闭时端点 503 且现有订单来源读取行为不变；真实飞书连通与真实卡片发送单列为未完成项。
