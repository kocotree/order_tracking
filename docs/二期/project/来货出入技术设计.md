## 2. 不变量

1. **数量只有一个口径**：统一已发数量 = `initial_shipped_quantity + SUM(quantity_ledger.quantity_delta)`。来货出入不写 `order_assignments`、不写 `order_lines`、不写发货表。
2. **正式记录与账本一一对应**：每条来货出入记录在确认时写且只写一条 `INCOMING_DIFF` 账本行；每次数量调整写且只写一条 `INCOMING_DIFF_ADJUST` 账本行，金额为新旧差额。账本行不删除、不更新。
3. **未确认不生效**：识别结果、候选匹配、Excel 各版本都不写账本、不改订单、不发通知。
4. **整批原子**：一次确认要么全部记录落库，要么全部不落库；部分成功不存在。
5. **不合并、不抵消**：同订单同规格的多条记录各自独立，展示与账本都不聚合。
6. **下限在事务内保证**：确认与调整都在锁定相关 `order_assignments` 后重算统一已发，任何一条会使其小于 0 即整体失败。
7. **模型输出不是业务事实**：识别结果只进候选表字段，永不直接生成正式记录。
8. **凭据不落库、不进文档**：飞书机器人密钥、事件 encrypt key、Excel 签名密钥、模型服务 Key 只经服务端环境变量注入，不写入 Excel、页面、日志、审计 `changes` 或仓库。

### 3.6 现有表的改动

- `quantity_ledger`：新增两个 `source_type` 取值，**不改表结构**。`INCOMING_DIFF` 的 `source_id` = `record_id`，`INCOMING_DIFF_ADJUST` 的 `source_id` = `adjustment_id`；唯一约束因此天然阻止同一记录重复生效，同时允许同一记录多次调整（每次一个新 `adjustment_id`）。
- `notifications`：`category` 新增 `INCOMING_DIFF`（枚举若在数据库侧受约束则随迁移放开）。
- 其余现有表不改结构。

## 4. 飞书机器人

### 4.1 入站

新增两个免登录端点，安全性由飞书签名保证，不参与现有会话 Cookie 体系：

| 端点 | 用途 |
|---|---|
| `POST /api/v1/integrations/feishu/events` | 消息事件（图片消息、Excel 文件消息）与 URL verification challenge |
| `POST /api/v1/integrations/feishu/card-actions` | 卡片按钮回调：生成核对表、确认登记、重新生成、继续核对 |

入站处理顺序固定：

1. **验签**：校验 `X-Lark-Signature`（timestamp + nonce + encrypt key + body），时间戳超窗直接 401；`encrypt` 字段按 AES-256-CBC 解密。
2. **challenge**：`type == "url_verification"` 时原样回 `challenge`，不落库。
3. **事件去重**：`idempotency_records` `scope="feishu_event"`、`key=event_id`；已存在直接 200 返回，不重复处理（飞书要求 3 秒内响应并会重推）。
4. **身份解析**：事件里的 `open_id` → `external_identities`（scope 为现有飞书身份 scope）→ `users`。必须 `role == "admin"` 且 `is_enabled`，否则只回附录 A「无权限」文案，不落业务数据。
5. **落库**：图片消息 → 取或建 `COLLECTING` 批次，下载图片写 `stored_files` 与 `incoming_diff_images`，回附录 A.1 第 1 步文案与「生成核对表」按钮。
6. **异步识别**：点击「生成核对表」→ 冻结批次 → `background_jobs` `job_type="incoming_diff.recognize"`、`dedupe_key=batch_id`，HTTP 立即返回。
7. **确认**：点击「确认登记」→ 第 7 节确认事务；耗时操作同样走后台作业，卡片先回「正在处理」，结果由出站消息给出。

图片下载用 `im/v1/messages/{message_id}/resources/{file_key}?type=image`，Excel 回传用 `im/v1/files/{file_key}`，均带 tenant token；下载有大小上限与超时，失败按附录 A.2 回复并标记该图片失败。

### 4.2 出站

复用 `outbox_messages` 的 `delivery` 通道（`channel="feishu"`，`recipient_id` = 提交人）与 `adapters/notifications.py` 现有卡片发送能力。文案取需求附录 A，占位符由 payload 填充。卡片 JSON 布局属于实施细节，按附录 A 的文案与按钮一一对应，不新增按钮。

机器人回复失败不回滚已登记数量（需求 §11、AC-16）。

### 4.3 应用与配置

**复用现有飞书应用**（2026-09-17 用户确认）：机器人与 `adapters/order_source.py` 使用同一套 `feishu_app_id` / `feishu_app_secret`，只在飞书后台为该应用增加机器人能力、消息事件订阅与 `im:message`、`im:resource` 相关权限，不新建应用、不新增第二套应用凭据。

因此只新增下列 settings（`ORDER_TRACKING_` 前缀，默认空、缺失即视为功能未启用）：

```
feishu_bot_enabled                      # 总开关，默认 false
feishu_bot_verification_token           # 事件回调校验
feishu_bot_encrypt_key                  # 事件加密
incoming_diff_workbook_signing_secret   # Excel 签名密钥
incoming_diff_vision_*                  # 见第 5 节
```

复用带来一个必须注意的边界：给现有应用加事件订阅后，飞书会把该应用能收到的消息事件全部推到本回调地址。回调必须先按 `event_type` 与 `chat_id`／`open_id` 过滤，只处理来货出入相关消息，其他事件直接丢弃并返回 200，不落库、不告警刷屏。同时，扩权只影响这一个应用，现有订单来源读取的既有行为不变。

未配置时端点返回 503 并且不写任何业务数据，与现有 `Disabled*` 适配器一致。

## 5. 识别（OCR 与大模型）

新增 `server/app/adapters/vision.py`，沿用现有适配器四件套：`IncomingDiffRecognizer` Protocol、`Fake…`（测试与本地）、`Disabled…`（未配置）、真实实现。

- **一次调用一张图**，输入原图字节，输出固定 JSON schema：`{factoryName, productCode, productName, color, size, businessDate, lines:[{color,size,quantity}], confidence, unresolvedFields}`。
- 提示词要求：箱贴提供默认值，手写／覆盖／标注优先；未写明的字段返回 `null` 而不是猜测；只输出 JSON。
- 数量符号规则、月日补年份（补批次当年）在**服务端**做，不交给模型。
- 失败重试由 `background_jobs` 的重试机制承担，超过上限进终态失败并按附录 A.2 回复；不做静默降级。
- 模型服务地址与 Key 只从 settings 读；请求与响应不写入审计 `changes`，只在应用日志记录 `image_id`、模型名、耗时、token 用量与错误码。
- **照片允许发到外部模型服务**（2026-09-17 用户确认）。照片内容为箱贴、手写数量与发货日期，不含人员或客户隐私字段。

### 5.1 模型选型用离线 AB 对比，不做线上分流

用户要求通过 AB 测试选模型。做法取最省的一种：

- `incoming_diff_vision_provider` 指定当前生效的实现，同一时刻线上只有一个模型在跑；**不做按批次或按图片的线上流量分流**，避免同一张核对表里混着两个模型的结果、出错时无法归因。
- 选型靠一个离线评测脚本：固定一组人工标注过的样张（含清晰箱贴、手写覆盖、模糊、多明细、少货负数、缺日期），依次用各候选模型跑同一组图，输出逐字段对比表——工厂名、产品名称、颜色尺码、数量、日期各自的正确率与错误样例。
- 判定按字段正确率，不看整体「大概能用」；数量与日期错一处就算该样张失败。脚本产物是可复核的表格，不是模型自评分。
- 换模型只改 `incoming_diff_vision_provider` 配置，历史记录里保留 `recognition_model`，因此任何时候都能查出某条记录当初是哪个模型识别的。
- 候选模型清单与账号由用户提供后再实现真实适配器；评测脚本与 Fake 实现不依赖任何真实 Key。

识别产物只写 `incoming_diff_images.recognition_payload`，任何情况下不直接生成 `incoming_diff_records`。

## 6. Excel 生成与回传校验

### 6.1 生成

- 一个批次一个工作簿；每个已识别工厂一个 Sheet，Sheet 名与系统工厂名一致；工厂无法确定的明细进「待确认」Sheet。
- 可见业务列固定 8 列（名称、规格、数量、单价、总金额、采购单号、入库单号、图片），顺序与需求 §4.2 一致；单价、总金额、入库单号留空。
- 图片按 `pillow` 等比压缩后用 `openpyxl.drawing.image.Image` 嵌入，锚定到该行的图片列；行高列宽以 `docs/reference/来货出入核对表样例.xlsx` 为视觉基线。首版**每行重复嵌入同一张原图**，不做跨行合并（需求 §4.2 允许两种，取解析稳定的一种）。
- 工作簿写入 `stored_files` 私有桶并登记 `incoming_diff_workbooks`（`direction=GENERATED`），再作为文件消息发给提交人。

### 6.2 技术标识与签名

- 隐藏 Sheet `_核对标识`（`sheet_state="hidden"`）保存批次级信息：`batch_id`、`version`、生成时间、HMAC 签名。
- 每个业务 Sheet 最后一列为**隐藏列** `_line_token`：`image_id` + 行序号 + 短哈希。管理员剪切整行移动到别的 Sheet 时 token 随行走，从而保住「明细仍关联本批次来源图片」。
- 签名 `HMAC-SHA256(signing_secret, batch_id | version | 排序后的全部 line_token)`。校验不过、版本不是 `current_workbook_id`、`batch_id` 不匹配、token 不属于本批次 → 拒绝并回附录 A.2 的「版本过期／技术标识无效」文案。
- **没有 token 的数据行一律判失败**，报出 Sheet 与行号，不做图片 anchor 反查、不做任何推断（2026-09-17 用户确认：Excel 不允许手工新增行，需求 V1.2 §4.2 已同步）。这样 token 就是行与来源图片之间唯一的绑定手段，回传校验没有第二条推断路径。

### 6.3 回传解析

复用 `repairs/workbook.py` 的加固范式：文件大小、zip 条目数、解压总量、Sheet 数与数据行数上限，逐项校验后返回 `(Sheet, 行号, 原因)` 列表。解析通过即写入新的 `incoming_diff_workbooks`（`direction=UPLOADED`，`version = 上一版 + 1`）并更新 `current_workbook_id`；旧版本保留，不可再确认。

支持的行级改动只有三种：改现有行的业务列、删行、整行移动到另一个工厂 Sheet。解析按 token 集合比对生成版之间的差异：token 消失 = 删行，token 换了 Sheet = 移动，token 内容变了 = 改行，**出现没有 token 的数据行 = 该行失败**（附录 A.2「手工新增行」文案）。漏识别的明细走「重新拍照 → 新批次」，不在本批次的 Excel 里补，因此解析器不需要「凭空新增一行并给它找来源图片」的路径。

## 7. 匹配与确认

### 7.1 候选匹配（只读）

对每行按下列条件在 `order_details`（已派工，`assignment_id` 非空、`is_active`）联 `product_variants`、`order_assignments`、`factories` 查候选：

1. 工厂（Sheet 名或识别值）；
2. 货号／产品编码、产品名称；
3. 颜色与尺码 → `variant_id`；
4. 图片业务日期与 `contract_ship_date` 的合理区间；
5. 已保存的 `purchase_order_id` / `purchase_order_item_id`。

判定：候选 `order_assignment_id` 恰好 1 个才算唯一。为 1 时自动关联并在 Excel 填写采购主单号；大于 1 时采购单号留空并标「待确认」；管理员填写主单号后再按主单号＋SKU 复核唯一性；为 0 或复核后仍不唯一即该行失败（需求 §6.3）。

不使用相似度分数自动选择，不因数量相同或日期接近选择订单。货号不等同于 SKU、订单号或采购单号。

### 7.2 确认事务

单个数据库事务，顺序固定：

1. 幂等占位：`idempotency_records` `scope="incoming_diff_confirm"`、`key=f"{batch_id}:{version}"`；已存在且 `completed` 直接返回原 `result`（AC-09）。
2. 锁批次行（`SELECT … FOR UPDATE`），校验 `status == READY`、`workbook_id == current_workbook_id`、提交人 == 确认人（需求 §3）。
3. 按 `order_assignment_id` 升序锁定全部涉及的 `order_assignments`（固定顺序避免死锁）。
4. 逐 assignment 汇总本批次全部相关行的数量之和，重算 `initial_shipped_quantity + SUM(ledger) + 本批次增量`，任何一个结果 < 0 即整批失败（AC-12）；允许结果大于下单数量（AC-13）。
5. 写 `incoming_diff_records`、`quantity_ledger`（`INCOMING_DIFF`）、`AuditLog`（`action="incoming_diff_registered"`，`changes` 含记录数、逐 assignment 的 before/after）。
6. 按「工厂＋订单」聚合写 `outbox_messages`：`event_type="incoming_diff.registered"`、`dedupe_key=f"incoming-diff:{batch_id}:{factory_id}:{order_id}"`（需求 §9.1）。
7. 批次置 `CONFIRMED`，写幂等 `result`（记录数、工厂数、确认时间、确认人）。

未发数量继续按现有 `max(下单数量 − 统一已发, 0)` 计算；本期不因来货出入自动把已完成订单改回未完成（需求 §7.1）——即确认路径不触碰 `orders.status` 与 `order_completion_records`。

### 7.3 登记后调整数量

`PATCH /api/v1/admin/orders/{orderId}/incoming-differences/{recordId}`，body `{ "quantity": -3, "version": 2 }`：

1. 锁记录行，校验 `version`（不符回 409，页面按现有范式恢复旧值并提示刷新）；
2. `delta = 新 − 旧`；`delta == 0` 直接返回当前快照，不写账本（`quantity_ledger` 有 `quantity_delta <> 0` 约束）；
3. 锁定该 `order_assignment_id`，重算下限，`< 0` 即 422 拒绝并保持原值；
4. 写 `incoming_diff_adjustments`、`quantity_ledger`（`INCOMING_DIFF_ADJUST`，`source_id=adjustment_id`）、更新 `incoming_diff_records.quantity` 与 `version`、写 `AuditLog`（`action="incoming_diff_adjusted"`）；
5. 写 `outbox_messages` `event_type="incoming_diff.adjusted"`；
6. 产品、规格、采购关联、订单归属不提供编辑入口（需求 §7.2）。

首版不提供删除已登记记录的入口；纠正一律通过调整数量完成（2026-09-17 用户确认）。

## 8. 接口与权限投影

| 方法与路径 | 角色 | 说明 |
|---|---|---|
| `GET /api/v1/orders/{orderId}/incoming-differences` | 管理员 / 工厂 | 一条路径按角色投影。管理员返回序号、登记时间、采购单号、产品编码、产品名称、颜色/规格、数量、`recordId`、`version`；工厂只返回产品名称、颜色/规格、数量、登记时间排序键，**不含 SKU、产品编码、采购单号、发货单号、`detailId`** |
| `PATCH /api/v1/admin/orders/{orderId}/incoming-differences/{recordId}` | 管理员 | 第 7.3 节 |

- 工厂查询强制按 `order_assignments.factory_id == 当前用户 factory_id` 过滤，不靠前端隐藏。
- 排序固定 `registered_at, record_id` 正序，不提供排序参数（需求 §8.1）。
- 管理员网页新增 `orderApi.incomingDifferences(orderId)` 与 `orderApi.updateIncomingDifferenceQuantity(...)`，按「操作记录」的懒加载范式在订单详情展开时取数；`admin-web/src/api/generated.ts` 随 `scripts/export_openapi.py` 重新生成，不手写类型。
- 小程序在 `factory-task-detail` 复用同一接口，按产品名称分组渲染折叠区；无记录时整区不渲染（Issue #117 已确认原型）。

## 10. 审计、安全与可观测性

- `AuditLog` 记录 `incoming_diff_registered`、`incoming_diff_adjusted`、`incoming_diff_workbook_rejected`；`changes` 只放业务值与前后数量，不放图片二进制、飞书 token、模型响应或文件直链。
- 图片与 Excel 只经后端按需读取；不签发长期公开 URL。
- 模型服务 Key、飞书机器人密钥、Excel 签名密钥只在服务器受控配置中；`app_env` 为 `shared_test` / `production` 且 `feishu_bot_enabled` 为真时，缺任一密钥启动即失败（沿用 `Settings` 现有校验范式）。
- 日志维度：批次号、图片数、识别耗时与失败率、Excel 版本数、确认成功／失败原因分布、通知投递结果。不记录图片内容与模型原文。

## 11. 与一期收货差额的隔离

- 两者写入不同 `source_type`，不做跨来源去重比较；系统不会因工厂、SKU、方向、数量相同判定重复（需求 §2.2）。
- 收货差额仍只在确认收货时产生，来货出入只在批次确认与数量调整时产生，互不触发。
- 集成测试断言：同一 assignment 先 `SHIPMENT_RECEIPT -2` 再 `INCOMING_DIFF -2`，统一已发应减少 4 而不是 2（AC-11）。

## 14. 已定决策

### 14.1 2026-09-17 已确认（7 项，无遗留开放问题）

| 问题 | 结论 |
|---|---|
| 照片能否发到外部模型服务 | 可以。模型选型通过第 5.1 节的离线 AB 对比决定，线上同一时刻只跑一个模型；候选清单与账号待用户提供 |
| 机器人用哪个飞书应用 | 复用现有应用，加机器人能力与消息事件权限，不新建应用（第 4.3 节） |
| 是否只在飞书卡片确认 | 是。管理员网页只展示与调整数量，不提供确认入口 |
| 已登记记录是否可删除／撤销 | 首版不提供。纠正一律走数量调整，审计留痕（第 7.3 节） |
| 未确认批次是否需要过期清理 | 不做。用户确认不会出现长期挂着不确认的批次，因此未确认批次保持原状态、不自动置失败、不自动删图；重复提交同一张照片仍由第 3.2 节的疑似重复提示兜住 |
| Excel 手工新增行如何绑定来源图片 | **不允许新增行**。没有 token 的数据行直接判失败，漏识别的明细重新拍照由系统重新识别（第 6.2、6.3 节）。此项与原需求 §4.2「管理员可以增加行」冲突，已同步改需求为 V1.2（§4.2、第 11 节、AC-07、附录 A.2） |
| 批次号格式与照片保留期限 | 批次号 `IN20260917-01`（`IN` + 年月日 + 当日序号，第 3.1 节）；原图长期保留、不做定期清理（第 3.2 节） |

设计仍依赖用户后续提供的两项外部输入（不是待决策项）：离线 AB 对比的候选模型清单与账号；飞书应用扩权后的机器人凭据配置。两项都在开发切片 6–8 才需要。

以上任一结论变化时，本文与相关正式资料同步更新，不在实施阶段静默选择。
