### 飞书证据

2026-10-09 完整读取以下官方文档：

- [接收消息事件](https://open.feishu.cn/document/server-docs/im-v1/message/events/receive.md)：事件提供一个 `message_id`；`root_id`、`parent_id` 表示回复关系，`thread_id` 表示话题。未定义一次多选发送的集合 ID、文件总数、序号或结束事件；明确消息幂等应使用 `message_id`，不能只依赖 `event_id`。
- [接收消息内容结构](https://open.feishu.cn/document/server-docs/im-v1/message-content-description/message_content.md)：`file` 内容只有一个 `file_key` 和 `file_name`。文件夹消息不能通过该 API 下载；文档列出的 `post` 标签没有普通文件集合。时间戳与回复关系均不足以证明附件已经收齐。

14:26:28 用户实际将两份 Excel 放入输入框后一次发送。服务器在同秒收到一次回调并返回 200；使用机器人身份读取该消息确认：一个 `message_id`，`msg_type=post`，`content.files` 完整包含两个文件的 key、文件名及 `is_folder=false`。旧处理器只读取 post 图片节点，因无图片而忽略本次消息。这里只验证消息和附件集合，未下载或登记业务数据。

**已确认：支持单个 `file` Excel，以及单条 `post.files` 的多个 Excel。** 一条消息为一次完整导入，按附件数组顺序处理所有文件。没有附件清单的独立消息分别形成独立上传，不按时间合并。无需 ZIP、超时或“上传完成”指令；容器 ZIP 支持不在实施范围。

## 2. 用户流程与版本

1. 图片识别、采购单预匹配、工厂分 Sheet 和八列布局保持现有规则。生成结果提供“核对登记”和“重新生成”；“核对登记”用服务端生成快照进入同一预检与疑似重复流程，最终汇总再提供“确认登记”。历史未确认卡片先进入新预检，不能绕过重复检查直接写数量。
2. 自由整理后的单个 Excel 或单条 post 的完整 Excel 附件数组建立一份导入，保存全部原件、哈希、文件顺序、解析快照及错误。待登记文件始终按最终五个业务字段重新匹配。
3. 同一管理员、同一私聊只有一个当前待处理的文件导入。新上传完整集合替换该会话的整个待处理集合（包括新文件解析失败的情况），旧汇总和旧异步结果立即失效；从不按文件名或哈希猜测局部覆盖。历史已登记集合不替换。汇总列出文件清单，防止管理员误以为新上传只是追加。
4. 接收时锁管理员行，以飞书消息创建毫秒时间判断先后，消息 ID 唯一约束处理重推。不同消息时间相同时设为 NEEDS_SELECTION，在卡片上明确选择保留的完整导入；选择前均不能确认。已知更早的迟到消息不顶替新集合，包含已有正式登记后的迟到消息。下载完成顺序不参与选择。
5. 初步校验无错误后显示疑似重复清单；决定未齐不出现有效确认操作。决定齐全后显示文件数、各厂记录数、多货／少货数量、跳过数及待登记总数。全部跳过时结束本次，记录零登记结果，不写数量和工厂通知。
6. 每次集合被替换、选择或重复决定变化都递增审核修订号。确认卡片绑定批次 ID、工作簿版本与审核修订号，由服务端加载已保存快照及原件摘要；按钮内容不能替代服务端校验。

已确认的文案与操作：

| 场景 | 文案与操作 |
|---|---|
| 新集合开始处理 | `导入 {编号} 已收到 {n} 份文件，正在统一核对。`；替换时追加旧导入编号与“旧确认已失效” |
| 校验错误 | `{文件名} / {Sheet} / 第 {行} 行：{原因}。本次全部未登记，请修正后重新发送完整文件集合。` |
| 疑似重复 | 清单展示稳定编号及当前／历史位置，提示回复本条消息作决定；支持 Issue 中三类自然语言样例 |
| 待确认 | 展示统一汇总与文件清单，按钮“确认登记” |
| 完成 | `导入 {编号} 已登记 {n} 条，跳过 {s} 条，涉及 {f} 个工厂。` |
| 无明确上传先后 | 列出两个导入编号和文件名，提示指定本次保留哪个完整集合；暂停确认 |

## 3. 存储与兼容

复用 `incoming_diff_batches`、`incoming_diff_workbooks`、正式记录、台账、审计、后台作业、Outbox。新增一张附件表，避免给每个文件建一套独立确认事务。

| 对象 | 变更 |
|---|---|
| `incoming_diff_batches` | 增加 `source_kind=PHOTO/FILE`（旧数据默认 PHOTO）、审核修订号、完整附件清单和来源消息时间／ID；状态约束扩展 `VALIDATING`、`NEEDS_DECISION`、`NEEDS_SELECTION`、`SUPERSEDED`。`READY` 仅表示允许确认，错误用现有 FAILED。保留旧图片批次及所有时间／审计字段；文件导入编号采用 IF 加 UUID，和 IN 图片批次区分 |
| `incoming_diff_workbooks` | `direction` 增加 IMPORTED；聚合导入的 `file_id` 可空，全部附件由新表关联；`line_snapshot` 保存全部解析行、位置、匹配、稳定编号、重复证据和决定；`validation_issues` 包含文件定位。旧 GENERATED／UPLOADED 的文件和签名保持原值 |
| `incoming_diff_import_files` | `import_file_id` 主键、`workbook_id`、`file_id`、`position`；唯一约束工作簿＋文件顺序。原始文件名、哈希和字节数在关联 StoredFile，源消息在关联批次。原 Excel 字节不重写 |
| `incoming_diff_records` | 增加可空 `import_file_id`、`source_sheet_name`、`source_row_number`；`image_id` 改可空。CHECK 要求有有效图片来源或完整文件行来源；文件来源对应当前登记工作簿由服务校验。旧 `batch_id`／`workbook_id` 继续非空，通知查询沿用 |
| 审计／幂等 | 保存原始管理员决定文本（仅受控业务审计）、消息 ID、模型／提示词版本、结构化决定和前后修订；日志不打印文本、密钥、文件内容或模型原文。确认幂等键包含导入及审核修订 |

文件行来源是自由整理后的确定依据。旧隐藏标识不参与匹配或校验，不根据名称、图片位置或相似内容伪造原图关系；没有确定关联时 `image_id=NULL`，仍可通过保存的最终 Excel 查看其图片。旧原图、原识别结果、原核对表与原正式记录原样保留。该变化意味着自由整理后不能保证每条新记录都直接关联某一历史原图，需要与本设计一起确认。

原图重复检查当前按已确认图片批次判断；新增文件来源后，图片预检查只能继续报告已有确定关联的重复，最终登记始终执行业务行重复检查。不得宣称无标识行也已完成原图级去重。

迁移从实施时最新 Alembic head 分配；验证存量 PHOTO 数据全部可读、旧查询与数量调整不变。有 FILE 记录时拒绝有损降级，不删除新数据来满足旧非空约束。不执行生产迁移。

## 4. 文件校验与匹配

- 使用现有 `zipfile`、`openpyxl`；复用 `IncomingWorkbookCodec` 的 ZIP／OOXML 安全边界，不手写格式解析器，不执行公式、不访问外部链接。只有登记读取的名称、规格、数量、采购单号列拒绝公式／错误值；价格、金额、入库单号和图片保留在原文件中，不参与业务登记。
- 首行八列名称和顺序保持现有格式，忽略既有技术 Sheet `_核对标识` 和隐藏 token 列；业务 Sheet 无论隐藏与否都纳入检查，不能静默漏行。空行跳过；其余行要求启用工厂、名称、规格、非零有符号整数，范围符合现有数据库 Integer；采购号按文本读取，禁止科学计数法或浮点精度丢失导致错号。
- 采购单号为空时仍执行现行候选规则；非空时作为明确约束。工厂＋名称＋规格先精确定位 SKU，再以当前已保存采购主／子单关系匹配订单明细。不继承旧 token 中的货号、子单或订单 ID；唯一候选和多候选的未发／合同出货时间规则复用 `match_detail`。
- 解析保存每行原值与匹配结果。确认时重新核验归属；已预览归属变更就退回预检，禁止确认时静默换到另一订单。零数量、布尔、非整数、未知工厂、错误采购号、不能唯一匹配都阻止整次。
- 集合上限：30 份 Excel；每份 20 MiB；集合内 Excel 压缩字节累计 100 MiB；集合全部 OOXML 解压累计 100 MiB；总数据行 5,000；每份最多 30 个业务 Sheet，保留 #237 的 31 个含技术 Sheet 上限。超限整次报错，不新增配置项。
- 按整个 `files` 数组校验；文件夹、非 Excel、重复附件项及任一下载失败均阻止整次。Excel 的 ZIP／OOXML 防护继续执行，不解压到文件系统。
- 不因单个成员失败跳过该文件继续登记。可以继续收集其他错误，最终统一报告；损坏到无法定位行的错误定位到文件。完整问题清单保存，卡片按现有长度限制摘要并提供完整错误附件，不能只让用户看到前十条。

## 5. 疑似重复与文本决定

重复候选依据精确匹配后的工厂／订单明细／SKU／采购主子单和正负数量；同时比较历史 `initial_quantity` 与当前 `quantity`，避免历史调整掩盖重传。相同文件哈希仅辅助提示，消息 ID 重推直接幂等；不同消息再次上传相同字节仍需业务预检。历史比对覆盖其他管理员已登记记录，权限限已启用管理员。

本次内部相同组的各行均提供独立稳定编号，列明互相对应关系，全部交由管理员决定；不默认保留第一条。跨文件同理。历史候选提供记录 ID、登记时间和数量及可用来源位置。编号按冻结文件顺序、Sheet 顺序和物理行号分配，当前版本内不重新编号。

文本使用 `qwen3.5-flash`，`enable_thinking=false`、`response_format={"type":"json_object"}`，提示词明确 JSON。支持依据：[百炼结构化输出文档](https://help.aliyun.com/en/model-studio/qwen-structured-output)。复用现有千问 Key／地址与 HTTP 客户端方式，不新增模型选择配置，不改图像识别参数。

请求只包含当前管理员回复和服务器给出的有效重复编号／决定范围；文件内文字及模型内容均为不可信数据。模型返回 `decisions=[{number, action:skip|register_new}]` 及是否有歧义。Python 严格拒绝额外动作、非法类型、bool 编号、无效编号、同编号冲突、越界、过期和不属于本人的上下文。明确的部分决定可暂存，遗漏项保持待决定；整句冲突／歧义／无效输出不应用任何决定。自然语言绝不触发正式确认。

管理员用飞书回复功能回复对应清单消息。服务端通过[获取指定消息内容](https://open.feishu.cn/document/server-docs/im-v1/message/get)读取 parent_id，校验发送者为当前应用、会话一致及清单审核标记；未引用时提示回复最新清单。同一文本消息按 `message_id` 去重。模型在锁外执行，落决定前重新锁批次检查快照修订；模型返回期间有新上传则拒绝该旧结果。上线须具备机器人读取本人私聊历史消息的权限。

实测用合成样本，覆盖逐条、全部、部分遗漏、否定、反悔、同条冲突、越界、含糊“按上次”、提示词注入、模型无效 JSON。测试记录实际模型、参数、结果及错误，不把 Fake 通过当成模型实测；真实调用前核对当前授权和受控凭据。

## 6. 接收、确认事务与并发

入站验签和身份映射沿用。接收文件先在一个短事务持久化来源消息及任务，以应用／租户／`message_id` 唯一约束去重；ACK 前必须有可恢复任务，不能仅占事件幂等后丢掉下载工作。下载、解包、解析和模型调用走现有 incoming worker；失败状态保留并可按原消息重试，不扩大真实业务权限。

确认按固定顺序执行：

1. 重新校验已启用管理员、本人私聊上下文；权限校验先于读取幂等结果。锁当前导入／版本，重查幂等，检查当前集合和审核修订。旧版按钮、旧 worker 任务均拒绝。
2. 按已有顺序锁所有受影响订单、明细及有效派工，复核匹配快照和每行来源；保持和数量调整／派工操作的锁顺序一致。
3. 在上述业务锁内使用当前读重查历史重复。若其他导入抢先登记产生新的候选，本次登记事务拒绝，机器人随后在独立事务锁批次更新重复证据、清除受影响决定并增加审核修订，再发最新清单。刷新失败由后台任务重试，任何重试仍执行当前读检查。此前决定只覆盖已展示的候选集合；并发不同管理员也受相同订单锁保护。
4. 将明确选定行按明细汇总增量，使用 `detail_shipped` 重算统一已发下限；来源未知或最终小于零则整次失败。跳过项不写记录；全部跳过按零登记结果结束。
5. 在同一事务写正式记录、每行唯一台账、审计、按工厂＋订单汇总的 Outbox、批次终态、确认幂等结果。各记录关联具体附件／Sheet／行号；所有附件共用一次事务。
6. 故障注入验证任一步失败均无部分数量生效。回复或通知失败仅重试投递，不能重新加数量。保留原未派工数量承接、派工／撤回与数量调整行为。

生成表直接登记也执行统一预检与确认；文件导入时保留所有旧表和已登记事实。旧卡片不得绕过当前重复规则或当前待处理集合的归属检查。
