# 跟单管理系统二期需求文档

> **版本：** V1.3
> **日期：** 2026-09-24
> **状态：** 来货出入业务规则已确认；V1.2 固化 Excel 不允许手工新增行，V1.3 按 #127 已确认变更修订单图单产品、取消图片日期识别与候选匹配顺序。
> **本稿范围：** 仅定义“来货出入”首版。周出货回填、月账单生成、工厂分析和库存预警继续留在二期后续需求建设中。

## 1. 目标与范围

仓库收货后，包装环节可能发现实际数量与箱贴不一致。首版由内部管理员把一批现场照片发送给飞书机器人，系统识别差异并生成 Excel 核对表；管理员核对并明确确认后，系统才正式登记差异、调整对应订单规格的有效已发数量，并通知工厂。

本功能必须满足：

1. 原始图片、识别结果、Excel 版本、匹配结果和正式登记可追溯；
2. 图片内容不能唯一确定订单与规格时不猜测、不生效；
3. 同一确认请求不会重复调整数量；
4. 发货单可以不存在，但必须唯一关联采购子单对应的系统订单明细与 SKU；
5. 工厂能够在原订单任务中查看每次来货出入，不把多次登记合并或抵消；
6. 正式登记后的数量允许管理员直接调整，系统只应用新旧值之间的差额并保留审计记录。

## 2. 业务定义与一期边界

### 2.1 来货出入

“来货出入”是仓库已经收货后，在包装环节发现的多货或少货事实：

- 多货使用正数，例如 `+3`；
- 少货使用负数，例如 `-2`；
- 数量归属到唯一的系统订单明细、采购子单和产品规格；
- 一张图片可以产生多条来货出入明细；
- 多张不同图片即使指向同一订单、产品和规格，也分别保存，不自动合并。

### 2.2 与收货差额的区别

一期“收货差额”发生在管理员确认收货时，以确认数量减原报数量计算；二期“来货出入”发生在收货后的包装阶段。两者是不同业务事实，只要分别具有来源证据，就可以先后影响同一订单规格的数量。

系统不得仅因工厂、SKU、方向和数量相同，就把收货差额与来货出入认定为重复。来货出入只按自身批次、版本、来源图片及明确重复确认规则防止重复生效。

### 2.3 与发货单、采购单和订单的关系

- 发货单不是来货出入的必填关联，没有对应系统发货单也允许登记；
- 发货单号不进入首版 Excel 业务列，也不在订单详情中展示；
- 采购主订单号用于核对与汇总，但一张采购主单可能包含多个 SKU，不能单独证明归属；
- 采购子订单号必须能够唯一对应系统中的订单明细与 SKU；
- 正式记录必须保存系统订单明细关联、采购主订单号和采购子订单号；发货单关联如能取得可以作为可选追溯信息保存，但不参与首版登记门槛。

采购关联显式字段的持久化由 [Issue #111](https://github.com/kocotree/order_tracking/issues/111) 单独建设。本需求不重复实现采购来源匹配基础能力。

## 3. 角色与权限

| 角色 | 权限 |
|---|---|
| 已启用管理员 | 向机器人发送图片、生成本人批次的核对表、上传修改后的核对表、确认本人提交的最新有效批次；在管理员网页查看记录并调整数量 |
| 工厂用户 | 在本厂订单任务中只读查看来货出入，接收本厂通知；不能提交、确认或修改 |
| 未启用账号或其他身份 | 不能生成、确认或修改来货出入 |

管理员只能确认自己提交的批次。机器人身份不能绕过管理员业务权限；模型服务的 API Key 只能由服务端受控配置保存，不进入 Excel、网页、小程序、日志或仓库。

## 4. 飞书机器人与 Excel 核对流程

### 4.1 正常流程

1. 管理员向机器人连续发送一张或多张现场图片；
2. 管理员点击“生成核对表”，系统把当前图片集合冻结为一个批次；
3. 系统保存原图，执行 OCR 与大模型结构化识别；
4. 系统按工厂、货号或品名、颜色规格及已保存的采购关联做只读候选匹配；
5. 系统生成一个按工厂分 Sheet 的 Excel，并发送给本批次提交人；
6. 管理员可以直接确认未修改的最新有效版本，也可以修改 Excel 后重新发送给机器人；
7. 系统校验回传 Excel，成功后把它设为本批次最新待确认版本；
8. 管理员明确点击确认；
9. 系统整批登记、调整数量、记录审计并生成工厂通知；
10. 机器人把成功或失败结果回复给提交人。

系统不得仅凭模型置信度自动正式登记。未点击确认前，识别、匹配、Excel 生成和修改都不改变订单数量，也不通知工厂。

### 4.2 Excel 结构

一个批次只生成一个工作簿，每个已识别工厂使用一个 Sheet。无法确定工厂的明细进入“待确认” Sheet；管理员必须把它移动到名称与系统工厂一致的 Sheet 后才能确认。

每个工厂 Sheet 的可见业务列固定为：

| 顺序 | 列名 | 首次生成规则 |
|---|---|---|
| 1 | 名称 | 填写识别到的产品名称 |
| 2 | 规格 | 填写“颜色 / 尺码” |
| 3 | 数量 | 多货为正数、少货为负数 |
| 4 | 单价 | 留空 |
| 5 | 总金额 | 留空 |
| 6 | 采购单号 | 唯一匹配时填写采购主订单号，否则留空待核对 |
| 7 | 入库单号 | 留空 |
| 8 | 图片 | 把来源原图嵌入单元格 |

首版不增加“发货单号”列。系统可以添加核对所需的隐藏技术标识，但不能把它们作为用户需要填写的业务列。结构样例见附录 A.3。

管理员可以修改现有行、删除错误行，以及把行移动到其他工厂 Sheet；**不允许手工新增行**（2026-09-17 技术设计阶段确认）。每行在生成时带一个隐藏技术标识绑定本批次来源图片，手工插入的行没有这个标识，系统无法判断它来自哪张照片，回传时该行直接判失败并报出 Sheet 与行号。漏识别、或错到无法在现有行上改对的明细，重新拍照发一次由系统重新识别，不在 Excel 里补行。移动后的明细仍关联原来的来源图片；不能通过 Excel 写入本批次之外的图片或任意外部记录。

一张图片涉及多条明细时，拆成多行。业务列不合并；图片列可以在连续行中合并同一张图片，但只有在生成、回传解析和人工核对均稳定时采用，否则每行重复嵌入同一原图。两种方式不得改变业务结果。

### 4.3 整批确认

确认采用整批原子规则：

- 全部明细通过校验时一次性正式登记；
- 任一明细失败时整批不登记、不调整数量、不发送工厂通知；
- 系统返回具体 Sheet、行号和失败原因，管理员修改后重新提交；
- 只能确认最新有效 Excel 版本，旧版本和重复确认请求不能生效。

## 5. 图片识别与拆分规则

### 5.1 箱贴与手写标注

箱贴中的工厂、货号、产品、颜色和尺码用于提供默认信息。图片上的手写文字、覆盖文字或聊天标注属于本次实际差异，优先级高于箱贴默认值。一张图片只对应一个产品名称和货号；同一批次允许多张不同产品图片。

示例：

- 只写“110少1，120多1”时，工厂、货号、产品和颜色沿用箱贴，拆成两条规格明细；
- 标注明确写了另一颜色或尺码时，使用标注值，未指定字段才继承箱贴；
- 一张图片有多个颜色或尺码时，按每个明确组合拆成独立明细；
- 无法确定某个字段时保持待确认，不由模型补造。

### 5.2 日期

不识别、不匹配图片发货日期；消息发送时间也不能充当图片日期。历史正式记录已保存的来源业务日期原样保留，新登记记录该字段为空。

### 5.3 多图和重复图片

- 不同照片全部登记，即使它们来自同一纸箱或内容相同；
- 同一图片在另一批次再次提交时，系统提示疑似重复，由管理员明确选择是否作为新的差异继续核对；
- 同一批次、同一 Excel 版本重复点击确认必须直接返回原结果，不能再次调整数量或通知；
- 同一订单、产品和规格在后续批次再次出现时新增明细，不累计成一行，也不自动正负抵消。

## 6. 订单与采购匹配

### 6.1 匹配目标

每条正式来货出入必须唯一确定：

1. 工厂；
2. 系统订单；
3. 订单明细及对应 SKU/规格；
4. 采购主订单号；
5. 采购子订单号。

采购主订单号本身不够；系统必须使用采购子订单号和 SKU/规格校验具体明细归属。

### 6.2 候选依据

系统可以综合使用以下证据缩小候选范围：

- 工厂；
- 货号或产品编码；
- 产品名称；
- 颜色和尺码；
- 系统订单明细；
- 已保存的采购主单、采购子单与 SKU 关联。

货号不自动等同于 SKU、订单号或采购单号。系统不能因为名称相近、数量相同或日期接近就任意选择订单。

### 6.3 匹配结果

- 先以工厂＋货号或品名＋颜色/规格精确定位唯一产品 SKU，再查该工厂、该 SKU 的有效派工及订单明细已保存的采购主单、采购子单关系；SKU 不唯一、采购关系缺失或无有效候选时保持待确认；
- 唯一候选且按统一已发数量口径计算的未发数量大于 0 时自动关联订单明细并填写采购主订单号；唯一候选未发为 0 时不关联；
- 多个候选按合同出货时间从早到晚检查，跳过未发为 0 的订单，关联首个未发大于 0 的订单；无法按该规则唯一确定时保持待确认；
- 管理员填写采购主订单号后，系统仍须校验其采购子单、SKU 和本地订单明细是否唯一一致；
- 没有候选或确认后仍不唯一时，该行校验失败，整批不能登记；
- 没有对应发货单不属于失败条件。

## 7. 数量生效与调整

### 7.1 首次登记

正式确认后，每条明细作为独立的包装阶段数量变化，作用于对应订单规格的系统有效发货数量：

- 多货增加有效已发数量；
- 少货减少有效已发数量；
- 初始已发数量保持不变；
- 调整后的有效已发数量允许超过下单数量；
- 调整后的统一已发数量不得小于 0；
- 未发数量继续按 `max（下单数量－统一已发数量，0）` 计算；
- 本期不因来货出入自动把已经确认完成的订单恢复为未完成。

正式登记不等同于确认整张发货单收货，也不改变其他未涉及明细。

### 7.2 登记后调整数量

管理员网页订单详情中的“来货出入”数量列允许直接编辑。输入完成后自动保存：

- 后端以“新数量－旧数量”的差额调整订单，不能把新数量再次全量叠加；
- 例如从“少2件”改为“少3件”，只再减少1件；
- 保存前再次校验权限、记录版本、订单明细归属和数量下限；
- 保存失败时页面恢复旧值并说明原因；
- 保存成功后记录调整前值、调整后值、操作人和时间；
- 产品、规格、采购关联和订单归属在正式登记后不提供直接编辑；
- 数量调整成功后向受影响工厂生成“来货出入已调整”通知。

数量直接编辑只改变该条记录的当前有效数量，历史审计不能覆盖或删除。

## 8. 页面展示

本节只规定展示内容和信息层级；具体尺寸、样式、控件和交互稿在原型阶段逐页确认。

### 8.1 管理员网页订单详情

在订单详情中展示“来货出入”表格，不在发货单详情新增业务入口。卡片位于“订单明细”之后、“关联发货单”之前，**默认折叠**：标题行整行可点击展开或收起，标题显示本订单来货出入条数；没有记录时显示 0 条且不可展开。

展开后表格展示（2026-09-17 确认，序号与登记时间为本次新增列）：

- 序号；
- 登记时间；
- 采购单号；
- 产品编码；
- 产品名称；
- 颜色/规格；
- 数量。

序号按登记时间正序生成，不是业务编号。登记时间取正式登记成功的系统时间，精确到分钟，只读；同规格多次登记时它是管理员区分具体记录的唯一可见依据。页面已经处于单个订单内，不重复展示关联订单或发货单号。数量列按第 7.2 节允许自动保存，其他列只读；本表不排序、不提供增删行。

### 8.2 工厂小程序订单任务

在工厂任务详情增加可展开区域：

```text
来货出入                         >
```

展开后按产品名称分组；同一产品名称只展示一次，每次登记按发生顺序追加规格行：

```text
小糯壳抓绒衣
云水蓝 / 110                  少2件
云水蓝 / 120                  多1件
云水蓝 / 110                  少1件
```

展示规则：

- 不展示 SKU 编码、采购单号或发货单号；
- 不重复展示当前订单编号；
- 同一规格多次登记时继续向下追加，不合并、不净额计算；
- 不显示“累计”文字，也不在折叠标题展示汇总数量；
- 工厂端只读。

## 9. 工厂通知

### 9.1 首次登记通知

批次登记成功后，按“工厂＋订单”合并通知：

- 同一批次影响同一工厂同一订单时只生成一条通知；
- 发送给该工厂全部已启用用户；
- 站内通知摘要展示受影响产品、规格和多/少数量；
- 点击进入对应工厂订单任务；
- 通知失败不回滚已经登记的数量，重试通知也不能再次调整数量。

### 9.2 数量调整通知

管理员修改已登记数量并保存成功后，向对应工厂生成“来货出入已调整”通知，点击进入同一订单任务查看最新明细。

### 9.3 微信订阅消息

首版复用现有工厂状态模板 `factory_status`，不新增第4个工厂订阅模板。微信外部消息只提示“订单来货出入已登记”或“订单来货出入已调整”，详细产品、规格和数量在站内通知及订单任务中查看。

若后续要求微信消息本身展示多条 SKU 和数量，须另行评审模板字段、订阅授权和模板数量，不属于本稿范围。

## 10. 数据、审计与安全

系统必须保留：

- 原始飞书消息与图片关联；
- OCR/模型识别结果；
- 每版 Excel 及其提交人、提交时间；
- 自动候选、管理员修正及最终采购/订单/SKU 匹配；
- 确认人、确认时间和幂等标识；
- 正式数量及每次调整前后值；
- 工厂通知事件及投递结果。

MySQL 8.0 是正式业务事实库。图片等受控文件使用现有私有附件存储能力，不能公开暴露永久链接。OCR 或模型输出只是候选，不是业务事实；只有管理员确认的最新有效版本能够生效。

## 11. 错误处理

| 场景 | 处理 |
|---|---|
| 图片无法读取或 OCR 失败 | 标记具体图片失败，整批不确认 |
| 工厂无法确定 | 进入“待确认” Sheet，确认前必须移动到有效工厂 Sheet |
| 产品、颜色或尺码不完整 | Excel 标记待确认，不能猜测 |
| 采购主单有多个符合条件的子单 | 要求管理员补充或修正，仍不唯一则失败 |
| 没有系统发货单 | 允许继续，只要订单明细与采购子单唯一 |
| 没有唯一订单明细或采购子单 | 整批失败，不调整数量 |
| 少货会使统一已发数量小于0 | 拒绝确认或拒绝本次自动保存 |
| Excel 被篡改、版本过期或技术标识无效 | 拒绝并要求重新生成/上传 |
| Excel 中出现手工新增行 | 该行判失败、整批不确认；漏识别的明细重新拍照识别 |
| 重复确认 | 返回原确认结果，不重复生效 |
| 通知发送失败 | 保留正式登记，按现有通知重试机制处理 |

## 12. 明确排除项

本稿不包含：

- 无人工确认的自动正式登记；
- 工厂、仓库人员或其他角色提交来货出入；
- 飞书自由文本逐字段修改；
- 语音输入；
- 把发货单作为必填关联或在发货单详情展示来货出入；
- 自动填写单价、总金额和入库单号；
- 月账单生成、价格结算、付款申请；
- 每周 Base 出货回填；
- 工厂指标、AI 月报、库存风险和自动催货；
- 自动修改聚水潭采购、库存或入库数据；
- 因来货出入自动回退已完成订单状态；
- 生产机器人启用、真实通知发送、版本发布和部署。

## 13. 验收标准

| 编号 | 验收场景 | 通过条件 |
|---|---|---|
| AC-01 | 单图单规格少货 | 识别成一条负数明细，核对前不生效，确认后只调整对应订单规格 |
| AC-02 | 单图多个规格 | 按明确颜色/尺码拆行，标注优先于箱贴默认值 |
| AC-03 | 同批多图不同产品 | 每张图只对应一个产品名称和货号；同批不同产品图片分别拆行并保留各自原图 |
| AC-05 | 无对应发货单 | 采购子单与订单明细唯一时仍可确认登记 |

| AC-07 | Excel 改行、删行和跨 Sheet 移动 | 回传后重新校验，来源图片、工厂和订单归属保持可追溯；手工新增行一律判失败并报出 Sheet 与行号 |
| AC-08 | 批次存在一条失败明细 | 整批不登记、不调整数量、不通知工厂，并返回具体错误行 |
| AC-09 | 重复确认同一版本 | 返回原结果，数量与通知均不重复 |
| AC-10 | 相同图片再次提交 | 提示疑似重复；只有管理员明确继续后才作为新批次核对 |
| AC-11 | 收货差额后又发现包装差异 | 两个有独立证据的业务事实分别生效，不因SKU和数量相同自动抵消 |
| AC-12 | 少货越过数量下限 | 确认或调整失败，订单数量保持原值 |
| AC-13 | 多货超过下单量 | 允许保存并保留超发事实，未发数量保持0 |
| AC-14 | 修改已登记数量 | 只应用新旧差额，保留审计并通知工厂；失败恢复旧值 |
| AC-15 | 工厂订单任务展示 | 按产品分组、逐次追加规格行，不展示SKU、不累计、不重复订单号 |
| AC-16 | 通知失败重试 | 正式登记不回滚，重试只补发通知，不再次调整数量 |
| AC-17 | 权限 | 仅已启用管理员可确认本人批次，工厂端只读 |

## 附录 A 机器人消息与按钮文案

### A.1 正常流程

### A.2 异常回复

与第 11 节错误处理逐项对应，同一批次的多条错误合并在一条回复中列出，最多展示前 10 条并提示剩余条数。

| 场景 | 机器人回复 |
|---|---|
| 图片无法读取或 OCR 失败 | `第 {n} 张图片无法识别（{reason}），本批次未生成核对表。请重拍后重新发送。` |

## 附录 B Codex 管理员接入（Issue #151）

本附录仅约束二期 Codex 接入基础能力。所有已启用管理员以本人账号通过受信任 Codex 客户端查询本人身份、看板、订单列表、详情和订单操作记录，筛选、排序、分页和角色边界与管理员网页一致。工厂账号、停用账号不得接入。工具提供本人统一退出，退出后同账号 Web 与 Codex 的旧凭据立即失效。

受信任客户端通过 OAuth Authorization Code 与 PKCE 接入；浏览器已有有效管理员登录时自动继续，未登录时完成现有飞书登录后继续。授权仅接受登记的客户端和回调、固定 MCP 资源及本人身份，不增设授权确认页和客户端管理页。Codex 使用独立短期凭据，不能获得 Web Cookie 或飞书令牌。

同账号 Web 与 Codex 共享最近有效业务活动时间。任一端有效业务使用可延长共同资格；刷新、轮询及失败请求不保活。连续 30 天无有效业务活动后，两端旧凭据失效。统一退出、停用或共同资格到期立即阻断两端；重新登录创建新资格，不恢复旧 grant。现存有效 Web 会话迁移时沿用已有活动时间，过期或已撤销会话不恢复；小程序会话规则保持现状。

验收覆盖真实 Codex 登录与查询、错误客户端/回调/资源/PKCE、授权码与刷新重放、30 天期限、跨端活动、多设备及并发退出、重启、代理与独立 MySQL 迁移。未具备真实环境的项目须明确记录为未验收。

## 附录 C Codex Excel 文件与质检返修（Issue #155）

已启用管理员可在 Codex 提供标准 `.xlsx` 质检单，每批最多 20 份、每份最多 20 MiB，一份文件只归属一个工厂。上传后逐份校验、预览，确认后复用一期质检返修的任务、周期、私有原件和通知流程。上传与解析不会自动创建任务；损坏、伪造扩展名、非 `.xlsx`、超限、匹配失败、重复文件及过期预览均给出对应文件的结果。Codex 可按网页相同权限查询周期、详情、归档已完成周期，并取得受权的原件下载。

批量确认默认先检查全部预览，存在错误即不创建本批任何任务。管理员明确允许部分执行时才逐份处理合格项；中途失败须报告成功、失败和未执行的每份结果，重试沿用原预览和幂等键。任务创建、通知发出及工厂实际查看分别核验。返修仍独立于正常订单数量。

文件来源仅接受经目标客户端联调确认的 HTTPS 主机，拒绝内部地址和越界跳转，传输设大小与超时上限。原件保存在既有私有存储中，下载须本人授权，不能提供公开永久附件链接。完整验收必须在真实 Codex 中完成本地引用和拖入附件的上传、预览、创建及本地接收下载，校验大小与哈希；协议模拟和网页上传不能替代此项。
